# PBR統合の考え方

本章では、30章のPBR照明と23〜25章の画面効果を土台に、`ComputeEffectPipeline`で一つの画面へ統合します。
G-buffer、シャドウ、SSAO、遅延照明、SSR、透明・屈折、フォグ、DoF、ブルーム、トーンマッピングなどを、同じカメラフレームと中間画像を使って正しい順序で実行します。
各処理の色、深度、座標の意味を揃え、GPUリソースの作成、画面サイズ変更、破棄までを一つの構成として扱えるようにします。
単純な標準Forward描画だけを使うアプリケーションは、`WebgApp`と`SmoothShader`の標準構成を利用できます。

## この章の読み方

### この章を読む前に必要な知識

30章のPBR（Physically Based Rendering：物理ベースレンダリング）、23章のポストプロセス、21章の接続方法を知っていると読みやすくなります。

### 初回に読む範囲

標準Forward、個別パス、PBR統合の選択と、G-buffer（照明計算へ渡す画面単位の表面情報）から表示までの順序を先に読んでください。

### 必要になったときに読む範囲

HDR（High Dynamic Range：広い輝度範囲）、透明、Transmission、SSR（Screen Space Reflections：画面空間反射）、トーンマッピング、HUD（Head-Up Display：画面へ重ねる情報表示）の順序は複数効果の統合時に参照してください。

### この章を終えた時点でできること

必要な効果に応じた描画経路を選び、各処理の色・深度・カメラ情報の意味を説明できます。

## 統合で使う三つの入力を知る

画面効果を組み合わせる前に、表面情報、光量、カメラ情報を分けて考えます。G-bufferは、画面の各画素に見えている表面の基本色、法線、材質、深度を保持する画像の組です。照明処理はこれを読み、線形HDRという広い明るさの範囲で光量を計算します。表示直前にトーンマッピングで画面へ収まる色へ変換します。

カメラフレームは、一回の描画で使う視点、投影、深度の情報をまとめたものです。同じ情報を描画と後段の効果へ渡すことで、深度から求める位置を、その画面を描いた視点へ揃えられます。

本章は各効果を並べる理由を、32章は接続コードを説明します。個々の効果の計算と調整は34〜36章、格納形式と深度の詳しい規則は41章で確認できます。この順で、まず完成画面へ至る全体像をつかみ、必要な処理を詳しく学びます。

## 最初に描画構成を選ぶ

同じPBRマテリアルを使う場合でも、必要な画面効果に応じて入口を選びます。PBR照明を中心に構成する画面は、標準のForward経路へPBRシェーダーを組み合わせる入口を選べます。

**描画構成：標準フォワード描画**

適する画面：Shapeを直接照明する色中心の画面

利用する入口：`WebgApp`の標準描画と`SmoothShader`

**描画構成：個別パスの手動接続**

適する画面：一つまたは少数の画面効果を処理順まで自分で組みたい画面

利用する入口：III部とIV部の各Render/Compute Pass

**描画構成：PBR統合パイプライン**

適する画面：G-buffer、遅延照明、SSR、透明・屈折、複数の画面効果を共有する画面

利用する入口：`ComputeEffectPipeline`

まず最小の構成を選び、必要な入力と効果が増えた段階で次の構成へ進みます。

## 個別の効果を1本の描画パイプラインへまとめる

統合パイプラインは、複数の画面効果を同時に使うアプリで、中間テクスチャを誰が管理するか、どの順序で処理するか、どのカメラ情報を共有するかを一箇所にまとめるために使います。
SSAO、シャドウ、SSR、DoF、ブルームはそれぞれ単独でも実行できますが、利用側で手組みすると、同じ画面サイズのターゲットを別々に管理したり、あるフレームの深度を別のカメラ設定で復元したり、トーンマッピングを二度行ったりする余地が生まれます。
統合すると、効果の追加時にも既存の色形式と深度規則を再実装せずに済みます。

GPUリソースやパスは、作成し、フレーム間で保持し、画面サイズに合わせて更新し、正しい順序で使用し、不要になったときに破棄するまでを一つのオブジェクトが管理します。
管理するオブジェクトを一つに決めると、同じ用途のテクスチャを二重に作ることや、使用中のリソースを別の処理が破棄することを防げます。

`ComputeEffectPipeline`は、これらのリソース管理と実行順序をまとめる統合APIです。
利用者はシーン、カメラフレーム、効果の設定を渡し、パイプラインはG-bufferから表示テクスチャまでの入力形式、実行順序、カメラ状態の整合性を検証します。

統合パイプラインは、G-buffer、画面空間効果、複数の後処理をまとめたいアプリケーションで選びます。標準のフォワードレンダリング経路は、単純な表示を構成する入口として使い分けます。
`WebgApp`の標準シェーダーで`Space`を直接描く場合は、カメラ用Reverse-Zとカメラ相対レンダリングが内部で適用されます。
遅延レンダリング経路の統合パイプラインが必要なのは、G-buffer、遅延照明、複数の画面空間のエフェクトを共有して使う場合です。

現在の標準的なPBR統合例は`examples/33_01.html`です。31〜33章の最初の二つのコード例は比較のための接続点を説明し、33_01はenvironment、手続きマテリアル、透明・屈折を含む一つの実行可能なファイルとして全体を示します。IBL用の環境は照明と反射へ使い、画面背景には独立した青灰色のclear colorを表示します。

[PBR統合例を実行する](examples/33_01.html)

## シーンの説得力を空間の関係から作る

複雑なモデルや高解像度のテクスチャに加えて、床と物体の接触、壁と柱の隙間、光を遮る物体と影、滑らかな面と反射像の関係を画面へ反映すると、3Dシーンの立体感が生まれます。
床と物体の接触、壁と柱の隙間、光を遮る物体と影、滑らかな面と反射像のように、ピクセル間の空間的な関係が視覚的な手がかりを作ります。

SSAOは周囲の面による環境光の遮蔽、シャドウは光源と表面の間の遮蔽、SSRは視点から見える反射先を追加します。
フォグはカメラから表面までの距離に応じて空気の厚みを表し、DoFは奥行きのどの範囲を見せるかを決め、ブルームは表示範囲を超える光量を周囲のにじみとして可視化します。
これらはマテリアルの物理特性だけでなく、物体、カメラ、光源の関係を画面へ反映させる処理です。
ビネットは三次元的な関係を再評価せず、完成した表示色の周辺を整えて視線を導きます。

統合の目的は、シーンで必要な手がかりを選び、同じ幾何情報と照明情報から一貫して生成することです。
屋外の広いシーンならシャドウとトーンマッピング、狭い室内ならSSAOと反射、スタイライズした画面ならトゥーンと輪郭抽出のように、役割に応じて構成します。

## 出力の意味に沿って統合順序を決める

描画順序は、可視性を正しい光へ作用させ、HDR（High Dynamic Range：広い輝度範囲）の光量を必要な効果まで残し、表示変換を一度だけ行うために決めます。
この順序を共有すると、効果の有効・無効の切り替えや設定変更を行っても、同じ入力が別の意味で解釈されるのを防げます。
統合パイプラインの標準順序は次のようになります。

![PBR統合パイプライン](img/fig31_01_compute_effect_pbr_flow.jpg)

```text
シャドウマップ（ライトビュー / 通常Z）
             \
カメラフレーム -> G-buffer（カメラビュー / Reverse-Z）
                     |
                     +-> シャドウ可視率
                     +-> SSAO可視率
                     |
                     v
              PBR遅延ライティング（直接光 + IBL / HDR）
                     |
                     +-> SSR反射 -> 鏡面IBLを置換
                     |
                     v
              Transmission / 背景ぼかし / 透明PBR
                     |
                     v
                   フォグ（HDR）
                     |
                     v
             トゥーン -> DoF -> ブルーム（HDR）
                     |
                     v
              トーンマッピング（表示色）
                     |
                     v
              輪郭抽出 -> ビネット
                     |
                     v
          最終表示 -> 画面上の情報表示（Head-Up Display：HUD）
```

シャドウマップはライトビューの通常Z、G-bufferはカメラビューのReverse-Zです。
AO（Ambient Occlusion：環境遮蔽）とシャドウは光が届く割合である可視率を返し、遅延ライティングが環境光と直接光へ別々に適用します。
SSRは独立した反射成分を作ってHDRシーンへ合成します。
半透明はその合成済みHDRシーンへ加え、フォグは透明合成後の画面全体へ一度だけ適用します。
その後のトゥーン、DoF、ブルーム、トーンマッピングも、不透明部分と半透明部分を一緒に通します。
輪郭抽出とビネットは表示色を処理し、最終表示より前、HUDより前に完了します。

この順序は、各パスの出力が持つ意味から決まります。例えばトーンマッピング後にブルームやフォグを置くと、明るい画素が0〜1へ圧縮された表示色になるため、線形HDRの光量を使う処理は前段へ配置します。
SSAOを色へ直接乗算してから遅延ライティングへ渡すと、直接光まで環境遮蔽で暗くしてしまいます。
ビネットをHUDの後へ置くと、シーンだけでなく操作表示まで暗くなります。
各パスの出力が何を意味し、画面のどの要素を対象にするかによって順序が決まります。

### HDR環境をPBR照明へ渡す

実写HDRによる画像ベース照明（Image-Based Lighting：IBL）を使う場合は、`PbrEnvironment`を初期化時に一度作り、`ComputeEffectPipeline`の`lighting.environment`へ渡します。同じ環境光データを、不透明物の遅延照明、PBR向けSSR、透明物の前方照明で共有します。

```js
const pbrEnvironment = new PbrEnvironment(gpu, environmentData);

const pipeline = new ComputeEffectPipeline(gpu, {
  width,
  height,
  lighting: {
    ambient: 0.0,
    // class内部のgpuや破棄状態を渡さず、照明用に公開されたresourceだけを渡す
    environment: pbrEnvironment.getResources(),
    environmentIntensity: 1.0,
    environmentBackground: true,
    environmentRotationDegrees: 0.0
  },
  composer: {
    mode: "pbr-ssr"
  }
});
```

環境光を有効にした状態で`ambient`を0以外へ設定すると、固定環境光とIBLが二重になるため例外になります。背景と照明の向きをそろえるには、`environmentRotationDegrees`で放射輝度による背景、拡散反射用の放射照度、事前積分済み鏡面環境へ同じ回転を適用します。

`composer.mode: "pbr-ssr"`は、SSRの交差が見つかった範囲で、遅延照明が出した鏡面反射を画面内の放射輝度へ置き換える指定です。交差がない範囲には元の環境反射を残し、画面内の情報とIBLを使い分けます。

### 透明PBRとTransmissionを接続する

透明三角形があるフレームでは、PBR遅延照明とSSRの後に`TransparencyPass`が動作します。処理は、Transmission用の入射面・射出面情報、背景屈折、粗さによる背景ぼかし、透明表面のPBR前方描画の順です。

```js
const finalColor = pipeline.encode(gpu.commandEncoder, {
  cameraFrame,
  ssrEnabled: true,
  transparency: {
    transmissionEnabled: true,
    transmissionStrength: 1.0,
    transmissionDistance: 80.0,
    transmissionHitThickness: 0.35,
    transmissionSteps: 48,
    transmissionRayMissFallback: "auto"
  }
});
```

Transmissionは透明物内部の射出面と、不透明物のG-bufferにある背景表面を画面空間で探索します。入射面と射出面で二回のスネルの法則による屈折を計算し、内部光路長へBeer-Lambert吸収を適用します。その後に透明表面自身のGGX反射をsource-over方式で合成します。

`transmissionRayMissFallback`では、設定時に必要な入力と、レイ探索後に背景へ到達できなかった場合の出力を分けて考えます。

| 指定値 | 設定時に必要な入力 | 外向き方向があり、背景交点が得られない場合 |
| --- | --- | --- |
| `"auto"` | なし | radianceがあれば環境色、なければclear color |
| `"environment"` | environment radiance | 外向き方向の環境色 |
| `"clear"` | `renderScene()`のclear color | clear color |
| `"constant"` | `transmissionRayMissColor` | 指定した固定色 |

`"environment"`にはenvironment radiance、`"constant"`には固定色を用意します。入力が不足した場合は例外で知らせ、指定したmodeの前提を明確にします。

入力がそろっていても、内部境界を発見できない場合や、2回目の境界でも全反射して外向き方向を決められない場合があります。この場合は環境を参照する方向自体がないため、`"constant"`だけが指定固定色を使い、ほかのmodeはclear colorを使います。これはenvironment radianceの不足とは異なる、レイ探索結果による分岐です。

```js
transparency: {
  transmissionEnabled: true,
  transmissionRayMissFallback: "constant",
  transmissionRayMissColor: [0.04, 0.06, 0.10, 1.0]
}
```

clear colorと`transmissionRayMissColor`は表示用sRGB色です。ほかのmodeで`transmissionRayMissColor`を指定した場合も、使われない値を受け入れず例外になります。

透明物がないフレームでは、`TransparencyPass`のマスク、レイ探索、すりガラス用ぼかし、前方描画を省略します。Transmissionを無効にしてもアルファ透明とすりガラスは別機能なので、透明三角形があれば必要な処理だけを実行します。

### 色の意味を保ったまま表示へ渡す

色の段階を分ける目的は、マテリアルの基本色、照明後の光量、ディスプレイへ出す色を混同せず、それぞれに適した効果を適用することです。
G-bufferのアルベドは照明前の基本色です。
遅延ライティングがマテリアル、法線、可視性、光源から線形HDRシーンを作ると、値は1.0を超えることがあります。
SSR、トゥーン、DoF、ブルームはこのHDR値を読み、光量の意味を保ったまま`rgba16float`で次へ渡します。

`ComputeEffectComposer`は照明結果とSSR反射を合流させます。
`mix`は反射のアルファの重みに応じてシーン色と反射色を補間するため、マテリアル色を残しやすい合成です。
`add`は反射色を追加し、発光的な強調に適しますが、反射面が多い画面では白くなりやすくなります。
透明合成後の`ComputeFogPass`もこの線形HDR区間でシーン色とフォグ色を混合します。

G-bufferへ渡す`color`とカラーテクスチャは、利用者が色を選ぶときと同じsRGB色です。
アルベドアタッチメントは`rgba8unorm-srgb`なので、保存時はsRGBで符号化され、シェーダーから読むときは線形色へ復号されます。
遅延照明へ渡すアルベドは、光量の計算に使える線形値です。表示用の色から線形値へ変換して渡します。
ここで色をもう一度sRGBから復号すると暗くなり、復号せず表示色のまま照明すると中間調が白っぽくなります。

トーンマッピングは、線形HDRの値域をディスプレイ用の範囲へ移す変換段階です。
`exposure`でトーンマッピング前の光量を決め、`mode`で高輝度の圧縮方法を選びます。
`reinhard`は`color / (color + 1)`で高輝度を連続的に圧縮し、`linear`は0から1の範囲へ切り詰めます。
その後、暗部の線形区間を含む正確なsRGB伝達関数で表示色へ変換し、`saturation`で彩度を調整します。

`gamma`は、正確なsRGB変換後の表示上の明るさを調整する値です。標準のsRGB変換後に`pow(srgbColor, 2.2 / gamma)`を追加します。
既定の`gamma: 2.2`では指数が1となるため、正確なsRGB変換の結果をそのまま保ちます。
トーンマッピング前の各効果でガンマ変換を行ったり、最終出力をさらに`sRGB`アタッチメントで符号化したりすると二重変換になるため、表示変換は`ComputeEffectToneMapPass`の一度だけにします。

- **G-bufferのアルベド**
  - 形式：`rgba8unorm-srgb`
  - 意味：sRGBで保存する照明前の基本色
  - 読み出し時には線形となる
- **G-bufferのマテリアル**
  - 形式：`rgba8unorm`
  - 意味：`specular`、`roughness`、`metallic`、`occlusion`
- **G-bufferの発光**
  - 形式：`rgba16float`
  - 意味：線形HDRのemissive color
- **遅延ライティングからフォグ、ブルームまで**
  - 形式：`rgba16float`
  - 意味：線形HDRの光量
- **トーンマッピング後**
  - 形式：`rgba8unorm`
  - 意味：sRGB伝達関数で符号化済みの表示色
- **輪郭抽出とビネット**
  - 形式：`rgba8unorm`
  - 意味：提示前に整える完成表示色
- **最終表示**
  - 形式：スワップチェーン形式
  - 意味：キャンバスへ提示する最終画像

背景も形状と同じ色・深度の流れへ含めます。
`renderScene()`へ渡した`clearColor`は表示用sRGB色として解釈され、G-bufferのアルベドクリア値へ線形色として入ります。
背景のReverse-Z深度は0なので、遅延ライティングは位置や光源を評価せず、そのアルベドクリア値をHDR出力へ引き継ぎます。
最終的には形状と同じトーンマッピングを受けるため、`reinhard`を選んだ場合は背景色も圧縮されます。
独自の空やグラデーションを使う場合は、遅延ライティングの固定色に頼らず、アプリケーションが背景を描画または合成します。

輪郭抽出は、この表の表示色区間に置きます。
`ComputeEdgePass`が受け付けるシーン色は`rgba8unorm`または`bgra8unorm`であり、出力は`rgba8unorm`です。
`rgba16float`のHDR色を直接渡すと、表示上の輝度差を抽出する役割と一致しないため例外になります。
統合パイプラインではトーンマッピング後に輪郭抽出を置き、個別に接続する場合も同じ処理順序を守ります。

ビネットは輪郭抽出の結果を含む`rgba8unorm`表示色を受け取り、同じ形式で最終テクスチャを返します。
ビネットは完成色と画面サイズを入力に使い、深度や`cameraFrame`から独立して処理します。
画面の周辺調整をトーンマッピング前の光量計算へ混ぜず、最終表示とHUDの間にも挟まないことで、シーン全体には作用し、後から描くHUDには作用しない範囲を明確にします。

## まとめ

PBR統合では、G-buffer、照明、反射、透明、フォグ、画面効果、表示変換を、入力データの意味に合わせて一つの順序へ並べます。画面へ表示する色、後段で使うHDRの光量、深度から復元する位置を混同しないことが重要です。
次に32章で、`ComputeEffectPipeline`へこの順序を接続する最小実装を確認します。
