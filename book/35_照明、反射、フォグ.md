# 照明、反射、フォグ

## この章の読み方

### この章を読む前に必要な知識

30章のPBR（Physically Based Rendering：物理ベースレンダリング）と、34章のG-buffer（照明計算へ渡す画面単位の表面情報）・SSAO（Screen Space Ambient Occlusion：画面空間で求める環境遮蔽）を知っていると読みやすくなります。カメラとシャドウの深度規則は41章で参照できます。

### 初回に読む範囲

遅延照明、シャドウマップ、SSR、フォグの入出力を先に読んでください。

### 必要になったときに読む範囲

多数の光源、ローカルライト、反射交差判定、背景、距離計算は組み合わせるときに参照してください。
水面の反射・屈折や水中の集光を加える場合は、「水面とコースティクスを追加する」へ進みます。

### この章を終えた時点でできること

照明、影、反射、空気の厚みを別々の画面処理として接続できます。
水面と集光をPBRへ独立に接続し、波・吸収・対象登録・GPU資源の寿命を管理できます。

## 遅延照明で多数の光源を評価する

遅延ライティングは、多数の動的な光源が複雑なジオメトリを照らすシーンで、光源を追加するたびに同じShapeを描き直す処理を避けるために使います。
まず照明を計算せずに不透明なShapeを一度だけG-bufferへ描き、次に画面の各画素でアルベド、法線、マテリアル、深度を読み、その画素に作用する光源を評価して照明済みのHDRシーン色を作ります。
光源数が増えても、頂点変換、ラスタライズ、マテリアルアタッチメントの生成といったジオメトリ処理は一度のままであり、ジオメトリの複雑さとライティングの複雑さを分けて管理できることが大きな利点です。

光源を増やすと、光源ごとの照明計算が増えてGPU負荷も変化します。
現在の`DeferredLightingPass`は各画素で有効なローカルライトを順に評価する基本構成なので、照明段階の計算量は画素数と光源数に応じて増えます。
それでも、光源ごとにシーン全体を再描画する方式と比べれば、ジオメトリの再処理を避けられます。
多数の光源を使うときは`lightCount`と描画解像度を計測し、さらに大規模なシーンではタイル分割やクラスタリングを別の最適化課題として検討します。

`DeferredLightingPass`は、アルベド、表面マテリアル、ビュー空間法線、カメラの深度、AO可視率、シャドウ可視率、光源を読みます。
各可視率を先に色へ乗算して受け渡すのではなく、環境光と直接光のどちらへ作用するかを照明式の中で区別します。
そのため、AOで環境光だけを弱め、シャドウで直接光だけを遮り、発光成分はどちらにも暗くされないという、入力の役割に沿った合成ができます。

ここで使うBRDF（Bidirectional Reflectance Distribution Function：双方向反射率分布関数）は、光の入射方向、視線方向、法線、マテリアルから、表面がどの方向へどれだけ光を反射するかを求める式です。
`DeferredLightingPass`は、微小な面の向きの分布を仮定するGGX反射モデルで、拡散反射と鏡面反射をまとめて評価します。

概念上の関係は次のようになります。
環境光にもFresnel反射と金属度による拡散成分の減少を適用し、完全な金属では鏡面環境反射を中心に評価します。

```text
F0 = mix（0.04 × specular, アルベド, metallic）
環境拡散光 = アルベド × 環境光 × AO可視率 × 環境光の拡散割合
直接光 = GGX BRDF（アルベド、法線、視線、光、表面マテリアル）× シャドウ可視率
発光 = アルベド × emissive
HDRシーン色 = 環境拡散光 + 直接光 + 発光
```

### 標準シェーダーの値を読み替える

標準の`SmoothShader`から遅延ライティングへ移るときは、同じ名前のマテリアル値を同じ数値のまま渡せば同じ見え方になる、と考えないことが重要です。
二つの経路は同じ`Shape`を描画できますが、`SmoothShader`はPhong型の簡潔な照明式を使い、`DeferredLightingPass`はGGX型のマテリアルモデルを使います。
パラメーターの役割を読み替えることで、暗さやハイライトの違いを不具合とマテリアルモデルの違いに切り分けられます。

- **color**
  - `SmoothShader`：入力された基本色をPhong型の照明計算へ使う
  - 遅延ライティング：sRGB色から線形アルベドへ変換し、G-bufferへ保存する
- **ambient**
  - `SmoothShader`：Shapeごとの最低照度と、直接拡散光との配分を決める
  - 遅延ライティング：G-bufferへ保存せず、照明パス全体の環境光強度を`encode()`へ渡す
- **specular**
  - `SmoothShader`：白いハイライトを加える強度として使う
  - 遅延ライティング：非金属の法線入射反射率F0を`0.04 × specular`で求める
- **power**
  - `SmoothShader`：Phong型ハイライトの鋭さを決める
  - 遅延ライティング：使用しない
- **roughness**
  - `SmoothShader`：使用しない
  - 遅延ライティング：GGX反射の粗さを決める
- **metallic**
  - `SmoothShader`：使用しない
  - 遅延ライティング：アルベドを拡散色と金属の鏡面反射色へ配分する
- **emissive**
  - `SmoothShader`：照明に依存しない基本色へ近づけ、鏡面反射を弱める
  - 遅延ライティング：`アルベド × emissive`を通常照明へ加算する

`color`は利用者から見ると、どちらの経路でも物体の基本色です。
ただし、計算途中の扱いは異なります。
`SmoothShader`は入力値をそのまま照明式へ使います。
G-buffer経路は`color`とカラーテクスチャをsRGB色として受け取り、それぞれを線形色へ戻してから乗算します。
遅延ライティング、SSR、ブルームなどは線形HDR色を処理し、最後のトーンマッピングで表示用sRGB色へ戻します。
このため、同じ`color`でも、照明式だけでなく色空間と最終表示変換の違いが見え方へ現れます。

`ambient`は、特に混同しやすい値です。
`SmoothShader`では、概念上、次のように暗部の最低照度を確保しながら、残りを直接拡散光へ割り当てます。

```text
拡散係数 = ambient + max（法線・光方向の内積, 0）×（1 - ambient）
```

正面から光を受ける非発光面では、環境光と直接拡散光を合わせた係数が概ね1になります。
一方、遅延ライティングの`ambient`は、直接光から独立した線形の環境光強度です。
AO可視率、Fresnel反射、`metallic`による拡散成分の減少を適用してから、直接光へ加えます。
したがって、標準経路の`ambient: 0.18`と遅延ライティングの`ambient: 0.18`は、それぞれの照明式における係数として解釈します。

`specular`も数値の尺度が異なります。
`SmoothShader`の`specular: 0.6`は、最大0.6の白いハイライトを基本色へ加える係数です。
非金属の遅延ライティングでは、同じ0.6からF0を次のように求めます。

```text
F0 = 0.04 × 0.6 = 0.024
```

この0.024は、光が面へ正面から入ったときに鏡面反射へ配分する割合です。
`metallic`を上げると、F0は`0.04 × specular`からアルベドへ近づき、同時に拡散反射が減ります。
そのため、遅延ライティングのハイライトは、`specular`だけでなくGGXの`roughness`と照明条件を合わせて調整します。

ハイライトの広がりは、標準経路では`power`、遅延ライティングでは`roughness`で調整します。
大きな`power`と小さな`roughness`は、どちらも狭いハイライトを作ります。
Phong型とGGX型では、ハイライトの中心、裾の広がり、斜めから見たときの変化が異なります。移行時は同じ見た目の再現より、材質の意図に合わせて`roughness`と`specular`を再調整します。
見た目を比較するときは、`power`と`roughness`を同じ数値へ揃えるのではなく、ハイライトの幅が近くなる組み合わせを基準にします。

同じShapeを両方の経路で使う場合は、片方が読まない値も含めてマテリアルを完全に設定できます。
次の例では、`ambient`と`power`を`SmoothShader`が使い、`roughness`と`metallic`をG-bufferと遅延ライティングが使います。
`color`、`specular`、`emissive`は両方が読みますが、照明式の中での意味は経路ごとに異なります。

```js
shape.setMaterial("smooth-shader", {
  has_bone: 0,
  use_texture: 0,
  color: [0.72, 0.24, 0.10, 1.0],
  ambient: 0.18,   // SmoothShaderが読むShapeごとの値
  specular: 0.60,  // 両方が読むが、反射モデル内の意味は異なる
  power: 40.0,     // SmoothShaderのPhong型ハイライト
  roughness: 0.42, // 遅延ライティングのGGX反射
  metallic: 0.0,   // 遅延ライティングの金属度
  emissive: 0.0
});
```

固定環境光を使う場合、遅延ライティングの環境光は照明を実行するときに`lighting.ambient`へ別途指定します。実写HDRの`environment`を使う場合は、irradianceとprefiltered specularが環境照明を担当するため、`ambient`は0に設定します。
次の0.035は、遅延ライティングで基準画像を作るための一例です。0.18から機械的に換算せず、材質と照明の組み合わせで調整します。
シーンの光量、背景、露出、トーンマッピングを含めて調整します。

```js
const comparisonHdrScene = deferredPass.encode(
  app.getGPU().commandEncoder,
  {
    ...gbuffer.getBindingResources(),
    shadowVisibility,
    spotShadowVisibility,
    ambientOcclusion: aoVisibility
  },
  {
    cameraFrame,
    directionalLight: null,
    spotLight: null,
    ambient: 0.035,
    lights,
    lightCount: lights.length,
    view: "lighting"
  }
);
```

`emissive`は標準前方描画との比較用に残る従来のスカラー入力です。物理ベースレンダリング（Physically Based Rendering：PBR）のテクスチャまたはglTFマテリアルでは、色を持つ`emissive_factor`と任意の`emissive_texture`を使い、独立したHDR発光色を作ります。
`SmoothShader`では値を1へ近づけるほど通常照明を弱め、照明に依存しない基本色へ近づけます。
従来のscalar入力では`アルベド × emissive`を通常照明へ加算するため、`emissive: 1.0`でも直接光は残ります。PBR入力では、線形化したemissive textureとemissive factorを乗算し、base colorとは独立した`rgba16float` attachmentへ保存します。
経路を切り替えるアプリでは、発光値を共有する前に、どちらの合成を意図するかを確認してください。

実際の差は`samples/materials`で確認できます。
4×4の球体を表示し、行方向で`roughness`と`power`、列方向で`specular`と`metallic`を変えます。
コマンドパレットから描画経路と各値を切り替えられるため、標準経路が`roughness`と`metallic`を読まないこと、遅延ライティングが`power`を読まないことも確認できます。
このサンプルでは照明モデルの比較へReinhard変換の圧縮を混ぜないよう、遅延ライティングの最終表示を線形切り詰めにしています。

ローカルライトは全方向の`point`と、放射方向を持つ`cone`を同じ配列で扱います。

```js
import DeferredLightingPass from "./webg/DeferredLightingPass.js";

const deferredPass = new DeferredLightingPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  maxLights: 128
});
await deferredPass.ready;

const lights = [{
  type: "point",
  position: [0.0, 2.5, -4.0],
  color: [1.0, 0.55, 0.18],
  radius: 9.0,
  intensity: 3.2
}, {
  type: "cone",
  position: [4.0, 6.0, -2.0],
  direction: [0.0, -1.0, 0.0],
  color: [0.45, 0.72, 1.0],
  radius: 12.0,
  intensity: 2.4,
  innerAngle: 32.0,
  outerAngle: 48.0
}];

const hdrScene = deferredPass.encode(
  app.getGPU().commandEncoder,
  {
    ...gbuffer.getBindingResources(),
    shadowVisibility,
    spotShadowVisibility,
    ambientOcclusion: aoVisibility
  },
  {
    cameraFrame,
    directionalLight: {
      direction: [0.35, -1.0, -0.25],
      color: [1.0, 0.96, 0.88],
      intensity: 1.0
    },
    spotLight: null,
    ambient: 0.10,
    lights,
    lightCount: lights.length,
    view: "lighting"
  }
);
```

`directionalLight`と`spotLight`は、使わない場合もオプション自体を省略せず`null`で明示します。
これにより、光源の設定漏れと、意図して使わない場合を区別できます。

ローカルライトは`type`、`position`、`color`、`radius`、`intensity`が必須です。
`position`はワールド座標で渡し、パスがカメラフレームを使ってカメラ相対なビュー空間へ変換します。
`type: "cone"`ではさらにワールド方向の`direction`と、度単位の`innerAngle`、`outerAngle`を渡します。
角度は`0 < innerAngle < outerAngle <= 90`である必要があり、inner内は係数1、innerからouterの間は滑らかに減衰し、outer外は0になります。
光円錐の角度が有効な範囲では円錐光源として扱い、角度設定に応じてポイント光源から切り替わります。

### ローカルライトを調整する

照明が暗いときは、画面全体を一度に補正する前に、暗い原因が光量、到達距離、照射角、環境光のどれにあるかを分けます。
各値は似た見た目を作る場合がありますが、変化する範囲と負荷の意味が異なります。
一つずつ変更すると、マテリアルやトーンマッピングの影響と混同せずに調整できます。

- **intensity**
  - 変化：現在の`radius`と光円錐に入っている画素の直接光を強くする
  - 注意：到達距離と照射角は変わらない
- **radius**
  - 変化：光の打ち切り距離を伸ばし、同じ距離にある面の減衰も弱くする
  - 注意：光円錐の角度は変わらず、対象画素が増える場合がある
- **outerAngle**
  - 変化：コーンライトの外縁を広げ、光が届く方向範囲を増やす
  - 注意：`innerAngle`内の強度は変わらない
  - 制約：`innerAngle < outerAngle <= 90`を保つ
- **lighting.ambient**
  - 変化：ローカルライトが弱い場所を含め、シーン全体の環境拡散光を増やす
  - 注意：直接光の到達距離は変わらない
  - 影響：AO、Fresnel反射、`metallic`による拡散成分の減少を受ける

ローカルライトの距離減衰は、距離を$d$、半径を$r$として、$d < r$の範囲で概念上次のように計算します。

```text
距離減衰 = max（1 - d / r, 0）²
直接光の放射輝度 = light color × intensity × 距離減衰 × 角度減衰
```

このため`radius`を上げると、単に遠方へ光が届くだけでなく、同じ距離の面も明るくなります。
明るさだけを変えたい場合は`intensity`を使い、照明の切れ目や光源間の暗い区間を広げたい場合は`radius`を使います。

コーンライトでは、`innerAngle`内の角度減衰は1です。
`innerAngle`から`outerAngle`の間で0へ滑らかに減衰し、`outerAngle`の外側は0になります。
中心の明るい範囲を広げる場合は`innerAngle`、光が届く外縁を広げる場合は`outerAngle`を調整します。
角度を広げるほど多くの画素が直接光の評価対象になり得るため、見た目だけでなくGPU時間も確認します。

遅延ライティングの環境光は、Shapeの`ambient`ではなく、`DeferredLightingPass.encode()`または`ComputeEffectPipeline.encode()`の`lighting.ambient`へ渡します。
アプリケーション側で`DEFERRED_AMBIENT`のような定数を用意する場合も、その名前はアプリ固有であり、APIへ渡す値の意味は`lighting.ambient`です。
環境光は発光や直接光とは別の役割を持ち、完全な金属ではアルベド由来の拡散環境光を0として鏡面反射へ配分します。

調整は、次の順序で行うと原因を切り分けやすくなります。

1. 光が届いている面だけが暗い場合は、`intensity`を上げます。
2. 光源と光源の間で照明が途切れる場合は、`radius`を上げます。
3. コーンの横方向だけが暗い場合は、`outerAngle`を上げます。
4. 光が届かない場所を含めて全体の基礎照度が不足する場合は、`lighting.ambient`を上げます。
5. 最後に露出とトーンマッピングを調整し、照明値の問題を表示変換だけで隠していないか確認します。

光円錐は光の放射形状を表し、幾何学的な遮蔽はシャドウ計算が担当します。
光円錐内の壁に光を遮らせるには、別途シャドウ可視率が必要です。
`view`を`"albedo"`、`"normal"`、`"depth"`、`"shadow"`、`"ao"`、`"roughness"`などへ切り替えると、照明の後からでは見分けにくい入力を個別に調べられます。

## シャドウマップで直接光の遮蔽を表す

シャドウマップは、光源から見て別の物体に隠れている表面へ直接光を届かせず、物体が床や壁へ落とす影を表すために使います。
SSAOが画面に見えている近傍から環境光の遮蔽を近似するのに対し、シャドウマップはライトビューからシーンを描くため、カメラから直接見えない遮蔽物も影へ反映できます。
照明色と分離した可視率として解決すれば、遅延ライティングで直接光だけへ適用できます。

方向光とスポットライトのシャドウマップは、ライトビューから見た最短深度を保存します。
通常カメラはReverse-Zですが、`ShadowMapPass`と`SpotShadowMapPass`は意図的に`SHADOW_STANDARD_Z`を使います。

```text
カメラ深度: depth32float / クリア値0 / greater / near側1 / far側0
シャドウ深度: depth32float / クリア値1 / less / near側0 / far側1
```

シャドウresolveは、カメラ用Reverse-Z深度から影を受ける面のビュー空間位置を復元し、それをライトビューへ変換して通常Zのシャドウ深度と比較します。
2枚の深度テクスチャはそれぞれの規約に合わせて線形化し、シャドウマップにはStandard-Zの`less`を使います。

方向光の範囲を固定する場合は`createDirectionalLightMatrices()`を使います。
カメラの視錐台へ追従させる場合、統合パイプラインの`shadow.directional.fitMode: "frustum-fit"`を使うと、カメラの8頂点を光源空間へ移したAABB（Axis-Aligned Bounding Box：軸平行境界ボックス）から投影範囲を作り、テクセル単位で安定化できます。
`fitFar`はカメラの`far`以下でなければならず、範囲外の値は縮めて続行せず例外になります。

低水準APIでは、まず`ShadowMapPass`がライトビューからシャドウ深度を作り、次に`ComputeShadowPass`がG-bufferの影を受ける面と比較して可視率を作ります。
色を出力するのではなく可視性だけを出力するため、遅延ライティングは直接光にだけ影を適用できます。

```js
const shadowVisibility = shadowPass.encode(
  app.getGPU().commandEncoder,
  {
    normal: gbufferResources.normal,
    depth: gbufferResources.depth,
    ...shadowMap.getBindingResources()
  },
  {
    cameraFrame,
    lightViewProjection: lightMatrices.viewProjection,
    lightDirection: [0.35, -1.0, -0.25],
    bias: 0.0015,
    normalBias: 0.003,
    pcfRadius: 1,
    enabled: true
  }
);
```

`bias`はシャドウ深度比較の数値誤差を吸収し、`normalBias`は法線方向へ影を受ける面をずらして表面が自分自身を遮るシャドウアクネを減らします。
大きすぎると影が物体から浮くため、解像度とシーンスケールに合わせて決めます。
`pcfRadius`は0から2で、大きくするほど影の端が柔らかくなる一方、参照数が増えます。

## SSRで画面内の反射を低コストに加える

SSR（Screen Space Reflection、画面空間反射）は、床、金属、水面などへ、現在の画面に映っている物体や光の反射を加えるために使います。
別のカメラでシーンを描いた反射テクスチャを用意せず、G-bufferと照明済みのHDRシーン色を再利用するため、動く物体や照明を反映した反射を比較的小さな追加構成で作れます。

SSRはビュー空間位置と法線から反射レイを作り、カメラ用Reverse-Z深度との交差を画面上で探索します。
PBR統合モードでは、出力RGBは交差位置の線形HDR放射輝度、アルファは交差の信頼度です。マテリアルのフレネル反射と鏡面反射の重みは、合成側で共有BRDFから求めます。遅延照明がすでに含む画像ベース照明（Image-Based Lighting：IBL）の鏡面反射へ単純加算せず、交差した範囲だけSSRへ置き換えます。`mix`と`add`は、IBLを使わない従来構成または演出的な合成に残るモードです。

反射レイは、表面に入る視線方向をG-bufferの法線で反転して作ります。
レイ上の点をカメラ投影で画面座標へ戻し、その画素の深度から復元した表面と奥行きを比べます。
一致する範囲へ入ったら交差とみなし、照明済みのHDRシーン色を反射色として読みます。

```text
ビュー空間の位置と法線
  -> 反射レイ
  -> カメラ投影で画面上のUV座標へ戻す
  -> カメラ用Reverse-Z深度と交差判定
  -> 交差位置のHDRシーン色を取得
  -> 距離と画面端からhit confidenceを求める
  -> PBR鏡面weightでIBLをSSRへ置換
```

深度テクスチャは立体の厚みを持たないため、`thickness`で交差とみなす許容幅を与えます。
小さすぎるとステップ間に面を通り過ぎ、大きすぎると本来は離れている面を交差判定と誤認します。
そのため`distance`、`steps`、`thickness`は別々の強さではなく、シーンスケールに対する一組の探索条件として調整します。

SSRは画面に存在する情報を使うため、画面内に見える不透明表面を反射へ加えます。画面外や完全に隠れた面はIBLなどの環境反射で補います。
これは不具合ではなく画面空間手法の制約です。
欠けを隠すために常に強い色を補うのではなく、環境マップなど別の反射情報と役割を分けます。

反射レイで得た色は、マテリアルの`roughness`に応じてぼかしと強度を調整して適用します。
`ComputeSsrPass`は反射結果から1/2、1/4、1/8の画像ピラミッドを作り、G-bufferの`roughness`に応じて元の反射と隣接する段階を補間します。
滑らかな面では鋭い反射を保ち、粗い面ほど低い解像度の反射色を選びます。
反射の重みを保存するアルファは現在の画素の値を保つため、周囲の面の反射率がぼけて流入することを避けられます。

```js
import ComputeSsrPass from "./webg/ComputeSsrPass.js";

const ssrPass = new ComputeSsrPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  resolutionScale: 0.7,
  reflectivityThreshold: 0.05
});
await ssrPass.ready;

const reflection = ssrPass.encode(
  app.getGPU().commandEncoder,
  {
    scene: hdrScene,
    normal: gbufferResources.normal,
    depth: gbufferResources.depth,
    material: gbufferResources.material
  },
  {
    cameraFrame,
    intensity: 0.82,
    distance: 42.0,
    thickness: 0.42,
    steps: 48,
    resolutionScale: 0.7,
    reflectivityThreshold: 0.05,
    view: "reflection",
    enabled: true
  }
);
```

`distance`はレイの最大探索距離、`steps`は粗い探索の基準ステップ数、`thickness`は深度面と交差したとみなす厚みです。
距離やステップを増やせば必ず正しくなるわけではなく、探索距離に対してステップが粗すぎると薄い物体を通り過ぎます。
`reflectivityThreshold`は反射性の小さい画素でレイマーチングを始めないための早期終了値です。
`resolutionScale`は反射レイ、`roughness`用の画像ピラミッド、最終反射の描画先へ適用され、G-bufferは元の解像度のまま参照されます。

反射は`rgba16float`で保持します。標準のPBR構成では`ComputeEffectComposer`の`pbr-ssr`を使い、`base + (SSR鏡面 - 鏡面IBL) × confidence`を線形HDRで計算します。ray missと画面端ではconfidenceが0になり、同じHDR環境の鏡面IBLが残ります。合成後もトーンマッピングまではHDRを維持します。

## フォグで距離に応じた空気の厚みを表す

フォグは、カメラから遠い表面ほどシーン色を霧の色へ近づけ、空気の厚み、遠近感、天候を画面全体へ加えるために使います。
形状ごとのシェーダーで同じ計算を繰り返す代わりに、`ComputeFogPass`は照明と半透明合成を終えた線形HDRシーンを一度だけ処理します。
遅延レンダリング経路では、フォワード描画側のフォグを重ねず、画面全体のフォグをこのパスへ集約します。

フォグの入力は、`rgba16float`のシーン色と、G-bufferに保存されたカメラ用Reverse-Z深度です。
深度を作ったものと同じ`cameraFrame`からビュー空間位置を復元し、その位置の長さをカメラから表面までの距離として使います。
出力も`rgba16float`なので、フォグを適用した後にトゥーン、DoF、ブルームを続け、最後にトーンマッピングできます。

```js
import ComputeFogPass from "./webg/ComputeFogPass.js";

const fogPass = new ComputeFogPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await fogPass.ready;

const foggedColor = fogPass.encode(
  app.getGPU().commandEncoder,
  {
    scene: transparentComposite,
    depth: gbufferResources.depth
  },
  {
    cameraFrame,
    mode: "linear",
    color: [0.10, 0.15, 0.20],
    near: 20.0,
    far: 80.0,
    density: 0.03,
    enabled: true
  }
);
```

`mode`は`"linear"`または`"exp"`です。
`"linear"`では、`near`まで元のシーン色を保ち、`far`へ近づくほど霧色の割合を増やします。
現在の実装では`density`も線形フォグの適用量へ使い、`density * 50`を0から1へ制限した値で、算出した霧の割合を弱めます。
既定の`density: 0.03`ではこの係数が1になるため、`near`と`far`で定めた線形変化がそのまま適用されます。
`density`を0.02より小さくすると、同じ距離範囲でもフォグが弱くなります。

ここでの`near`と`far`はカメラの投影面ではなく、フォグを変化させるための距離です。
カメラの`projectionNear`と`projectionFar`は`cameraFrame`を介して深度復元に使われますが、フォグの開始距離と終了距離はシーンの尺度と演出に合わせて別に指定します。

`"exp"`では、可視率を$e^{-density \times distance}$で求めます。
`density`を大きくすると短い距離でも霧が濃くなります。
このモードの見た目は`near`と`far`では変わりませんが、パスの共通入力契約として`near >= 0`、`far > near`を満たす値を指定します。
`color`は3成分の線形フォグ色で、各成分は0以上です。

| 設定値 | 既定値 | 意味 |
| --- | ---: | --- |
| `mode` | `"linear"` | 距離から可視率を求める方式 |
| `color` | `[0.1, 0.15, 0.1]` | 線形HDR区間で混合するフォグ色 |
| `near` | `20.0` | 線形フォグが始まる距離 |
| `far` | `80.0` | 線形フォグがフォグ色へ到達する距離 |
| `density` | `0.03` | 指数フォグの密度、または線形フォグの適用量 |
| `enabled` | `false` | フォグを適用するかどうか |

フォグは半透明合成後に置きます。
これにより、ガラスや半透明の粒子を別のフォワードフォグで再描画せず、合成済みシーン全体へ一回の全画面処理として適用できます。
ただし、参照する深度は不透明なG-buffer深度だけです。
半透明面はこの深度を書き換えないため、半透明画素では背後の不透明面までの距離を使う近似になります。

背後に不透明面がなく深度が背景値0の画素では、背景として距離計算を行わず、透明合成済みの色をそのまま使います。
その画素の透明合成済みシーン色をそのまま出力します。
このため、フォグは不透明面までの距離へ適用し、背景は背景用のclear colorや環境色として扱います。
空や独自背景にもフォグを適用したい場合は、その背景の距離または別の合成規則をアプリケーション側で定義する必要があります。
複数の半透明層ごとに固有のフォグ距離を評価する処理も、このパスの対象外です。

標準フォワード描画で`WebgApp.setFog()`を使う構成とPBR統合描画を切り替える場合は、その設定を`ComputeFogPass`または31〜33章の`ComputeEffectPipeline`へ移します。
両方を有効にすると、フォワード描画された面と全画面処理でフォグが二重に適用されるため、同じシーンではどちらか一方がフォグを担当するようにします。

## 水面とコースティクスを追加する

### 例を選び、表示を比較する

コースティクスは、波によって屈折した光が集まってできる明暗です。
水面の反射・屈折と集光の設定を一つずつ比較する場合は、
`samples/water/index.html`の説明から`samples/water/water.html`へ進みます。
最初に両方OFFで通常PBRを確認し、集光だけ、水面だけ、両方ONの順に比較してください。

動く部隊へ適用する場合は、`samples/fantasy/fantasy.html`へ進みます。
このゲームは水面表示をOFFにし、集光、青緑の方向光、距離フォグ、
漂う粒子で、水に沈んだ砦を表現します。右側で集光をON/OFFできます。
マスの読みやすさを保つ水中の照明演出で、水中カメラの屈折描画ではありません。
接続する関数は`samples/fantasy/main.js`の`connectWater()`です。

### 共通の波と照明の仕組み

`WaterBody`が水域、波、吸収係数、受光するShape／Nodeを保持します。
`ComputeEffectPipeline`または`PbrRenderer`の`setWater()`へ接続すると、
水面と集光が同じ波の高さ・勾配・時刻を使います。
シェーダー文字列の置換や内部描画関数の差し替えは不要です。

集光はGPUで光線を水面から屈折させ、水平基準面へ届く光束を蓄積して
相対照度画像を作ります。登録した物体の位置と法線に対応させ、
直接光の拡散反射だけをこの照度へ置き換えます。
鏡面、環境光、局所光、emissiveは既存のPBR経路で評価します。
そのため、模様を発光テクスチャとして貼る方法とは、材質への効き方が異なります。
金属度の高い鎧では、粗い石の上面より模様が弱くなる場合があります。

立体への模様は水平基準面からの投影近似です。
物体のUVに依存せず、移動や姿勢の変化を毎frameの受光対象描画で追います。
各物体の形状へ光線を再追跡する計算ではありません。
上向き法線への投影なので、鉛直面へ真上の光が当たる模様は付きません。
水中判定には同じ波の高さを使い、水際では`waterlineFade`の幅で滑らかに混ぜます。

### 起動済みのシーンへ接続する

次は、`WebgSceneApp`の初期化後、`sceneApp.start()`より前に接続する例です。
`floorShape`と`objectNode`には、シーンで生成済みの対象を渡します。
`WaterBody`は`webg/app/index.js`からもimportできます。

```js
import WaterBody from "../../webg/WaterBody.js";

const renderer = sceneApp.renderer;
const pipeline = renderer.pipeline;

// この初版の集光は、真上からのdirectional lightに対応する。
pipeline.lightOptions.direction = [0, -1, 0];
pipeline.shadowOptions.directional.up = [0, 0, 1];

const water = new WaterBody({
  origin: [0, 0, 0], width: 8, depth: 8, surfaceHeight: 2,
  amplitude: 0.15, wavelength: 0.75, speed: 1.3,
  waveMix: [1, 0.4, 0.2], absorption: [0.12, 0.05, 0.025]
});
water.addReceiver(floorShape);
water.addReceiver(objectNode, { strength: 0.7 });

// setWater()はGPU資源の準備を含むので、完了までframeを作らない。
await renderer.setWater(water, {
  surfaceEnabled: true, causticsEnabled: true, quality: "low"
});

// 既存のonUpdate({ deltaSec })へ加える。粒子のstepや別の描画ループは追加しない。
function updateWater({ deltaSec }) {
  water.setTime(water.time + deltaSec);
}
```

直接`ComputeEffectPipeline`を生成する場合は、constructorのoptionsへ
`lightDirection: [0, -1, 0]`と
`shadow: { directional: { up: [0, 0, 1] } }`を渡せます。
高水準のrenderer manifestは`lightDirection`を受け付けないので、
上の例のように初期化後の`renderer.pipeline.lightOptions.direction`へ設定します。
水域もmanifestのキーとして宣言せず、`setWater()`で接続します。
水面表示だけなら斜めのdirectional lightも使えます。

`addReceiver(shape)`はそのShape、`addReceiver(node)`は既定で子も対象にします。
部隊の親Nodeを登録すれば、歩行で動く手足や装備へ登録が引き継がれます。
`children: false`では登録したNode自身だけを対象にします。
Shapeの登録が最優先で、Nodeでは最も近い親の登録を使います。
`strength`は0〜1です。選択マーカーは登録から外すか、
親が登録済みなら`strength: 0`でそのShapeを上書きします。
対象から外すときは`removeReceiver(target)`、全解除は`clearReceivers()`です。

### 波の高さ、細かさ、色を変える

波や吸収の変更は`water.setOptions()`で行い、`setWater()`の再接続は不要です。
`setTime()`の単位は秒です。同じ時刻なら波も集光も同じ形になります。

- `amplitude`：合成した波の変位の上界、m。峰から谷までの差ではありません。
- `wavelength`：波長倍率。小さくすると細かく、大きくすると広い波になります。
- `speed`：時間の倍率。0で停止、1.3なら同じ波を1.3倍の速さで進めます。
- `waveMix`：交差波・うねり・さざ波の相対強度。非負の値を合計1へ換算します。
- `variation`：連続な位相・振幅変調の量、0〜1。frameごとの乱数ではありません。
- `absorption`：RGBの吸収係数、1/m。大きい成分ほど、その色を強く吸収します。
- `roughness`：水面の鏡面と環境反射の粗さ。集光だけの用途には効きません。

例えば、`samples/water/main.js`の表示設定は次の値です。

```js
water.setOptions({
  amplitude: 0.15, wavelength: 0.75, speed: 1.3,
  absorption: [0.12, 0.05, 0.025]
});
```

赤を青より吸収するので、水面越しの物体に淡い青みが出ます。
緑系にする例は`absorption: [0.07, 0.015, 0.07]`です。
水面表示では、視線の水中距離に対してRGBを別々に減衰させます。
集光画像はスカラー照度で、RGB係数の平均による入射光の減衰を使います。
集光だけの用途で吸収係数を変えても、RGBの水色を直接塗る処理にはなりません。

水域の`origin`は水平照度基準面の中心で、幅・奥行きはそのXZ範囲です。
`surfaceHeight`はワールドの平均水面Y、平均水深は
`surfaceHeight - origin[1]`です。平均水深は`amplitude`より大きくします。
`extent`は照度計算の一辺で、幅・奥行き以上にし、境界へ流れる光の余裕を取ります。
不正な値は拒否され、`setOptions()`前の有効な設定を保持します。

### 水面と画面効果の描画順

水面は現在のPBR環境とdirectional lightを反射し、
画面内の深度を使う屈折とRGBの吸収をHDRで合成します。

水中のAlpha Blend面とCompute粒子を屈折用背景へ入れ、
手前の面と粒子を水面の後に描きます。粒子更新は一frameに一度です。
Fog、DoF、Bloom、Tone Map、Edgeは合成の後に適用し、
深度・法線を使う効果には水面を含む値を渡します。
不透明G-bufferは書き換えません。

### ON/OFFとGPU負荷を確認する

`surfaceEnabled`と`causticsEnabled`の既定値は両方falseです。
水面だけ、集光だけ、両方ONを選べます。`quality`は集光の品質で、
既定の`high`は1024×1024光線・512×512照度画像、
`low`は512×512光線・256×256照度画像です。水面表示の画面解像度とは別です。

実行中の切替では新しいframeを止め、`setWater()`を待って再開します。
ゲームのルールやNode、`WaterBody`の時刻・登録を作り直す必要はありません。

```js
sceneApp.stop();
try {
  await sceneApp.renderer.setWater(water, {
    surfaceEnabled: false, causticsEnabled: false
  });
} finally {
  sceneApp.start();
}
```

水面表示と集光の両方をOFFにするか、`await renderer.setWater(null)`を呼ぶと、
専用GPU資源と追加照明variantを解放し、通常PBRへ戻ります。
受光対象の登録は`WaterBody`に残るので再利用できます。
水面OFFでは水面合成・専用深度処理を、集光OFFでは照度生成・対象maskを実行しません。
照度は波の設定と時刻が同じなら再利用しますが、動く物体の対象maskは更新します。
受光対象が空なら集光の照度生成と対象描画も行いません。

`renderer.getWaterStats()`または`pipeline.getWaterStats()`で、
有効状態、集光・水面のdispatch数、対象・深度のpass数、`timing`を確認します。
両方OFFでは専用処理の数が0、`timing`はnullです。
GPU時刻計測は対応する環境だけで利用でき、対象maskや追加照明の全負荷を
含む総frame時間ではありません。手動でsubmitする構成では、
submit後に`afterGpuSubmit()`を呼びます。標準callbackでは自動処理します。
`samples/water/`の検証ボタンは、対象選択、画面効果、OFF時の画像・資源を確認します。
検証用readbackと、通常frameの描画は分けて扱います。

### 水中ゲームへ適用するときの範囲

水面表示の対象は、一つの有限な水平水域を上から見る用途です。
水中カメラ、水の側面、画面外の屈折、周囲の物体の鏡像、
水中のFrost・Transmission・Volumeとの物理的な屈折の重ね合わせは扱いません。

`samples/fantasy/`では`surfaceEnabled: false`として、
幅・奥行き18m、基準面Y=-2m、平均水面Y=6mの水域へ地形と部隊を登録します。
波高は0.15m、波長倍率0.9、速度1.3、`waveMix: [1, 0.2, 0.12]`です。
選択リングと移動範囲は対象から外します。
背景と方向光に青緑の色を使い、`pipeline.fogOptions`へ指数フォグを設定します。
このフォグは視点距離に応じた濁りの近似で、物体ごとのRGB視線吸収ではありません。

コードを読むときは、`connectWater()`の初期接続、`update()`の時刻更新、
チェックボックスの停止→接続→再開を対応させます。
集光を切り替えた後に段差移動、射撃、敵ターン、再開始を試し、
追加した照明がゲームの状態と描画の所有者を崩していないか確認してください。
全体の読む順序は`PBRシーンから小さなゲームへ.md`にあります。

## まとめ

遅延照明はG-bufferの表面情報を読み、光源を画素単位で評価します。
影とSSAOは可視率、SSRは画面内の反射、フォグは合成後の距離効果を担当します。
水面と集光は`WaterBody`を共有し、通常PBRへ独立に追加できます。
用途に応じて水面の屈折表示と水中の照明演出を選び、対象登録、更新、解放を確認します。
焦点、画風、画面周辺の調整、GPU上の粒子更新は、続く36章で確認します。
