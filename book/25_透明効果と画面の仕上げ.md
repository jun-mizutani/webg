# 透明効果と画面の仕上げ

## この章の読み方

### この章を読む前に必要な知識

07章のマテリアルと23章のポストプロセスを知っていると読みやすくなります。

### 初回に読む範囲

透明三角形、FrostedGlassPass、手動接続の基本を先に読んでください。VignettePassの基本は23章で確認できます。

### 必要になったときに読む範囲

PBR透明、Transmission、透明物の深度、ComputeEffectPipelineはPBR画面で参照してください。

### この章を終えた時点でできること

透明表面、PBR（Physically Based Rendering：物理ベースレンダリング）透明、すりガラスを入力形式と処理段階に合わせて追加できます。

## FrostedGlassPassの実装と活用

`FrostedGlassPass`は、フォワード描画へ曇りガラスを手動で追加する場合の低水準なポストプロセスです。画面周辺を暗くする`VignettePass`は23章で扱い、本章では透明表面と組み合わせる場合の考え方に集中します。
`ComputeEffectPipeline`を使うPBR統合レンダリングでは、materialの`alpha_mode`、`alpha`、`roughness`などを入力に、内部の`TransparencyPass`が透明面を処理します。Transmissionを指定したマテリアルでは、表面反射、屈折、全反射、厚みに応じたBeer–Lambert吸収を同じ透明描画内で評価します。`FrostedGlassPass`はForward描画で個別に使う経路です。

半透明の表現を考えるとき、単純にマテリアルのアルファ値を下げてアルファブレンドで描画すれば十分なケースもあるでしょう。
しかし、曇りガラスのように「背後のシーンがぼけて見える」表現では、半透明Shape自体の色を出すだけでは不十分です。
背後のシーンを一度テクスチャとして取り出し、それをぼかした結果を、ガラス面が重なる領域だけに合成する必要があります。

`FrostedGlassPass` は、この処理をポストプロセスとして実装したクラスです。
実際に行っているのは、「不透明シーン」「ぼかしたシーン」「ガラス領域を示すマスク」の3つを合成する処理です。
ガラスShapeは通常の描画ではなく、`GlassMaskShader` を用いてマスクターゲットへ描き出されます。
このマスクのアルファ値は「ぼかしを混ぜる強度」を、RGB値は最終的な色に加える「ティント（色付け）」を表します。

この構成の利点は、手前にある不透明オブジェクトとの関係を自然に扱える点です。
`FrostedGlassPass.beginMask()` は、不透明シーンの深度バッファを保持した状態でマスクを描画します。
そのため、ガラス板より手前にオブジェクトがある場合、その部分はマスクから除外され、正しく遮蔽されます。

### 実装の考え方とフロー

`FrostedGlassPass` の1フレームは、通常のポストプロセスより複雑な手順を踏みます。

1. `beginScene()`: ガラスShapeを除外して、不透明なシーンだけを描画する。
2. `beginMask()`: ガラスShapeだけを `GlassMaskShader` でマスクターゲットへ描画する。
3. `render()`: シーンをぼかし、元のシーン、ぼけたシーン、マスクを合成する。

同じシーングラフ（`Space`）を使いながら、描画するShapeをパスごとに分けるため、`Space.draw(eye, { filter })` を利用して、ガラスShapeの抽出と除外を制御します。

### 実装例

以下は `unittest/translucent` の構成をベースにした実装例です。

```js
import WebgApp from "./webg/WebgApp.js";
import Shape from "./webg/Shape.js";
import Primitive from "./webg/Primitive.js";
import FrostedGlassPass from "./webg/FrostedGlassPass.js";
import GlassMaskShader from "./webg/GlassMaskShader.js";

const GLASS_MATERIAL_ID = "frosted-glass";

const app = new WebgApp({
  document,
  messageFontTexture: "./webg/font512.png",
  autoDrawScene: false
});
await app.init();

const glassMaskShader = new GlassMaskShader(app.getGPU(), {
  targetFormat: app.getGPU().format,
  cullMode: "none"
});
await glassMaskShader.init();
glassMaskShader.setProjectionMatrix(app.projectionMatrix);

const frosted = new FrostedGlassPass(app.getGPU(), {
  sceneFormat: app.getGPU().format,
  canvasFormat: app.getGPU().format,
  blurRadius: 2.8,
  blurScale: 0.5,
  blurIterations: 2,
  blurStrength: 0.9,
  tintStrength: 0.28,
  maskPower: 0.9
});
await frosted.ready;

const isGlassShape = (shape) => {
  return shape?.materialId === GLASS_MATERIAL_ID ||
    shape?.shaderParam?.frosted_glass === true ||
    shape?.shaderParam?.frosted_glass === 1;
};

const glassShape = new Shape(app.getGPU());
glassShape.applyPrimitiveAsset(Primitive.cuboid(60.0, 38.0, 0.8));
glassShape.endShape();
glassShape.setShader(glassMaskShader);
glassShape.setMaterial(GLASS_MATERIAL_ID, {
  frosted_glass: true,
  color: [0.78, 0.76, 0.68, 0.74]
});

const glassNode = app.space.addNode(null, "glass");
glassNode.setPosition(0.0, 2.0, -24.0);
glassNode.addShape(glassShape);

app.start({
  onUpdate: ({ screen }) => {
    glassMaskShader.setProjectionMatrix(app.projectionMatrix);
    frosted.resizeToScreen(screen);
  },
  onBeforeDraw: () => {
    // 1. 不透明シーンの描画（ガラスを除外）
    frosted.beginScene(app.screen, app.clearColor);
    app.space.draw(app.eye, {
      filter: ({ shape }) => !isGlassShape(shape)
    });

    // 2. ガラスマスクの描画（ガラスのみを抽出）
    frosted.beginMask(app.screen);
    app.space.draw(app.eye, {
      filter: ({ shape }) => isGlassShape(shape)
    });
  },
  onAfterDraw3d: () => {
    // 3. 合成と出力
    frosted.render(app.screen, {
      clearColor: app.clearColor
    });
    app.screen.clearDepthBuffer();
  }
});
```

ここで `glassShape.setShader(glassMaskShader)` を呼んでいる点に注目してください。
ガラスShapeは通常の質感を描くのではなく、マスクターゲットへ「この領域にガラスが存在する」という情報を書き込みます。
`setMaterial()` で設定した `color` のRGBはティント色として、アルファはぼかしを混ぜる強度として利用されます。

### パラメータの調整

曇りガラスのパラメーターは、背後をどれだけぼかすか、glass自身の色をどれだけ残すか、マスク境界をどう見せるかを分けて調整するために使います。
最終画像だけでなくシーン、マスク、ぼかしを比較しながら一項目ずつ変えると、ぼかし不足とマスク不良を混同せずに済みます。

- `blurRadius`: ぼかしサンプルの間隔を制御します。値を大きくすると背後の形状がより曖昧になります。
- `blurIterations`: ぼかし処理の繰り返し回数です。増やすほど滑らかになりますが、描画負荷が増加します。
- `blurScale`: ぼかし用ターゲットの解像度倍率です。`0.5`（半解像度）に設定すると、処理が軽量化されるだけでなく、より柔らかい表現になる場合があります。
- `blurStrength`: マスク領域において、元のシーンとぼけたシーンをどれだけ混ぜるかを決定します。
- `tintStrength`: マスクのRGB色を最終的な出力にどれだけ反映させるかを制御します。
- `maskPower`: マスクのアルファ効き方を指数的に調整します。

### デバッグと注意点

曇りガラスの調整では、最終結果だけでなく中間ターゲット（`scene`, `mask`, `blur`）を切り替えて確認することが不可欠です。
これにより、フィルタリングが正しく機能しているか、深度関係が維持されているかを切り分けることができます。

なお、`FrostedGlassPass` は「全ての半透明ポリゴンを深度順に描画する」ための汎用的な仕組みではなく、あくまで「背後をぼかして見せる」ための手動合成パスです。
通常の半透明はmaterialの`alpha_mode`を`BLEND`にすると、`Space.draw()`が全Shapeから三角形を集めて奥から手前へ描きます。
`alpha_mode`を省略した場合は、`alpha`を1.0未満にすると`BLEND`として扱われます。
ComputeEffectPipelineでは、同じ分類結果を次節の`TransparencyPass`がHDR sceneへ合成します。

## PBR統合レンダリングでは透明描画も後段へ移る

本章の`FrostedGlassPass`は、不透明シーン、ぼかし画像、ガラス領域のマスクを利用者が手動で用意することで、Forward描画の後へ曇りガラスを追加します。この構成は、完成色とは別のマスクを作り、後段の合成条件として利用する例です。遅延レンダリングで基本色や法線を複数のG-bufferへ分けて書く場合も、保存する情報は異なりますが、後段が必要とする画像を先に用意する点は共通しています。

PBR統合レンダリングでは、透明面をmaterialの`alpha_mode`で分類し、`OPAQUE`と`MASK`を不透明G-bufferへ、`BLEND`を後段の透明Forward描画へ送ります。不透明G-bufferは背後にある不透明面の深度と表面情報を保持し、透明体越しの背景評価に使います。`alpha_mode`を省略した場合は、`alpha === 1.0`を`OPAQUE`、1.0未満を`BLEND`として扱います。

`ComputeEffectPipeline.encode()`はPBR遅延照明とSSRの後で、透明三角形が存在するときだけ内部の`TransparencyPass`を実行します。不透明表面はG-bufferを使う遅延照明、透明表面は同じPBR BRDFを使うForward描画と処理方法を分けながら、照明モデルを揃えます。

```text
不透明G-buffer
  -> PBR直接光とIBL
  -> SSRによる画面内反射
  -> 透明背景用のぼかし画像
  -> 透明PBR表面とTransmissionを奥から手前へ合成
  -> Fog / Toon / DoF / Bloom
  -> Tone Mapping / Edge / Vignette
```

表面の粗さによる背景ぼけでは、sharp、medium、strongの背景画像を`roughness`に応じて選びます。透明表面の直接光、IBL、フレネル反射には、`PbrForwardShader`が不透明照明と同じ`PbrBrdf.js`を使用します。Transmissionを有効にした場合は、entry面から物体内へ屈折し、exit面から空気側へ再屈折したレイで背景を探索します。厚みと吸収係数がある場合は、物体内の距離からBeer–Lambert吸収を求めます。

```js
glassShape.setMaterial("smooth-shader", {
  color: [0.95, 0.78, 0.18, 1.0],
  alpha_mode: "BLEND",
  alpha: 0.42,
  specular: 1.0,
  roughness: 0.18,
  metallic: 0.0,
  occlusion: 1.0,
  emissive_factor: [0.0, 0.0, 0.0]
});
```

利用側は透明用Render Passや`FrostedGlassPass`を個別に`ComputeEffectPipeline`へ挿入せず、透明面の設定を指定します。統合パイプラインが透明面を検出し、透明背景のぼかし、マスク、透明表面描画を決められた処理順へ接続します。この構成によって、本章で手動構成した複数のレンダーパスを一つの入口から利用できます。

透明三角形の順序は、まずインスタンスの投影boundsを比較し、重なり候補だけを実頂点から求めたtightな投影boundsで再判定します。短辺が8 pixel以下の小さな重なりは独立した描画として扱い、干渉しないインスタンスは既存のバッチを保ちます。前後関係が曖昧な組だけを三角形単位の大域ソートへ送ることで、順序の安定性とCPU処理量の両方を考慮しています。

画面空間のTransmissionは、画面内にある背景情報と不透明深度を使って近似します。画面外や不透明深度の背後、透明三角形同士が交差して循環する前後関係、複数の透明物体を順に通過する完全な多層屈折は、近似の対象外となるため、背景未到達時の選択や処理順を設定します。PBR透明表面とTransmissionの入力、詳細な選択肢は31〜33章と`samples/transmission`を参照してください。通常のAlpha Blendは`samples/opacity`で確認できます。

## ポストプロセスを支える共通部品

各エフェクトの内部で利用されている共通コンポーネントについて解説します。

- `RenderTarget`: オフスクリーン描画の先となるターゲットです。ポストプロセスの土台となる「描き出し先」を制御します。
- `FullscreenPass`: 1枚のテクスチャを現在のパスへ出力するための最小限のヘルパーです。デバッグビューの表示や、エフェクト適用前のシーンとの比較に多用されます。
- `SeparableBlurPass`: 横方向と縦方向のぼかし処理を交互に繰り返す（ピンポン処理）ことで、効率的にガウスぼかしなどを実現する共有ヘルパーです。`BloomPass`、`DofPass`、`FrostedGlassPass` の内部で利用されています。

これらはレンダーパスを使う部品ですが、入力画像、出力画像、処理順を分ける考え方はコンピュートパスでも共通です。20〜22章では、フラグメントシェーダーの代わりにコンピュートシェーダーを実行し、ストレージテクスチャへ結果を書き込む方法を説明します。コンピュートパスはワークグループ単位で画像を処理します。

## 導入パターンと使い分け

レンダーシェーダー版の手動ポストプロセスを学ぶ場合は、まず23章の`VignettePass`から始め、24章の`BloomPass`へ進みます。
どちらも「オフスクリーン $\rightarrow$ フルスクリーン $\rightarrow$ キャンバス」という基本フローを追いやすく、深度情報の参照という複雑な工程を含まないためです。

`DofPass` は投影行列の `near` / `far` やカメラ設定と密接に結びついているため、描画コールバックが受け取る同じ`renderFrameToken`をシーンと合成へ渡してください。
nearやfarを別のオプションとして複製せず、トークンが表すカメラフレームを距離復元の基準にします。
単独の`FrostedGlassPass`では、どのShapeをマスクへ描くかを利用側が選びます。
`ComputeEffectPipeline`では、materialの`alpha_mode`が`BLEND`の三角形を自動選択します。`alpha_mode`を省略した場合は、`alpha`が1.0未満の三角形が対象です。

新しくPBRアプリケーションを構成する場合は、30章でPBRのマテリアルと環境光を理解し、31〜33章の`ComputeEffectPipeline`を入口にして必要な効果を有効にします。独自の画像処理を一つだけ追加する場合や、Compute Shaderを使わない小さなForward描画を保つ場合は、本章の手動構成を選びます。

## トラブルシューティング

画面に変化が見られない場合: `autoDrawScene: false` に設定されているか確認してください。
設定されていない場合、シーンが直接キャンバスへ描画され、ポストプロセス処理がスキップされます。

リサイズ後に解像度がずれる場合: `onUpdate()` 内で `resizeToScreen(screen)` を呼び出しているか確認してください。
オフスクリーンターゲットは、キャンバスのサイズ変更に合わせて適切にリサイズする必要があります。

被写界深度（DoF）が正しく効かない場合: `beginScene()`、`Space.draw()`、`DofPass.render()`へ同じコールバックの`renderFrameToken`を渡しているか確認してください。
次にデバッグビューで`depth`と`focusMask`を表示し、同じカメラフレームの深度が読まれ、意図した領域が合焦しているかを確認してください。

HUDが表示されなくなった場合:最終パスの後に `app.screen.clearDepthBuffer()` を呼び出しているか確認してください。
これを忘れると、ポストプロセスで書き込まれた深度情報が残り、後から描画するHUDが深度テストで棄却されます。

FrostedGlassPassでガラスが見えない場合:不透明シーンパスとマスクパスのフィルタ（`filter`）が逆になっていないか確認してください。
また、`GlassMaskShader` の投影行列が通常シェーダーと同じ値に更新されていないと、マスクの位置がずれて表示されます。

## 関連サンプルとテスト

サンプルは完成した操作UI（User Interface：利用者との操作・表示の接点）と中間ターゲットの見え方を確認するため、テストはAPI仕様と数値条件を変更後にも保つために使います。
目的に応じて両方を見ることで、画面が動くことだけでなく、入力とパス順序が仕様どおりであることも確認できます。

- レンダーシェーダー版ブルーム (`samples/bloom`): パラメータ調整UI、デバッグドック、`extractHeat`の可視化など、Forward描画へ手動接続する実装を確認できます。
- レンダーシェーダー版DoF (`samples/dof`): フォーカスガイド、深度デバッグ、フォーカスマスク、段階マスク、3段階ぼかしの差異を確認できます。
- 曇りガラスの最小テスト (`unittest/translucent`): 不透明シーン、ぼかし、マスク、合成を切り替えながら、`FrostedGlassPass` と `GlassMaskShader` の関係を確認できます。
- 最小構成のテスト (`unittest/vignette`): 23章で扱う`RenderTarget`、`FullscreenPass`、`VignettePass`の関係性を最短ルートで追うことができます。
- Compute版Bloomは画像Pyramidの各段階を使って広がりを作り、Compute版DoFはcoverageとCoCを分けてぼかし段階を選択します。
- Vignetteを含む公開向けのPBR統合処理は、`examples/33_01.html`で確認できます。
- PBR透明表面と屈折 (`samples/transmission`): 透明PBR、屈折、全反射、吸収、背景未到達時の処理を確認できます。
- PBR統合例 (`examples/33_01.html`): G-bufferからIBL、透明表面、Fog、Bloom、Tone Mappingまでを一つの処理順で確認できます。

## まとめ

本章のレンダーシェーダー版ポストプロセスは、標準Forward描画の頂点シェーダー、ラスタライズ、フラグメントシェーダーが作った完成色を、キャンバスではなくオフスクリーンターゲットへ保存します。その色、深度、マスクを後段の全画面レンダーパスで読み、最終表示を作ります。

23章のVignetteと24章のブルームは、色テクスチャをレンダーパス間で渡す基本を示します。DoFは同じ`renderFrameToken`でシーンと深度参照パスを結び、曇りガラスは完成色とは別のマスクを後段へ渡します。このように、前段で必要な情報を保存し、後段で評価する考え方が、G-bufferを使う遅延レンダリングの理解につながります。

webg 2.0以降では、20〜22章のコンピュートシェーダーによって、同じ画像処理を全画面三角形に限定せず、ストレージテクスチャとワークグループで構成できます。PBR統合レンダリングでは、`ComputeEffectPipeline`がG-buffer、PBR照明、透明表面、DoF、Bloom、Tone Mapping、Vignetteを適切な色空間と処理順で管理します。本章の手動構成は、Compute Shaderを使わない場合の実装方法であると同時に、その統合処理が内部で何を管理しているかを理解する基礎です。

最終パスの後でHUDを描く場合は、`app.screen.clearDepthBuffer()`で深度状態を整えてから重ねます。
