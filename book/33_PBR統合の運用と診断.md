# PBR統合の運用と診断

本章では、32章で作った表示を基準に、画面のずれ、明るさ、サイズ変更、GPUリソースの片付けを確認します。まず観測する画像を決め、処理の段階ごとに調べることで、調整する設定を絞ります。

## この章の読み方

### この章を読む前に必要な知識

32章の接続方法と03章のカメラ・深度の基本を知っていると読みやすくなります。

### 初回に読む範囲

最初の「表示結果を段階ごとに確認する」を読み、32章の実行例と中間結果を比較してください。その後、症状別の確認方法を使います。

### 必要になったときに読む範囲

カメラ相対、シャドウ、リサイズ、破棄、中間結果、症状別切り分けは複雑化したときに参照してください。

### この章を終えた時点でできること

物理ベースレンダリング（PBR）統合の深度ずれ、黒画面、色の飽和、負荷増大を処理段階ごとに診断できます。

## 表示結果を段階ごとに確認する

32章で画面を表示できたら、モデルの位置、表面の色、照明、反射、後処理を順に確認します。まず完成画面を基準にし、変更する効果を一つへ絞ると、その効果が加えた違いを見分けやすくなります。

暗い画面では、G-bufferへ表面の情報が入っているか、照明後の画像に光量があるか、最終表示へ正しいテクスチャを渡しているかを順に確認します。影や反射の位置がずれる場合は、描画と効果に同じ`cameraFrame`を渡しているか確認します。画面サイズを変えた後の症状では、描画先と効果のサイズを一緒に更新しているかを調べます。

本章後半の中間結果表示と症状別の節は、この確認を具体的な画像と設定へ対応付けます。後半のカメラ相対レンダリングは、原点から遠い場所を移動するシーンで座標精度を保つための説明です。通常のシーンでは、表示・サイズ変更・破棄・診断の節へ先に進めます。

## `beginPresentPass()`で表示する

`beginPresentPass()`は、完成テクスチャを画面へ転送する深度不要の処理と、ジオメトリやHUD（Head-Up Display：画面上へ重ねる情報表示）を描く深度付きの処理を分けるために使います。
パイプラインとレンダーパスのアタッチメント構成を一致させることで、最終コピーが正しくても後続HUDのためにコマンドバッファ全体が無効になる、といった表示切り替え時の不具合を防げます。

トーンマッピング後の`finalColor`は、すでに画面へ表示できる完成テクスチャです。
これを`FullscreenPass`でswapchainへ転送する処理は、3Dジオメトリの深度テストを使わず、`Screen.beginPresentPass()`でカラーアタッチメントだけを持つレンダーパスを開始します。

通常の3Dパスはカメラ用Reverse-Zの`depth32float`アタッチメントを持ちます。
全画面用パイプラインはカラーアタッチメントだけで構成します。完成テクスチャはこの表示パスへ渡し、通常3Dパスの深度アタッチメントを要求する`Font`やHUDは、深度付きパスへ切り替えて描きます。

そこで最終表示とHUD描画の切り替えを次の対で構成します。

```js
app.screen.beginPresentPass({
  clearColor: app.clearColor,
  colorLoadOp: "clear"
});
copyPass.draw(finalColor);

// 最終表示パスを閉じ、色を保持したまま
// HUD用にカメラのReverse-Z深度を持つレンダーパスを再開する
app.screen.clearDepthBuffer();
```

`clearDepthBuffer()`はこの場面で、深度なしの最終表示パスから深度付きパスへ戻る切り替え用APIとして使います。
標準の単一パス描画では、`WebgApp`が深度付きパスとHUD用パスの切り替えを管理します。

## リソースの生成と破棄を集約する

リサイズ、生成、破棄をパイプラインへ集約すると、関連テクスチャの寸法を同じフレームで揃え、作成したリソースを一つのパイプラインから破棄できます。
利用側が個別ターゲットの一覧を持たないため、新しい効果を追加してもリサイズ漏れや二重破棄を増やさずに済みます。

キャンバス寸法が変わると、G-buffer、可視率、ライティング、反射、フォグ、ビネットを含む各後処理用描画先の画素対応も変わります。
個別の描画先を利用側でリサイズすると更新漏れが起きるため、統合パイプラインへ一度だけ通知します。

```js
onUpdate: ({ screen }) => {
  pipeline.resize(
    screen.getWidth(),
    screen.getHeight()
  );
}
```

同じ寸法ならリソースは維持されます。
シャドウマップのように画面寸法から独立したターゲットは、通常のキャンバスリサイズでも同じリソースを維持します。
フレーム途中にターゲットを個別リサイズすると、G-bufferと後段パスが異なるテクスチャ同一性を参照する可能性があるため、`onUpdate`でパイプライン全体を同期します。

不要になったリソースは、それを生成したパスまたはパイプラインの`destroy()`で破棄します。

```js
window.addEventListener("pagehide", () => {
  app.stop();
  copyPass.destroy?.();
  pipeline.destroy();
}, { once: true });
```

## 派生ターゲットの解像度から計算量を調整する

派生ターゲットの解像度調整は、ジオメトリの輪郭やマテリアル情報を保ったまま、画面効果が処理する画素数を大きく減らすために使います。
外観に直結するG-bufferと最終表示は元の解像度のまま保ち、環境遮蔽、反射、ぼかしなど、拡大やぼかしを前提とする成分から縮小すると、画質と負荷の釣り合いを取りやすくなります。

画面空間のエフェクトの計算量は、おおむね処理画素数、1画素あたりの参照数、パス数の積で決まります。

SSAOの`resolutionScale`はSSAOの計算結果へ適用され、法線と深度を使うバイラテラルフィルターで元の解像度の可視率へ戻されます。
SSRの`resolutionScale`は反射レイの出力、`roughness`用の画像ピラミッド、最終反射へ適用され、元のG-bufferは元の解像度で読みます。

画像ピラミッドぼかし、DoF、ブルーム、すりガラス表現、SSRの粗さ処理は`ComputeImagePyramid`を使いますが、必要な段階と入力画像は効果ごとに異なります。
`ComputePyramidBlurPass`は線形HDR画像を1/16まで縮小し、最小段階の低周波画像だけを元の解像度へ段階的に拡大します。
DoFはシーン、近景、遠景、錯乱円（Circle of Confusion：CoC）の補助情報の4系統を1/16まで作ります。
ブルームは高輝度抽出結果を1/32まで縮小し、元の解像度へ段階的に再構成します。
すりガラス表現とSSRの粗さ処理は1/8までを使います。
これらの段階数は、各パスの入力と出力を揃えるために固定されています。

- **SSAO**
  - 主な負荷：`resolutionScale`、`samples`、`radius`
  - 最初に見直す値：`resolutionScale`
  - 下げすぎた症状：接触部の欠け、物体境界のにじみ
- **SSR**
  - 主な負荷：`resolutionScale`、`steps`、`distance`
  - 最初に見直す値：`resolutionScale`
  - 下げすぎた症状：反射輪郭の粗さ、薄い物体の見落とし
- **DoF**
  - 主な負荷：4系統の1/2〜1/16画像ピラミッド、CoC抽出、最終合成
  - 最初に見直す値：不要な場面での`dofEnabled`
  - 画質調整：`focusRange`、`cocScale`、`blurRadius`
  - 注意：設定値を変えても固定段階数と基本ディスパッチ回数は変わらない
- **画像ピラミッドぼかし**
  - 主な負荷：1/2〜1/16画像ピラミッド、元の解像度までの段階的な拡大
  - 画質調整：`filterRadius`
  - 注意：`filterRadius`を変えても固定段階数と基本ディスパッチ回数は変わらない
- **ブルーム**
  - 主な負荷：1/2〜1/32画像ピラミッド、段階的な拡大、HDR合成
  - 最初に見直す値：不要な場面での`bloomEnabled`
  - 画質調整：各段階の重み、`filterRadius`、`strength`
  - 注意：設定値を変えても固定段階数と基本ディスパッチ回数は変わらない
- **半透明のすりガラス表現**
  - 主な負荷：1/2〜1/8画像ピラミッド、粗さのマスク、透明表面の描画
  - 最初に見直す条件：半透明三角形が本当に必要か
  - 注意：半透明三角形が0枚のフレームでは処理全体を省略する
- **フォグ**
  - 主な負荷：元の解像度で1回のディスパッチ
  - 最初に見直す値：効果が不要な場面での`fogEnabled`
  - 注意：`density`や距離範囲を変えても処理画素数は変わらない
- **ビネット**
  - 主な負荷：元の解像度で1回のディスパッチ
  - 最初に見直す値：効果が不要な画面での`vignetteEnabled`
  - 注意：`strength: 0`より、無効化した方がパス自体を省略できる
- **シャドウ**
  - 主な負荷：シャドウマップサイズ、`pcfRadius`
  - 最初に見直す値：投影範囲とmapサイズの釣り合い
  - 下げすぎた症状：影の階段、接地部のずれ

解像度倍率は縦と横の両方へ効くため、1.0から0.7へ下げると処理画素数は約49%になります。
これに比べて、しきい値や合成強度は見た目を変えますが、計算量への影響は小さい値です。
フォグとビネットには低解像度の派生描画先がなく、最終画素との対応を保った元の解像度での処理です。
性能調整と外観調整を混同せず、GPU時間の計測値と診断表示を使って別々に決めます。

設定を比較するときは、次の条件を固定して一項目ずつ測定します。

1. GPU、ブラウザ、Canvas解像度、シーン、カメラ位置、アニメーション開始状態をそろえる
2. 対象の効果を無効にした基準構成を十分にウォームアップし、同じ時間または同じフレーム数のGPU時間とフレーム時間を記録する
3. 対象の効果を有効にするか、比較する設定を一項目だけ変更し、同じ区間を測定する
4. 基準値との差だけでなく、ちらつき、輪郭の欠け、反射の見落としなどの外観差も同時に記録する
5. 複数回測定し、初回のパイプライン生成や一時的な負荷が定常値へ混ざっていないことを確認する

`filterRadius`、`density`、合成強度のように外観だけを変え、固定された段階数やディスパッチ回数を変えない設定もあります。値を小さくしただけで高速になったと判断せず、実測値で確認します。

## 中間結果を診断表示して最初の異常を探す

診断表示は、完成画像を作る途中のどの入力から異常が始まったかを特定するために使います。
効果を一つずつ無効にして推測するより、アルベド、法線、深度、可視率、マテリアル成分を直接確認できるため、入力の欠落と後段の合成ミスを短い手順で区別できます。
`lightingView`を使うと、遅延ライティングが読んでいる各成分を最終表示まで通して確認できます。

```js
const finalColor = pipeline.encode(gpu.commandEncoder, {
  cameraFrame,
  shadowEnabled: true,
  ssaoEnabled: true,
  ssrEnabled: false,
  lightingView: "roughness"
});
```

`lightingView` は、照明結果とG-bufferの成分を切り替えて表示します。
指定できる値は、`"lighting"`、`"albedo"`、`"normal"`、`"depth"`、`"shadow"`、`"spotShadow"`、`"ao"`、`"specular"`、`"roughness"`、`"metallic"`、`"emissive"` です。

`"lighting"`以外は診断用のモードです。成分を確認するときに使い、最終外観には`"lighting"`を使います。
診断中はSSR、フォグ、DoF、ブルーム、ビネットなどを無効にします。
調べる成分の後から色が改変されない構成にします。

SSRには`ssrView: "reflection"`に加え、`"normal"`と`"depth"`があります。
反射が欠ける場所で、元の法線と深度が連続しているか、マテリアルの反射性が`reflectivityThreshold`を超えているか、探索レイが画面外へ出ていないかを順に調べます。
DoFは34〜36章の`debugView: "depth"`と`"focus"`を使い、距離復元とぼかしの問題を分けます。

フォグとビネットは、他の効果を固定した有効・無効の比較で診断します。フォグは、他のHDR効果を無効にした状態で比較し、G-bufferの`lightingView: "depth"`で背景値0と不透明面の距離分布を先に確認します。
ビネットはトーンマッピングと輪郭抽出の設定を固定して有効・無効を比較し、中心位置、内側の変化開始位置、外周の色を順に確認します。
両方を同時に調整せず、HDR区間の問題と表示色区間の問題を分けます。

## 症状をパイプラインの段階へ対応付ける

症状を入力、ジオメトリ、位置復元、HDR、最終表示の段階へ対応付けると、関係のないパラメーターを変更せずに原因へ到達できます。
統合後に画面が意図と異なる場合は、最終画像の印象だけで調整せず、パイプラインの各処理段階を順に確認します。

### 起動時に例外になる

起動時の例外は、不完全な入力がGPUコマンドへ進む前に止められたことを示します。
メッセージに含まれるShape、プロパティ、投影範囲から、不足している設定を直接修正します。
`material.roughness must be finite`のような例外は、ShapeのG-bufferマテリアルが不完全です。
対象Shapeの`setMaterial()`へ`roughness`、`metallic`、`emissive`を追加します。
そのマテリアルが表す表面を決め、意味に合う値を設定します。

`directional shadow projection far must be > ...`は、ライトビューの正射影範囲へ影を受ける面またはcasterを含める必要があることを示します。
シーンスケール、光源ターゲット、distance、深度padding、fitFarの関係を見直します。
farだけを極端に増やすとシャドウマップの深度精度が落ちます。

### ジオメトリが見えない

ジオメトリが見えない症状では、マテリアルや照明より先に、ジオメトリを通す深度規則を確認すると原因を絞れます。
独自パイプラインの深度形式、比較、クリアを一体で確認します。
通常カメラは`depth32float`、`greater`、クリア0です。
`depth24plus`や`less`を使うパイプラインが一つでも混ざると、Screenのアタッチメントと一致しないか、ジオメトリが背景に負けます。

### AOや反射がカメラ移動でずれる

カメラ移動に連動するずれは、G-buffer生成と位置復元が異なる視点を使った可能性を示します。
`renderScene()`と`encode()`へ同じコールバックの`cameraFrame`を渡しているか確認します。
near、far、投影配列、cameraWorldは共有された`cameraFrame`から取得し、同じフレームの値をそのまま各パスへ渡します。
G-bufferの法線がビュー空間であることも確認します。

### フォグの背景と透明面の距離を確認する

背景深度0でフォグがかからない動作は、距離情報の欠落を無限遠として扱わないための仕様です。
空やグラデーションまでフォグ色へ近づけたい場合は、背景に距離を持たせる別の表現または専用の背景合成を追加します。
`far`を大きくしても、背景深度0は背景値として扱います。

半透明面でフォグの境界が面自身の距離と一致しない場合は、背後の不透明深度を使う近似が見えている可能性があります。
透明面自身の深度はG-bufferへ書き込まず、背後の不透明深度をフォグの距離に使います。
多層透明や透明面ごとの距離フォグが必要なら、透明描画の段階でフォグを評価する別設計を追加します。標準の`ComputeFogPass`は不透明深度を使う全画面近似を担当します。
ただし、その場合も全画面フォグとの二重適用を避けます。

画面全体が予想以上に濃い場合は、フォワード描画側の`WebgApp.setFog()`とパイプラインのフォグが同時に有効でないか確認します。
その後、`mode`、`near`、`far`、`density`、フォグ色の順に確認します。
指数フォグでは`near`と`far`を変えても見た目は変わらず、`density`が主な距離減衰値です。

### 最終画面だけ黒い

中間テクスチャが正しく最終画面だけ黒い場合は、最終表示処理を先に調べます。
`beginPresentPass()`を使っているか、その後に`clearDepthBuffer()`を呼んでいるかを確認します。
WebGPUの`uncaptured error`（捕捉されなかった検証エラー）に、アタッチメント形式や深度状態の不一致が出ていないかも調べます。
コンピュートの出力が正しくても、最終コピーまたは後続HUDでコマンドバッファー全体が無効になることがあります。

### 色が白く飽和する

白い飽和は、照明が強すぎる場合だけでなく、HDRを早く表示色へ変換した場合や、sRGB表示変換を重ねた場合にも起こります。
ライティング、反射、フォグ、DoF、ブルームが`rgba16float`のHDR区間にあり、トーンマッピングとsRGB表示変換が`ComputeEffectToneMapPass`の一度だけか確認します。
途中の`rgba8unorm`へHDRシーンを保存したり、各効果が個別に累乗変換したりすると、後段へ元の光量を渡せなくなります。HDR区間は`rgba16float`と一度の表示変換で接続します。

### ビネットが楕円に見える、またはHUDまで暗くなる

`ComputeVignettePass`は画面のアスペクト比を内部で補正します。
パイプライン全体をキャンバス寸法へ`resize()`すると、ビネットの出力先と現在の表示寸法が一致し、意図した中心や半径で表示できます。
個別パスだけでなく、`pipeline.resize(width, height)`を呼んで全画面の描画先を同時に更新します。

HUDまで暗くなる場合は、ビネット後の最終テクスチャへHUDを合成してから最終表示していないか、最終表示後に独自のビネットを重ねていないかを確認します。
標準順序は「トーンマッピング、輪郭抽出、ビネット、最終表示、HUD」です。
統合パイプラインの戻り値を表示し、その後に`clearDepthBuffer()`でHUD用パスへ戻すと、HUDをビネットから分離して表示できます。

## 管理する範囲に合わせてAPIを選ぶ

高水準APIと低水準APIは、リソースと処理順序を管理する範囲で使い分けます。
一般的な順序で複数の効果を使う場合は、作成、保持、リサイズ、接続、破棄を`ComputeEffectPipeline`へ任せます。
利用側はシーンと設定を渡すだけで、カメラフレーム、G-bufferのレイアウト、HDR形式、最終表示までの処理順序を揃えられます。

個別の`GeometryBufferPass`、`SsaoPass`、`ComputeSsrPass`などを直接使う低水準APIでは、それぞれの入力と出力を利用側が作成し、実行順序、リサイズ、破棄も利用側で管理します。
この方法は、新しいアルゴリズムを研究する、特定の中間結果を可視化する、標準順序に含まれないパスを開発するときに適します。
その場合も、同じカメラフレーム、深度規則、G-bufferのレイアウト、色空間の規則を継続して使います。
低水準APIでは、必要なリソースと処理順序を利用側で管理します。

### 統合パイプラインが管理するもの

管理範囲を把握し、ターゲットの生成と破棄をパイプラインへまとめます。
`ComputeEffectPipeline`は、34〜36章で説明する個別パスを生成して接続します。
そのため、低水準パスの深度規約や出力形式の修正は、統合経路にも同じ実装として反映されます。

```text
ComputeEffectPipeline
  +-- GeometryBufferPass
  +-- ShadowMapPass / SpotShadowMapPass
  +-- ComputeShadowPass / ComputeSpotShadowPass
  +-- SsaoPass
  +-- DeferredLightingPass
  +-- ComputeSsrPass + ComputeEffectComposer
  +-- TransparencyPass
  +-- ComputeFogPass
  +-- ComputeToonPass
  +-- ComputeDofPass
  +-- ComputeBloomPass
  +-- ComputeEffectToneMapPass
  +-- ComputeEdgePass
  +-- ComputeVignettePass
```

パイプラインはこれらのパスを生成して接続し、各パスが作るG-buffer、可視率、HDR色、反射、フォグ、ぼかし、表示色、ビネットの描画先をまとめて管理します。
利用側が取得する主な結果は`encode()`の戻り値である最終色です。
中間の描画先の生成や破棄はパイプラインに任せ、外側で同じ目的の描画先を二重に作らないようにします。

### 2段階に分かれる理由

`renderScene()`と`encode()`を分けると、WebgAppが持つレンダーパスの前半と、テクスチャを読むコンピュート処理の後半へ、統合パイプラインを自然に配置できます。
レンダーパスを閉じる必要がある処理をAPIの役割分担として明確にできる一方、同じカメラフレームを検証することで、二つを別フレームの処理として誤用するのを防げます。

`renderScene()`はレンダーパスを使う幾何描画の段階です。
シャドウマップとG-bufferを作り、そのフレームで使ったカメラフレーム、シャドウの種類、有効状態を記録します。
`encode()`はそれらのテクスチャを読むコンピュート段階で、可視率から最終表示色までをコマンドエンコーダーへ記録します。

両者を分けることで、`WebgApp`の`onBeforeDraw`と`onAfterDraw3d`というレンダーパスの切り替え時点に合わせられます。
これらは、同じ1フレームの前半と後半を構成します。
そのため、同じ`cameraFrame`オブジェクト、同じ`shadowEnabled`、同じシャドウ種別を渡す必要があります。
不一致の場合は、適当な中間テクスチャで続行せず例外になります。

### 低水準へ降りる判断

低水準APIは、標準パイプラインでは表せない入力、順序、G-bufferの配置が必要なときに選びます。
標準順序へ一つの効果を追加するだけなら、新しい個別パスをパイプラインのHDR区間または表示区間へ組み込む方が、既存の入出力仕様とリソース管理を再利用できます。
フォグとビネットはこの方針で標準順序へ統合されており、単独検証には個別パス、通常のアプリケーションには統合パイプラインを使えます。
一方、G-bufferの配置自体を増やす、半透明面ごとのフォグ距離を保存する、照明モデルを全面的に変える、複数カメラの結果を同時に合成する場合は、個別パスから構築する理由があります。

その場合も、法線はビュー空間、カメラ深度はReverse-Z、シャドウ深度はStandard-Z、照明、フォグ、その他のHDR効果は`rgba16float`、トーンマッピング、輪郭抽出、ビネットは`rgba8unorm`の表示区間、トーンマッピングは表示前の1回という前提条件から始めます。
低水準APIでは、各入力テクスチャの生成、`encode()`順序、`resize()`、`destroy()`を利用側で記述します。

## カメラ相対レンダリングで巨大座標の精度を保つ

カメラ相対レンダリングは、原点から遠いワールド座標でも、カメラ付近にある物体同士の小さな位置差をGPUへ残すために使います。
大規模な地形や長距離移動を扱うシーンを原点付近へ頻繁に移し直さずに済み、通常描画とG-buffer系効果の座標を同じ基準で保てます。

JavaScriptのシーングラフや物理シミュレーションはワールド座標を`Number`で保持できますが、GPUユニフォームへ渡した時点でfloat32になります。
巨大なワールド座標からカメラ位置をシェーダーの行列演算で引くと、近くの物体同士の差が丸められます。

カメラフレームは、CPU側で`objectWorld - cameraWorld`を計算してからfloat32のモデルビューへします。
統合パイプラインのG-bufferもこの経路を使うため、通常シーンのワールド座標を保ったまま描画できます。
シャドウマップはライトビューの座標系で別に作られますが、方向光の視錐台追従ではカメラフレームが持つ視錐台をもとに必要範囲を決めます。

`WebgApp`が作成したカメラフレームを共有することで、G-buffer、位置復元、シャドウ影を受ける面、SSRレイが同じ座標基準になります。利用側はその`cameraFrame`を`encode()`へ渡します。

## Directionalシャドウの範囲を選ぶ

Directionalシャドウの範囲は、限られたシャドウマップの画素を必要な場所へ配分し、影の精度とカメラ移動への追従を両立するために選びます。
方向光のシャドウには、固定範囲とカメラ視錐台追従の2つがあります。

固定範囲は、`target`、`distance`、`halfWidth`、`halfHeight`、`near`、`far`を明示します。
カメラがその範囲から外れないシーンでは、影の密度が一定で理解しやすい方式です。

視錐台追従は次のように指定します。

```js
const pipeline = new ComputeEffectPipeline(gpu, {
  width,
  height,
  shadow: {
    type: "directional",
    directional: {
      fitMode: "frustum-fit",
      fitFar: 80,
      xyPadding: 0.8,
      depthPadding: 4.0,
      minHalfExtent: 1.0,
      minNear: 0.2,
      texelSnap: true
    }
  }
});
```

`fitFar`はカメラの有限far以下に設定します。
大きすぎる値をカメラ farへ黙って縮めると設定ミスを隠すため、整合しない値は例外です。
`texelSnap`は光源-空間の投影中心をシャドウマップテクセルへ揃え、カメラ移動時の影の揺れを抑えます。

### Spotシャドウで局所的な光と影をまとめて定義する

Spotシャドウは、ステージ照明、懐中電灯、屋内のダウンライトのように、限られた方向と範囲へ光を当て、その円錐内で遮られる影を作るために使います。
シーン全体をシャドウマップへ収めず、光が届く範囲へ解像度を集中できることが利点です。
スポットライトは光源の位置、向き、視野角、有効距離を持つ透視投影です。

```js
const pipeline = new ComputeEffectPipeline(gpu, {
  width,
  height,
  shadow: {
    type: "spot",
    bias: 0.0015,
    normalBias: 0.003,
    pcfRadius: 1,
    spot: {
      position: [0.0, 7.5, 4.0],
      direction: [0.0, -0.72, -1.0],
      fov: 70,
      innerAngle: 40,
      outerAngle: 50,
      near: 0.05,
      far: 42,
      aspect: 1.0
    }
  },
  lighting: {
    ambient: 0.06,
    spotColor: [1.0, 0.86, 0.68],
    spotIntensity: 2.2
  }
});
```

`fov`はシャドウマップが覆う投影円錐、`innerAngle`と`outerAngle`は照明強度が一定の内側と、0へ減衰し終える外側の角度です。
`innerAngle < outerAngle < fov`となるように設計すると、照明の端とシャドウマップの端に余裕が生まれます。
`near`は0より大きく、`far`は`near`より大きくします。
必要以上に`far`を大きくすると通常Zのシャドウ深度精度が広い範囲へ分散します。

シャドウtypeは`renderScene()`と`encode()`の間で一致させます。
フレーム前半でDirectionalのシャドウマップを作った後、後半でSpotの可視率として解釈することはできないからです。
実行時に種類を切り替えるときは、1フレームのオプションを同じ状態から作り、両方の呼び出しへ渡します。

## 水面と集光の負荷を分けて確認する

35章の水面・コースティクスを追加した場合は、
通常PBR→集光だけ→水面だけ→両方ONの順に比較します。
設定と検証の例は`samples/water/water.html`、
動くゲームへの接続は`samples/fantasy/main.js`の`connectWater()`です。

`setWater()`は非同期です。切替中に新しいframeを記録せず、
準備完了を待って再開します。水面と集光の両方OFFでは、
専用buffer・texture・QuerySetと追加照明経路を解放します。
通常PBR自体の資源・処理は引き続き必要です。

`getWaterStats()`の`causticDispatches`は照度生成、`receiverPasses`は対象描画、
`surfaceDispatches`・`geometryDispatches`・`depthPasses`は水面側の処理です。
波の時刻と設定を固定すると照度を再利用できますが、
受光するNodeの移動を反映する対象描画は続きます。
両方OFFでは専用処理数0、`timing`はnullになります。
GPU計測の値は対象描画・追加照明などを含む総frame時間ではありません。

OFF時の見た目は通常PBRと同じ条件で比較し、
専用資源はサンプルの検証ボタンで確認します。
計測・画像readback用の処理と通常描画を分け、検証中の時間を描画性能と混同しません。
ゲームでは切替後に移動・攻撃・再開始も試し、描画と状態管理の両方を確認します。

## まとめ

PBR統合を運用するときは、カメラフレーム、深度、色形式、リソースの寿命、効果の有効状態を同じ処理フローで追跡します。中間画像を診断表示し、基準シーンから効果を一つずつ有効にすることで、黒画面、深度ずれ、色の飽和、負荷増大の原因を段階ごとに切り分けられます。
描画内部の共通規則やReverse-Zをさらに調べる場合は、41章を参照します。
