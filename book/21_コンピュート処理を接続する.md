# コンピュート処理を接続する

## この章の読み方

### この章を読む前に必要な知識

20章の役割と05章のWebgAppフレーム処理を知っていると読みやすくなります。

### 初回に読む範囲

リソース、座標、深度、色形式の前提、Render-first、Compute-first、ComputePassを先に読んでください。

### 必要になったときに読む範囲

画像処理の最小例、ストレージテクスチャ、ストレージバッファ、描画との受け渡しは実装時に参照してください。

### この章を終えた時点でできること

コンピュート処理の入出力を定義し、WebGPUのコマンド処理へ組み込めます。

## 接続前に確認する4つの前提条件

コンピュートシェーダーを安全に描画へ接続するには、GPU（Graphics Processing Unit：画像処理装置）で計算する目的に加え、リソースを生成・保持・破棄する担当、座標空間、深度規則、色空間の4つを先に定めます。
たとえばストレージバッファ上のパーティクル位置がワールドかカメラ相対か、ストレージテクスチャの色が線形HDR（High Dynamic Range：広い輝度範囲）か表示用8ビットかで、同じWGSL型でも接続可否は異なります。

カメラの深度を読まない色処理、Vignette、独立したバッファシミュレーションは、色とサイズを入力として処理できます。`CameraFrame`や`renderFrameToken`は、カメラ深度と位置復元を共有する処理へ渡します。
逆に、G-bufferの深度から位置を復元するSSAO（Screen Space Ambient Occlusion：画面空間で求める環境遮蔽）、SSR（Screen Space Reflections：画面空間反射）、Fog、DoF（Depth of Field：被写界深度）、接触シャドウ、形状の輪郭抽出は、同じカメラフレームの投影を使う必要があります。
コンピュートシェーダーの有無ではなく、深度と投影の共有で判断します。

高ダイナミックレンジ中間ターゲットには`rgba16float`、可視率やマスクには0〜1を表す`rgba8unorm`を使うというように、形式は処理の意味と結び付きます。
中間パスでガンマ、露出、0〜1への切り詰めを重複させず、表示変換は最終トーンマッピングへ1回だけ置きます。

## 描画とコンピュートのパイプライン比較

描画パイプラインとコンピュートパイプラインの違いは、処理対象が頂点やフラグメントとして自然に生成されるか、利用側が任意の要素数をディスパッチしたいかを判断するために理解します。
目的に合う入口を選ぶと、画像や配列の計算を無理に三角形描画へ置き換えず、必要な出力リソースへ直接書き込めます。
両者はいずれもGPU上で動作しますが、起動される単位が根本的に異なります。

頂点シェーダーは頂点バッファを入力とし、頂点ごとに起動してクリップ空間の頂点位置を出力します。
一方、フラグメントシェーダーはラスタライズ結果を入力とし、ピクセル候補ごとに起動してカラーアタッチメントの色を出力します。
これらは「レンダーパイプライン（Render Pipeline）」の中で動作し、三角形の描画や深度テストといった標準的な描画フローに組み込まれています。

対してコンピュートシェーダーは、任意のバッファやテクスチャを入力とします。
`dispatchWorkgroups()`で指定した単位で起動し、ストレージバッファやストレージテクスチャへ出力します。
これはコンピュートパイプラインとして独立して実行されます。
全画面処理では、三角形の代わりにFullscreen passが画面全体を覆う頂点構成を使います。
JavaScript側から、処理するデータの範囲をディスパッチとして明示します。
例えば、画面効果なら画面の画素数、粒子シミュレーションなら粒子数に応じた要素を処理対象にします。

## コンピュートシェーダーの実行モデル

コンピュートシェーダーを制御するために不可欠な概念として、「インボケーション（Invocation）」「ワークグループ（Workgroup）」「ディスパッチ（Dispatch）」の3つがあります。

- **インボケーション**: シェーダー関数の1回の実行単位です。画面処理では1ピクセル、粒子処理では1粒子に対応させることが一般的です。
- **ワークグループ**: 複数のインボケーションをまとめた実行グループであり、GPU内部で効率的に管理される単位となります。
- **ディスパッチ**: 必要な数のワークグループをGPUへ発行し、計算を開始させる操作です。

画面全体を処理する基本的な実装例を以下に示します。

```wgsl
@compute @workgroup_size(8, 8, 1)
fn main(@builtin(global_invocation_id) id : vec3<u32>) {
  let coord = vec2<i32>(id.xy);
  // coord がこのインボケーションの担当ピクセル座標となる
}
```

`@workgroup_size(8, 8, 1)` は、1つのワークグループに $8 \times 8 \times 1 = 64$ 個のインボケーションを含める指定です。
画面サイズが $1280 \times 720$ の場合、JavaScript側では次のようにワークグループ数を計算し、切り上げてディスパッチします。

```js
pass.dispatchWorkgroups(
  Math.ceil(width / 8),
  Math.ceil(height / 8),
  1
);
```

ここで注意が必要なのは、画面の幅や高さが任意の値になるため、末尾にワークグループの端数が生じる点です。
切り上げてディスパッチすると、画面の外側を担当するインボケーションが発生します。
そのため、WGSLの先頭で必ず範囲外アクセスを防止するガード処理を記述してください。

```wgsl
let size = textureDimensions(outputTexture);
if (id.x >= size.x || id.y >= size.y) {
  return;
}
```

この範囲確認を怠ると、ストレージテクスチャやストレージバッファの範囲外へアクセスし、WebGPUのバリデーションエラーや不定な計算結果を招く原因となります。

## ストレージテクスチャとストレージバッファ

コンピュートシェーダーは、出力先としてストレージテクスチャまたはストレージバッファを使用します。

ストレージテクスチャは、コンピュートシェーダーから画像データとして直接書き込めるテクスチャです。
書き込みには `textureStore()` を使用します。

```wgsl
@group(0) @binding(1)
var outputTexture : texture_storage_2d<rgba8unorm, write>;

// 書き込み処理
textureStore(outputTexture, coord, vec4f(color, 1.0));
```

一方、ストレージバッファは、構造体や配列などの汎用データを読み書きするためのバッファです。
粒子や物理オブジェクトの状態のように、画像形式ではなく「要素の配列」としてデータを更新したい場合に適しています。

```wgsl
struct Particle {
  positionLife : vec4f,
  velocitySize : vec4f,
};

@group(0) @binding(0)
var<storage, read_write> particles : array<Particle>;
```

なお、1つのディスパッチ内で同じリソースを入力と出力の両方に使用する設計には注意してください。
あるインボケーションが読み取ろうとしている値を、別のインボケーションが先に書き換えてしまうと、結果がGPUの実行順序に依存する「データ競合」が発生します。
ブラー（ぼかし）や布のシミュレーションのように、前状態を読み取って次状態を書き込む処理では、2つのリソースを交互に使用する「ピンポン（Ping-pong）」構成を採用します。

## GPU計算の2つの処理フロー

`webg` におけるコンピュートシェーダーの利用パターンは、大きく分けて「Render-first（描画後処理）」と「コンピュート-first（計算先行）」の2つのフローに分類されます。

### Render-first（描画後処理）
先に3Dシーンをレンダーターゲット（RenderTarget）へ描き、その画像や深度情報をコンピュートシェーダーで後加工するフローです。
ブルーム、Fog、DoF、SSAO、ディファードライティング、SSR、Vignetteなどのポストプロセスはこの系統に属します。

```text
3D シーン Render Pass
  -> コンピュートパス（効果の適用）
  -> FullscreenPass（画面へのコピー）
  -> キャンバス
```

このフローでは、標準の `WebgApp.frame()` を維持しながら、`onBeforeDraw` と `onAfterDraw3d` を使用して処理を挿入します。

Render-firstの処理では、GPU内部で扱う色と、キャンバスへ表示する色を分けて考えることが重要です。
照明、影、SSAO、SSR、Fog、ブルームなどの計算は、基本的に光量の加算や乗算が成立する線形色として進めます。
一方、画面に出す直前には、明るすぎる値を表示範囲へ圧縮するトーンマッピングと、ディスプレイ用のsRGB変換を行います。
この変換段階を一度だけ通すことで、暗部が白く浮く二重変換や、色がくすむ変換漏れを防げます。

`webg` の `ComputeEffectToneMapPass` では、トーンマッピング方式として `reinhard` と `linear` を選択できます。
`reinhard` は強い光をなだらかに圧縮するため、反射やブルームを含むシーンで白飛びを抑えやすい方式です。
`linear` は値を大きく変形せずに表示範囲へ収めるため、元の色の鮮やかさを確認したい調整用や、すでに明るさを制御できているシーンに向きます。

表示変換に関係する代表的なパラメーターは、`exposure`（露出）、`saturation`（彩度）、`gamma`（ガンマ）です。
`exposure`は線形HDR色へ掛けるため、トーンマッピングより前に全体の光量を調整します。
`saturation`はsRGB変換後の表示色で、輝度との補間量を調整します。

`gamma`は、sRGB変換の単純な累乗近似ではなく、トーンマッピング後の線形色を表示色へ変換する設定として扱います。`ComputeEffectToneMapPass`は暗部の線形区間と明部の2.4乗区間を持つ正確なsRGB伝達関数を適用します。
その後、`pow(srgbColor, 2.2 / gamma)`を表示上の追加調整として適用します。
したがって`gamma: 2.2`では追加の累乗が恒等変換になり、標準sRGBの結果をそのまま使います。
2.2以外の値は、表示装置の符号化を選ぶ設定ではなく、sRGB変換後の明るさを意図的に調整する設定です。

トーンマッピングの入力は線形HDRの`rgba16float`、出力はsRGB表示値を格納する`rgba8unorm`です。
出力形式を`rgba8unorm-srgb`にして同じsRGB変換をWebGPUへもう一度任せると、表示変換が二重になります。
輪郭抽出へ渡す入力は、表示色の輝度差を読めるトーンマッピング後の`rgba8unorm`または、標準描画先と同じ`bgra8unorm`にそろえます。`rgba16float`の中間色を使う場合は、先に表示色へ変換します。

FogとVignetteは、どちらも画面全体を処理しますが、置くべき色の段階は異なります。
Fogは距離に応じてシーンの光量と霧の色を混合するため、トーンマッピング前の線形HDR区間へ置き、`rgba16float`を入出力に使います。
Vignetteは完成した画面の周辺色を調整するため、トーンマッピングと必要な輪郭抽出が終わった表示色区間へ置き、`rgba8unorm`を入出力に使います。

この形式境界は、効果の実装がコンピュートシェーダーかどうかとは別の条件です。
Fogをトーンマッピング前の線形HDRへ置くことで、霧色とシーン光量の関係をトーンマッピングへ反映できます。
VignetteをHDR区間へ移すと、その後の露出やトーンマッピングによって周辺減光の見え方が変わり、最終画面を整えるという役割が曖昧になります。
個々のパスを手動接続するときも、統合パイプラインを使うときも、この順序と形式を保ちます。

また、負荷を軽減させる手法として、出力解像度の調整が有効です。
例えばSSRの場合、G-bufferはフル解像度のまま保持し、反射を計算するストレージテクスチャだけを低解像度に設定します。
`ComputeSsrPass` の `resolutionScale`（既定値 `0.7`）はこのための設定です。
反射は元のシーン色に混ぜられる補助成分であるため、出力解像度を下げても、元の色や深度の読み取り精度は保たれたまま負荷を下げられます。

さらに、計算不要なピクセルを明示的に除外することも重要です。
SSRでは、物理ベースレンダリング（Physically Based Rendering：PBR）のマテリアルから求めた鏡面寄与が十分小さい画素を`reflectivityThreshold`（既定値`0.05`）で除外します。基本色のアルファを反射率へ読み替えず、鏡面反射率、金属度、フレネル反射から鏡面反射の重みを求めます。
このように「出力解像度を下げる」方法と「寄与しないピクセルを早期に終了させる」方法を組み合わせることで、見た目の品質を維持しつつGPU負荷を最適化できます。

### コンピュート-first（計算先行）
先にGPU上の状態（粒子位置や物理状態など）を更新し、その最新結果をそのまま描画するフローです。
GPU粒子や布シミュレーション、GPU物理などがこれに当たります。

```text
コンピュートパス（状態更新）
  -> Render Pass（最新状態の描画）
  -> submit
```

このフローでは、`WebgApp` に `computeFrame: true` を指定し、`onComputeFrame` ハンドラの中で1フレーム分のGPUコマンド発行から `queue.submit()` までの全行程を制御します。

## `ComputePass` による処理の構築

`ComputePass`は、WGSL、バインディング、ユニフォーム、ディスパッチを一つの再利用可能な処理単位へまとめるために使います。
WebGPUの定型的なパイプライン準備をパスごとに繰り返さず、入力と出力の仕様、毎フレーム変わる値、実行数へ集中できます。

このクラスの目的は、内部処理をブラックボックス化することではなく、WGSLが要求するリソースをJavaScript側でも「名前」「バインディング番号」「種類」として明示し、実装上の不整合を早期に検出することにあります。

以下に、入力画像を少し暗くしてストレージテクスチャへ書き込むシンプルな構成例を示します。

```js
import ComputePass from "./webg/ComputePass.js";

const code = `
struct Params {
  values : vec4f,
};

@group(0) @binding(0) var<uniform> params : Params;
@group(0) @binding(1) var sourceTexture : texture_2d<f32>;
@group(0) @binding(2) var outputTexture : texture_storage_2d<rgba8unorm, write>;

@compute @workgroup_size(8, 8, 1)
fn main(@builtin(global_invocation_id) id : vec3<u32>) {
  let size = textureDimensions(outputTexture);
  if (id.x >= size.x || id.y >= size.y) {
    return;
  }
  let coord = vec2<i32>(id.xy);
  let color = textureLoad(sourceTexture, coord, 0);
  let gain = params.values.x;
  textureStore(outputTexture, coord, vec4f(color.rgb * gain, color.a));
}
`;

const darkenPass = new ComputePass(app.getGPU(), {
  label: "darken",
  code,
  workgroupSize: [8, 8, 1],
  uniformFloats: 4,
  bindings: [
    { binding: 0, name: "params", type: "uniform-buffer" },
    { binding: 1, name: "source", type: "sampled-texture" },
    {
      binding: 2,
      name: "output",
      type: "storage-texture",
      dispatchSize: true
    }
  ]
});

darkenPass.setUniforms(new Float32Array([0.82, 0.0, 0.0, 0.0]));
```

実行時は、現在動作しているレンダーパス（Render Pass）を閉じてから、同じコマンドエンコーダーへコンピュートパスを追加します。

```js
app.getGPU().endPass();

darkenPass.encode(
  app.getGPU().commandEncoder,
  {
    source: sceneTarget,
    output: outputTarget
  },
  {
    timestampWrites: app.getGpuTimestampWrites(true, true)
  }
);
```

`ComputePass`はエフェクトのエンコードに集中し、コマンドエンコーダーの作成と`queue.submit()`をアプリケーション側へ委ねます。
これにより、「シーン描画 $\rightarrow$ コンピュート効果 $\rightarrow$ フルスクリーンコピー」という1フレーム内の実行順序を、アプリケーション側で完全にコントロールできます。

### 最小の画像コンピュート処理

ここまでの断片を実際のアプリケーションへ組み込むには、入力となるシーン用レンダーターゲット（RenderTarget）、出力となるストレージテクスチャ、最終結果をキャンバスへ描く `FullscreenPass` が必要です。
次の例は、前節の `darkenPass` をRender-firstのフレームへ接続する全体の構成を示します。

シーンのShapeとNodeは38章までと同じ方法で `app.space` へ登録済みであるものとします。

```js
import WebgApp from "./webg/WebgApp.js";
import ComputePass from "./webg/ComputePass.js";
import FullscreenPass from "./webg/FullscreenPass.js";
import StorageTargetFactory, {
  resizeTarget
} from "./webg/StorageTargetFactory.js";

const app = new WebgApp({
  document,
  autoDrawScene: false,
  clearColor: [0.04, 0.05, 0.07, 1.0]
});
await app.init();

// createScene() 内で Shape と Node を app.space へ追加する
createScene(app);

const sceneTarget = app.screen.createRenderTarget({
  label: "darken:scene",
  format: app.getGPU().format,
  hasDepth: true
});

const targetFactory = new StorageTargetFactory(app.getGPU(), {
  label: "darken:storage"
});
const outputTarget = targetFactory.create({
  label: "darken:output",
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});

const darkenPass = new ComputePass(app.getGPU(), {
  label: "darken",
  code,
  workgroupSize: [8, 8, 1],
  uniformFloats: 4,
  bindings: [
    { binding: 0, name: "params", type: "uniform-buffer" },
    { binding: 1, name: "source", type: "sampled-texture" },
    {
      binding: 2,
      name: "output",
      type: "storage-texture",
      format: "rgba8unorm",
      dispatchSize: true
    }
  ]
});

const copyPass = new FullscreenPass(app.getGPU(), {
  targetFormat: app.getGPU().format
});

await Promise.all([
  sceneTarget.ready,
  outputTarget.ready,
  copyPass.init()
]);

app.start({
  onUpdate: ({ screen }) => {
    // 入力と出力の pixel 対応を保つため、両方を同じ寸法へ変更する
    resizeTarget(sceneTarget, screen.getWidth(), screen.getHeight());
    resizeTarget(outputTarget, screen.getWidth(), screen.getHeight());
  },

  onBeforeDraw: () => {
    // 第1段階: 通常の3Dシーンをオフスクリーンターゲットへ描く
    app.screen.beginPass({
      target: sceneTarget,
      clearColor: app.clearColor,
      colorLoadOp: "clear",
      depthClear: true
    });
    app.space.draw(app.eye);
  },

  onAfterDraw3d: () => {
    // 第2段階: シーンのレンダーパスを閉じ、同じコマンドエンコーダーへコンピュートパスを追加する
    darkenPass.setUniforms(
      new Float32Array([0.82, 0.0, 0.0, 0.0])
    );
    app.getGPU().endPass();
    darkenPass.encode(
      app.getGPU().commandEncoder,
      {
        source: sceneTarget,
        output: outputTarget
      }
    );

    // 第3段階: ストレージテクスチャをキャンバス用レンダーパスへコピーする
    app.screen.beginPresentPass({
      clearColor: app.clearColor,
      colorLoadOp: "clear"
    });
    copyPass.draw(outputTarget);
    app.screen.clearDepthBuffer();
  }
});
```

この例では、`WebgApp` がフレームのコマンドエンコーダーと最終的なサブミット（submit）を管理します。
ストレージテクスチャはスワップチェインへ直接表示せず、最後に `FullscreenPass` から読み取ってキャンバスへ描画します。

アプリケーションを終了してこれらのリソースが不要になった場合は、それぞれを作成したオブジェクトの`destroy()`を明示的に呼びます。

```js
darkenPass.destroy();
outputTarget.destroy();
sceneTarget.destroy();
```

## まとめ

コンピュート処理を安全に接続するには、入力と出力の資源、座標空間、深度規則、色の意味、実行順を先に決めます。`WebgApp`のフレーム処理へ記録したコマンドは、結果を表示するパスまで含めて一つの処理フローとして確認します。
次に22章で、ストレージ資源の交換、同期、メモリ配置、実行時間の測定を詳しく調べます。
