# 描画内部の共通規則

本章では、行列の配列配置、投影と姿勢、深度、G-buffer、PBRテクスチャの色空間を、描画内部の共通規則として詳しく説明します。03章の位置と見え方、30章の材質と光を、GPUへ渡す値と計算へ対応付けます。

## この章の読み方

### この章を読む前に必要な知識

03章の座標変換、18章のWGSL（WebGPU Shading Language：WebGPU用シェーディング言語）、30章のPBR（Physically Based Rendering：物理ベースレンダリング）基本を知っていると読みやすくなります。

### 初回に読む範囲

座標空間、投影行列、ビュー行列、カメラフレーム、深度の意味を先に読んでください。

### 必要になったときに読む範囲

Reverse-Z（深度精度を遠方側へ配分する投影規則）、G-buffer（照明計算へ渡す画面単位の表面情報）、線形HDR（High Dynamic Range：広い輝度範囲）、sRGB、トーンマッピング、透明と不透明の順序は内部接続時に参照してください。

### この章を終えた時点でできること

描画パス間で共有・変換すべき座標、深度、色の情報を説明できます。

## 計算の流儀：行列とベクトル

行列とベクトルの計算規約は、変換を合成する順序とGPUへ渡す配列の並びを一致させるために理解します。
規約が分かれば、値の格納形式と乗算の意味を分けて確認できます。
`webg`の`Matrix`クラスは4×4行列を使用し、内部配列`mat[16]`は列優先（Column-major）で保持されています。
`set(row, column, val)`メソッドが`column * 4 + row`というインデックス計算を行うため、メモリ上の並びは次の通りです。

```text
| m[0]  m[4]  m[8]  m[12] |
| m[1]  m[5]  m[9]  m[13] |
| m[2]  m[6]  m[10] m[14] |
| m[3]  m[7]  m[11] m[15] |
```

この構成では、平行移動成分は最後の列に格納され、`m[12] = tx`、`m[13] = ty`、`m[14] = tz` となります。
また、左上の3×3部分は主に回転基底として利用されます。
`CoordinateSystem` は `position`（位置）、`quat`（回転）、`uniform scale`（一様スケール）からローカル行列を再構築します。
なお、本ライブラリでは、X、Y、Z軸によって倍率が異なる非一様スケール（non-ユニフォームスケール）はサポート対象外としています。

`webg` では、ベクトルを列ベクトルとして右側に配置する数学的な作法を採用しています。
数式としては以下のように表現されます。

```text
v' = M * v
```

これを4次元同次座標で記述すると、以下の計算になります。

```text
|x'|   | m00 m01 m02 tx |   |x|
|y'| = | m10 m11 m12 ty | * |y|
|z'|   | m20 m21 m22 tz |   |z|
|w'|   |  0   0   0   1 |   |1|
```

`Matrix.mulVector([x, y, z])` は、この考えに基づき `w=1` とした点を掛けています。

```js
let x = m[0] * v[0] + m[4] * v[1] + m[8]  * v[2] + m[12];
let y = m[1] * v[0] + m[5] * v[1] + m[9]  * v[2] + m[13];
let z = m[2] * v[0] + m[6] * v[1] + m[10] * v[2] + m[14];
```

`webg` では列ベクトル（`M * v`）形式を採用します。行ベクトル（`v * M`）を使う実装とは、行列の読み方と合成順序を分けて考えます。
行列合成において、`Matrix.mul(mb)` は `this = this * mb`、`Matrix.lmul(mb)` は `this = mb * this` となります。
この二つは、回転、平行移動、一様スケールからなる3Dオブジェクトの変換を効率よく合成するメソッドで、結果の4行目を剛体変換の形式に揃えます。
透視投影行列には透視除算に必要な4行目があるため、projectionとviewを合成するときは`Matrix.mul_()`を使用し、4×4の全要素を計算します。
`mul()`と`mul_()`は乗算順序が同じですが、保持する行列要素の範囲が異なります。
親子階層の計算では `world = parent * local` となるため、列ベクトル形式では「右側の変換から先に作用する」と理解してください。
つまり、`parent * local * v` という式では、最初に `local` が点 `v` に作用し、その結果に `parent` が作用します。

### 座標空間の変換フロー

3Dのコードを読むときは、値が「どの座標空間にあるのか」を常に意識する必要があります。
同じ `[1, 2, 3]` という数値でも、それがローカル座標なのか、ワールド座標なのか、カメラから見た座標なのかによって意味が変わります。
`webg` の描画では、頂点はおおむね次の順序で変換されます。

```text
ローカル座標
  -> ワールド座標
  -> view 座標
  -> clip 座標
  -> NDC
  -> 画面座標
```

ローカル座標は、形状やノード自身から見た座標です。
`Shape` に登録した頂点は、最初はこの座標系にあります。
例えば、立方体の中心を原点にして頂点を `[-1, -1, -1]` から `[1, 1, 1]` に置く場合、それは「立方体自身から見た座標」です。

ワールド座標は、シーン全体の中での座標です。
ノードの位置、回転、スケール、親子構造を反映すると、ローカル座標の頂点はワールド座標へ移ります。
親ノードが動くと子ノードのワールド座標が変わり、子ノードのローカル座標は親からの相対位置として保持されます。

ビュー座標は、カメラから見た座標です。
実際にはカメラを原点へ戻し、カメラの向きを基準方向へ戻すような逆変換を、シーン全体にかけた座標系です。
`webg` では視点ノードのワールド行列からビュー行列を作り、ワールド座標をビュー座標へ変換します。

クリップ座標は、透視投影行列を掛けた直後の座標です。
この段階では、`x, y, z, w`の4成分を持つ同次座標です。透視除算と画面への対応付けを経て、二次元の画面座標になります。
GPUはこの値を使って視錐体の外側にある頂点や三角形をクリップします。

NDC（Normalized Device Coordinates）は、クリップ座標を `w` で割った後の正規化された座標です。
概念的には、画面の左が `-1`、右が `+1`、下が `-1`、上が `+1` という範囲になります。
WebGPUでは、深度に対応するNDCの `z` は `0..1` の範囲として扱われます。
最後にビューポート変換によって、NDCは実際のキャンバス上のピクセル位置、つまり画面座標へ変換されます。
キャンバスのピクセル座標では一般に左上が原点になり、下方向へ `y` が増えるため、3D空間やNDCの `+Y=上` とは見方が変わる点に注意します。

この変換フローを意識すると、デバッグ時の質問が具体的になります。
例えば「モデルの頂点が壊れている」のか、「ノードのワールド変換が間違っている」のか、「ビュー行列でカメラ基準にした時点で外へ出ている」のか、「投影後にクリップされている」のかを分けて考えられます。
矩形選択やマーカ表示のように3Dの点を2D画面上へ投影する処理でも、この順序がそのまま使われます。

### 同次座標とwの役割

3Dの行列計算では、位置を `[x, y, z]` の3成分だけでなく、`[x, y, z, w]` の4成分で扱います。
この表現を同次座標と呼びます。
通常の点は `w=1` として扱います。
これにより、4×4行列の中に回転、拡大縮小、平行移動をまとめて表現できます。

```text
point = [x, y, z, 1]
```

一方、方向ベクトルは `w=0` として扱います。

```text
direction = [x, y, z, 0]
```

この違いは重要です。
点には平行移動が作用し、方向には回転とスケールだけが作用します。
例えば「光がどちらから来るか」や「法線がどちらを向いているか」は方向です。カメラやモデルを平行移動しても、方向ベクトルの向きは保たれます。
`w=0` にすると、4×4行列の平行移動成分が計算に入らないため、方向として正しく変換できます。

透視投影では、この `w` がさらに重要になります。
投影行列を掛けた後のクリップ座標は `[x, y, z, w]` のままで、GPUは最終的に `x / w`、`y / w`、`z / w` を計算します。
これを透視除算と呼びます。
遠くの点ほど `w` の影響を受け、画面上では小さく、中心に近づくように写ります。
これが遠近感の正体です。

`w` は普段のアプリケーションコードでは直接意識しないことも多い値ですが、シェーダー、投影、画面座標への変換、選択処理を理解するための重要な手掛かりです。
`vec4(position, 1.0)` は「これは点である」、`vec4(direction, 0.0)` は「これは方向である」と読むと、行列計算の意味を追いやすくなります。

## 透視投影行列と視野角

3Dカメラにおいて、位置と姿勢に加えて「どの範囲を写すか」を決定するのが「透視投影行列」です。
`webg` では `Matrix.makeProjectionMatrix(near, far, vfov, ratio)` を使用してこれを生成します。
FOV（Field of View）は「視野角」のことで、一度に見える範囲の角度のことです。

![視野角と見える範囲](img/fov.png)

*FOVが小さいほど望遠寄りで写る範囲は狭くなり、FOVが大きいほど広角寄りで写る範囲は広くなります。
*

```js
makeProjectionMatrix(near, far, vfov, ratio) {
  const h = 1.0 / Math.tan(vfov * 0.5 * Math.PI / 180.0);
  const w = h / ratio;

  this.makeUnit();
  this.mat[0] = w;
  this.mat[5] = h;
  this.mat[10] = near / (far - near);
  this.mat[11] = -1.0;
  this.mat[14] = far * near / (far - near);
  this.mat[15] = 0.0;
}
```

この抜粋は、通常カメラで使うReverse-Z投影の有限`far`版です。
near planeを深度1、far planeを深度0へ写します。
実際の`Matrix.makeProjectionMatrix()`は`near`、`far`、画角、アスペクト比を検証し、`far: Infinity`にも対応します。
シャドウマップは同じ式を流用せず、第5引数へ`SHADOW_STANDARD_Z`を渡してnearを0、farを1へ写します。

ここで重要なのは、`vfov` が縦方向の視野角である点です。
`h = 1 / tan(vfov / 2)` となるため、視野角を小さくすると `h` が大きくなり、結果として画面に写る範囲が狭まります。
これは写真の焦点距離を長くした状態に近く、望遠寄りの圧縮された見え方になります。
逆に視野角を大きくすると、写る範囲が広がり、広角寄りの強い遠近感が生じます。

写真や映像に慣れている人にとっては、視野角をレンズの焦点距離に置き換えると感覚をつかみやすくなります。
フルサイズカメラのセンサーは一般に `36mm x 24mm` として扱われるため、短辺方向のFOVをフルサイズ換算の焦点距離へ変換する場合は、短辺 `24mm` を使って次の式で求められます。

```text
focalLengthMm = 24 / (2 * tan(fovShort / 2))
```

`fovShort` は短辺方向の視野角です。
横長画面では縦方向が短辺であり、縦長画面では横方向が短辺になります。
次の表は、代表的なフルサイズ換算の焦点距離と画角の関係です。

|焦点距離(mm)|水平画角(度)|垂直画角(度)|
| ---: | ---: | ---: |
|   8  | 132.1 | 112.6 |
|  12  | 112.6 |  90.0 |
|  16  |  96.7 |  73.7 |
|  24  |  73.7 |  53.1 |
|  35  |  54.4 |  37.9 |
|  50  |  39.6 |  27.0 |
|  85  |  23.9 |  16.0 |
| 135  |  15.2 |  10.1 |
| 200  |  10.3 |   6.9 |

![焦点距離と見え方の違い](img/camera_fov.jpg)

焦点距離は、同じ対象を同じ大きさに写したときの遠近感を考える上でも役立ちます。
広角側では近くのものが大きく、遠くのものが小さく見えやすくなり、望遠側では奥行き方向の差が圧縮されたように見えます。
`webg` の `viewAngle` は物理レンズを模した視野角です。短辺FOVをこの表に対応させると、ビューアやモデラーで「いまどの程度のレンズ感で見ているか」を判断しやすくなります。

人間の視野は非常に広く、上下方向でもおよそ120度、水平方向では180度程度まで外界を感じ取れます。
これは「何かが視界に入っている」範囲です。画面上の大きさや奥行きを自然に判断する範囲は、視野角の選択で別に設計します。
写真や映像では、フルサイズ換算で55mm程度の標準レンズが、人が対象の大きさを無理なく捉える感覚に近いものとして扱われます。

そのため、3Dアプリケーションでは、対象を注視するか移動感を重視するかに合わせてFOVを選びます。
モデラー、キャラクターの確認のように狭い範囲を注視するアプリケーションでは、望遠側のFOVにすると形状の比率を読み取りやすくなります。
一方、広大な地形、レースゲームといった俯瞰的なシーン演出では、広角寄りのFOVにすることで周囲の情報や移動感を得やすくなりますが、画面隅の歪みは大きくなります。
カメラの`viewAngle`は、アプリケーションが何を見せたいかに合わせて調整します。

また、横方向の範囲は `ratio = width / height`（アスペクト比）を用いて `w = h / ratio` として決定されます。
アスペクト比とは画面の横幅を縦幅で割った値です。
例えば `16:9` のPC画面は約 `1.78`、正方形は `1.0`、縦長のスマートフォン画面は `0.5` 前後になることがあります。
同じ縦FOVを使っても、横長画面では横方向に広く写り、縦長画面では縦方向に広く写るため、アスペクト比は構図と操作感に強く影響します。

`webg` の `Screen.getRecommendedFov(base)` は、アスペクト比の違いによって短辺方向の見える範囲が大きく変わらないようにするためのヘルパー関数です。
`base` は短辺方向のFOVとして扱われます。
横長画面では縦方向が短辺なので `base` をそのまま縦FOVとして使い、縦長画面では横方向が短辺になるため、横FOVが `base` になるように縦FOVを逆算します。
この仕組みの詳しい式と実装上の扱いは、06章の「視野角と投影行列の管理」で説明します。

`near`（近面）と `far`（遠面）は、描画対象とする奥行きの範囲を決定するクリッピング面（裁断面）です。
この範囲外のオブジェクトはクリップ対象となり、描画対象から外れます。
また、この値は深度バッファの精度に影響します。
通常カメラのReverse-Zと`depth32float`は遠方の精度を改善します。`near`はシーンの実寸に合わせ、極端に小さい値を避けると深度精度を保てます。
シーンの実際の規模に合わせて範囲を決めます。

なお、「カメラを近づけて対象を大きく見せること」と「FOVを狭めて大きく見せること」は異なります。
カメラを近づけると遠近感が強調されますが、FOVを狭めると位置を変えずに写る範囲だけを制限するため、望遠レンズのような見え方になります。
この違いを理解しておくことは、`EyeRig` 等によるカメラ制御を設計する上で非常に重要です。

### 深度バッファと描画順

3Dシーンでは、手前のものが奥のものを隠します。
この前後関係をGPUが判定するために使うのが深度バッファです。
深度バッファには、各ピクセルについて「これまでに描かれた最も手前の深度」が記録されます。
新しいフラグメントを描こうとしたとき、その深度がすでに記録されている値より手前であれば描画され、奥であれば破棄されます。
この判定が深度テストです。

深度バッファがあるため、多くの不透明オブジェクトは描画順に強く依存せず、正しく前後関係を保って表示できます。
例えば、奥の立方体と手前の立方体をどちらの順で描いても、深度テストと深度書き込みが正しく有効なら、GPUが深度に基づいて前後関係を揃えます。

webgの現行通常カメラでは、深度形式は`depth32float`、クリア値は0、比較関数は`greater`です。
近い面ほど大きな深度になります。
方向光とスポットライトのシャドウマップだけはStandard-Zを使い、クリア値1、比較関数`less`とします。
Camera用深度とShadow用深度は形式が同じでも数値の向きが反対です。復元式もそれぞれの規約に合わせます。

選択面、頂点マーカ、ワイヤーフレーム、半透明の面といった補助表示は、深度テスト、深度書き込み、アルファブレンドの組み合わせで描き分けます。
選択面、頂点マーカ、ワイヤーフレーム、半透明の面のような補助表示では、深度テストを使うか、深度書き込みを行うか、アルファブレンドを使うかによって見え方が変わります。
例えば、通常のシーンを描いた後に選択面を重ねる場合、選択面が深度を書き込むと、その後に描くマーカや辺の表示を邪魔することがあります。
反対に、深度をまったく見ない補助表示は、奥にある要素まで手前に浮いて見えることがあります。

そのため、3Dの描画では「どの順序で描くか」と「深度テスト / 深度書き込み / ブレンドをどう設定するか」を組み合わせて考えます。
webgの現行描画では、materialの`alpha_mode`が`OPAQUE`または`MASK`の三角形を先にdepth書き込みありで描き、`BLEND`の三角形を全Shapeから集めます。
`alpha_mode`を省略したマテリアルは、`alpha`が1.0なら`OPAQUE`、1.0未満なら`BLEND`として扱います。
半透明三角形はview-spaceの重心深度で奥から手前へ並べ、depth testあり、depth書き込みなし、Alpha Blendありで描きます。
三角形同士の交差や循環する前後関係には、重心深度ソートに加えて、形状分割や専用の順序制御を組み合わせます。
深度バッファは、物体の前後関係を決め、見え方と操作感を支える基礎です。

## 視線方向とビュー行列

透視投影行列を理解するときは、「カメラがどちらを向いているか」と「その向きに対して視錐体（画面に表示される範囲）がどのように広がるか」を一緒に捉えることが重要です。
`webg` では空間全体の基本軸を `+X=右`、`+Y=上`、`+Z=前` と定義していますが、視点ノードをカメラとして使うときは、そのノードのローカル座標系における `-Z` 方向が視線方向になります。
したがって、視点ノードに回転が入っていない初期状態では、「カメラの前方」はローカル `-Z`、「カメラの右」はローカル `+X`、「カメラの上」はローカル `+Y` です。

ここは、概念の切り替えが必要なため、混乱を招きやすいポイントです。
空間全体の定義では `+Z` を「前」と呼んでいるのに、カメラは `-Z` を見るからです。
しかしこれは3Dグラフィックスでは一般的な考え方で、カメラを「世界を見るための座標変換」として扱うと自然に理解できます。
例えばカメラをワールド座標で `z=20` に置き、原点方向を見せたいとき、視点ノードは `+Z` 側に配置され、そこから `-Z` 方向へ向いていると考えると整理しやすくなります。

![座標系と視線方向](img/ViewFrustum.jpg)

*webgの座標系とは右手系を採用し、+X=右、+Y=上、+Z=前を基本軸としますが、視線方向はZ軸の負の方向です。
*

視錐台は、この視線方向 `-Z` に向かって広がる「先端を切り落とした四角錐」です。
視点ノードの近くにある面が `near`、遠くにある面が `far` で、`vfov` は縦方向の開き具合を決めます。
`vfov` を大きくすると視錐体は大きく開き、広い範囲が写ります。
逆に `vfov` を小さくすると視錐台は細くなり、狭い範囲を望遠寄りに写します。
透視投影行列は、この視錐台の内側にある点を画面へ写すための変換です。

`webg` の低水準な実装では、この考え方を `Space.draw(eye_node)` と `Matrix.makeView()` がそのまま受け持っています。
描画の開始時には、まず視点ノードのワールド行列を作り、その後でその逆行列をビュー行列として使います。

```js
eye_node.setWorldMatrix();
let view_matrix = new Matrix();
view_matrix.makeView(eye_node.worldMatrix);
```

`Matrix.makeView()` の中身は非常に単純で、渡されたワールド行列をコピーして逆行列へ変換しているだけです。

```js
makeView(w) {
  this.copyFrom(w);
  this.inverse();
}
```

ここで意味しているのは、「カメラ自身を動かす代わりに、シーン全体をカメラ基準の座標系へ変換する」ということです。
例えば、視点ノードがワールド空間で右へ5動いていれば、ビュー行列ではシーン全体が左へ5動いたのと同じ効果になります。
視点ノードが上を向けば、ビュー行列ではシーン全体が下を向いたように見える変換になります。
つまりビュー行列は、「視点ノードの姿勢を打ち消して、世界をカメラから見た座標へ並べ替える行列」と考えると理解しやすくなります。

この変換を通したあとで透視投影行列を掛けると、視錐体の内側にある点だけが正しく画面へ投影されます。
流れとしては、`ローカル座標 -> ワールド座標 -> view 座標 -> 透視投影 -> 画面` です。
`Node` の親子構造やボーン階層でどれだけ複雑な変換を行っていても、最終的にはまずワールド座標へ集約され、次にビュー行列で「カメラから見た座標」へ変換され、そのあと投影行列で2D画面へ写されます。
透視投影行列とビュー行列を一続きの変換として理解すると、カメラ制御やデバッグ時の見通しが大きく良くなります。

## クォータニオンによる回転表現

クォータニオン（四元数）は、3Dの回転を4つの要素で表現する手法です。
`webg` の `Quat` クラスでは、要素の並び順を `[w, x, y, z]` と定義し、`w` を実部、`x, y, z` を虚部として保持します。
回転がない状態は単位クォータニオン `[1, 0, 0, 0]` となります。

```js
this.q = [1.0, 0.0, 0.0, 0.0];
```

クォータニオンを採用する主な理由は、姿勢をオイラー角の3軸状態として保持する場合のジンバルロックを避け、回転の合成や球面線形補間（Slerp）を安定して行えるためです。
オイラー角から姿勢を入力する際の特異性や、pitch制限の設計は、入力値を受け取るアプリケーション側で扱います。
`webg` の `CoordinateSystem` は内部姿勢をクォータニオンで保持し、`setAttitude()` や `rotate()` の入力を最終的に `Quat` へ変換して格納します。

実行時（ランタイム）においては、クォータニオンを回転行列へ変換して利用します。
`CoordinateSystem.setMatrix()` では、`Quat` から3×3の回転成分を `Matrix.setByQuat()` で生成し、そこに平行移動成分を加えてローカル行列を構築します。
また、`CoordinateSystem.setByMatrix(matrix)` では、行列から `Quat.matrixToQuat(matrix)` を用いてクォータニオンを復元します。

単軸回転の場合、回転軸 $\text{axis} = (ax, ay, az)$ と回転角 $\theta$ を用いて、概念的に次のように定義されます。

```text
q = [ cos(theta / 2),
      ax * sin(theta / 2),
      ay * sin(theta / 2),
      az * sin(theta / 2) ]
```

`webg` の `setRotateX()`、`setRotateY()`、`setRotateZ()` は、この定義を各軸に特化させたものです。
クォータニオンが回転を正しく表すためには、長さが1の「単位クォータニオン」である必要があります。
計算を繰り返すと丸め誤差が蓄積するため、`Quat.normalize()` を用いて長さを補正します。
`Quat.slerp()` の後にも `normalize()` が呼ばれるのは、回転表現を維持するための基本処理です。

数学的には、ベクトル $v$ をクォータニオン $q$ で回転させる操作は $v' = q * v * q^{-1}$ と表現されますが、`webg` の通常フローでは、クォータニオンを回転行列に変換して計算する手法が一般的です。

## glTF / GLBとの整合性

glTF / GLB形式のデータを扱う際は、クォータニオンの要素順序に注意が必要です。
`webg` は数学的な表記に基づき実部を先頭とする `[w, x, y, z]` 形式を採用していますが、glTF規格では `[x, y, z, w]` 形式が採用されています。

![クォータニオンとglTFの並び順](img/fig03_04_quat_and_gltf_order.jpg)

*webgのクォータニオンは [w, x, y, z]、glTF / GLBは [x, y, z, w] であるため、読み込み時に順序を変換してランタイム姿勢に適用します。
*

このため、`SceneLoader` や `ModelBuilder` では、glTFのデータを読み込んだ後に要素の並べ替えを行い、`webg` 形式の `Quat` へ変換しています。
glTFの値をそのまま `Quat.q` に代入すると回転が正しく適用されないため、ローダー側でこの変換が行われていることを理解しておく必要があります。

また、glTFのTRS（Translation, Rotation, Scale）情報はローダーを通じて読み込まれます。
`webg` の `Node` / `CoordinateSystem` は一様スケール（ユニフォームスケール）を保持できるため、glTFの変換情報をそのままシーングラフのローカル行列として扱うことが可能です。
ただし、非一様スケール（non-ユニフォームスケール）は本ライブラリのサポート対象外であるため、この点に留意して実装する必要があります。

## 描画とコンピュートで共有する座標と深度

画面の深度や三次元位置を利用するコンピュート処理では、描画時と同じ座標、カメラ状態、投影方法を使う必要があります。
ここでは、公開APIを複数の処理から共有するために必要な実装上の基準を説明します。
通常のアプリケーションで`WebgApp`の標準描画だけを使う場合、これらの処理は`WebgApp`がまとめて組み立てます。
G-buffer、深度を読む画面効果、独自の描画パイプラインを接続するときに必要になる知識です。

### JavaScriptのワールド座標とGPUのデータ精度

JavaScriptの`Number`は64ビット浮動小数点数です。
一方、WGSLの`f32`、頂点バッファ、一般的なユニフォーム行列は32ビット浮動小数点数です。
32ビット浮動小数点数は、値が大きくなるほど隣り合う表現可能な値の間隔も大きくなります。
そのため、原点から遠い位置をGPUへそのまま渡すと、近くにある物体同士の小さな位置差を保持できない場合があります。

`webg`では、Node、物理ボディ、レイキャストなどのワールド位置をJavaScriptの`Number`で保持します。
メッシュの頂点とボーンパレットは、形状自身を表すモデルローカル座標です。
ワールド配置をメッシュの全頂点へ焼き込まず、Nodeの変換として分けて保持することで、同じ形状を異なる場所へ配置できます。

### カメラ相対座標へ変換してからGPUへ渡す

大きなワールド座標をGPUへ渡した後でオブジェクト位置とカメラ位置を減算すると、減算前の変換で細かな位置差が失われる可能性があります。
そこで`webg`は、CPU側で次の差を先に求めます。

```text
カメラ相対位置 = オブジェクトのワールド位置 - カメラのワールド位置
```

この計算はJavaScriptの`Number`で行われます。
カメラ付近の小さな値へ変換した後、その結果をGPU用の32ビット浮動小数点数へ変換します。
回転と拡大率はオブジェクトのワールド行列から維持し、平行移動だけをカメラ相対位置へ置き換えてモデルビュー行列を作ります。

カメラ相対座標は描画用の表現です。
カメラの移動は、Node、アニメーション、物理ボディ、音源、衝突判定の座標へ直接反映する操作とは分けて扱います。
モデルローカルの頂点やボーン行列も、カメラ位置を求める入力として別の座標変換へ渡します。
アプリケーション状態はワールド座標に保ち、GPUへ渡す直前だけカメラ相対座標へ変換します。

### カメラフレームで描画状態を確定する

`CameraFrame`は、一回の描画で共有するカメラ状態を、作成後に内容を変更できないスナップショットとして保持します。
内容は、カメラのワールド行列と位置、ビュー回転、`near`、`far`、縦方向の視野角、アスペクト比、深度規則、投影行列です。
`WebgApp`は入力と`onUpdate`による状態更新が終わった後、描画を始める直前にカメラフレームを作ります。

G-bufferの生成、深度からの位置復元、SSAO、SSR（Screen Space Reflections：画面空間反射）、Fog、DoF（Depth of Field：被写界深度）などが同じカメラフレームを使うと、ある視点で作った深度を別の視点の投影で読み直す誤りを防げます。
`Space.draw(eye)`による単純なフォワードレンダリング経路では、`WebgApp`が投影情報を持たないカメラ変換のスナップショットを内部で作ります。`CameraFrame`はG-bufferや深度依存効果を使う経路で共有します。

`renderFrameToken`は、完全な`CameraFrame`を公開コールバックへ直接渡さず、同じ描画フレームであることだけを示す識別子です。
利用者は中の値を読み書きせず、オフスクリーンシーンの開始、`Space.draw()`、その深度を読むパスへ同じトークンを渡します。
色テクスチャだけを読む処理や通常の単一パス描画は、入力テクスチャと現在の描画状態で処理します。`renderFrameToken`は同じフレームのオフスクリーン描画と後段効果を結び付ける値として共有します。

### 通常カメラではReverse-Zを使う

透視投影後の深度は0から1の範囲で深度テクスチャへ保存されます。
通常カメラでは、浮動小数点深度の精度分布を遠方まで活用するため、手前を1、奥を0とするReverse-Zを使います。
`CAMERA_REVERSE_Z`は、次の設定を一つの変更不能なオブジェクトへまとめています。

|用途|形式|nearの深度|farの深度|クリア値|比較|
|---|---|---:|---:|---:|---|
|通常カメラ|`depth32float`|1|0|0|`greater`|
|シャドウマップ|`depth32float`|0|1|1|`less`|

通常カメラでは、クリア値0が未描画の背景も表します。
新しいフラグメントの深度が記録済みの値より大きい場合に、そのフラグメントが手前にあると判断します。
シャドウマップはライトから見た通常Zを使うため、同じ`depth32float`でもnear、far、クリア値、比較関数の意味が逆です。
形式に加えて用途と深度規約を確認し、カメラ深度とシャドウ深度をそれぞれのパスへ渡します。

通常の不透明面では`CAMERA_REVERSE_Z.compare`、すなわち`"greater"`を使います。
同じ深度の面も描画するワイヤーフレームやオーバーレイでは、`CAMERA_REVERSE_Z.compareEqual`、すなわち`"greater-equal"`を使います。
深度による前後関係が不要な画面固定表示では、深度アタッチメントを持たない表示パスを使うか、深度付きパスなら`"always"`を明示します。

`CAMERA_REVERSE_Z`と`SHADOW_STANDARD_Z`は、形式、クリア値、比較関数、nearとfarの意味を一組にした変更不能な規則オブジェクトです。
API境界では、公開された規則オブジェクトそのものを渡します。
`depth32float`が同じでも、用途とReverse-Z／Standard-Zの規約を一緒に管理すると、カメラ深度とシャドウ深度を区別して正しい復元式を選べます。
規則オブジェクトの同一性まで検証することで、一部の値だけを変更した独自規則が後段へ混入することを防ぎます。

### 深度から距離と位置を復元する

Fog、DoF、SSAO、SSRなどは、深度テクスチャに保存された0から1の値を、カメラからの距離またはビュー空間位置へ戻して使用します。
通常カメラの有限`far`に対するReverse-Z深度$d$から、正のビュー空間距離$z$を求める式は次のとおりです。

```text
z = near * far / (near + d(far - near))
```

`far`が無限遠の場合は、次の式になります。

```text
z = near / d
```

背景の深度はクリア値0で、物体までの距離とは別の背景値として扱います。
そのため、深度を復元する前に背景かどうかを判定し、処理の目的に応じた値を返します。
たとえばSSAOでは遮蔽なし、SSRでは反射なし、DoFでは元のシーン色を使います。
Fogでも距離を推測せず、入力されたシーン色をそのまま残します。
背景値0は背景として分岐し、物体距離の式から切り離します。分母へ微小値を足して巨大な有限距離へ読み替える処理は、入力の意味を変えるため対象外です。

深度から画素の三次元位置を復元する場合は、同じカメラフレームの視野角、アスペクト比、`near`、`far`を使います。
深度テクスチャと同じフレームのカメラ情報を使い、投影値は共有された`cameraFrame`から取得します。

## PBR G-bufferへマテリアルを保存する

不透明物は、最初に照明前の表面情報をG-bufferへ保存します。現在の構成は次のとおりです。

- 基本色：`rgba8unorm-srgb`
- ビュー空間法線：`rgba8unorm`
- マテリアル：`rgba8unorm`
  - R：鏡面反射率（`specular`）
  - G：粗さ（`roughness`）
  - B：金属度（`metallic`）
  - A：環境遮蔽（`occlusion`）
- 発光：`rgba16float`
- カメラ深度：`depth32float`のReverse-Z

発光をマテリアルの8ビット成分へ入れず、独立したHDRアタッチメントへ保存することで、色付きの強い発光をトーンマッピング前まで保持できます。

透明物は一画素に複数の表面が重なるため、不透明物のG-bufferとは分けてPBR前方描画として合成します。不透明物の照明とSSRを先に処理し、その後に透明表面を重ねます。

## PBRテクスチャを役割で分ける

glTF 2.0 coreと同じ基本構成では、五種類のテクスチャを使います。

### 基本色テクスチャ

表示用sRGBの色です。基本色係数（`baseColorFactor`）も線形計算へ入る前に正しく扱います。アルファモード（`alphaMode`）によって、不透明、マスク、アルファ合成の分類にも使われます。

### 法線テクスチャ

接線空間の法線です。TBN（Tangent、Bitangent、Normal：接線、従法線、法線）を使って描画空間へ変換します。法線倍率（`normalScale`）で凹凸の強さを調整します。

### 金属度・粗さテクスチャ

glTFではGチャンネルに粗さ、Bチャンネルに金属度を格納します。それぞれの係数とテクスチャ値を乗算して最終値を作ります。

### 環境遮蔽テクスチャ

環境光が届きにくい細部を表し、環境遮蔽の強度（`occlusionStrength`）で作用量を調整します。直接光には独立したシャドウと照明計算を適用します。

### 発光テクスチャ

自己発光の色を表します。sRGBテクスチャを線形化し、発光係数（`emissiveFactor`）を掛けて独立したHDRアタッチメントへ保存します。

PBRテクスチャは、チャンネルごとに意味と色空間が異なります。base colorとemissiveはsRGBから線形色へ変換し、normal、metallic-roughness、occlusionは数値dataとして扱います。

## glTFマテリアルを同じ意味で読み込む

`GltfShape`は、glTF 2.0 coreの`baseColorFactor`、`metallicFactor`、`roughnessFactor`、五種類のテクスチャ、`normalScale`、`occlusionStrength`、`emissiveFactor`、`alphaMode`、`alphaCutoff`、`doubleSided`を実行時の`Shape`へ反映します。

重要なのは、glTFの値をPBR G-bufferとPBR前方描画が同じ意味で読むことです。金属度と粗さはPBRの意味を保ったまま使い、Phong用の`power`とは別のPBRパラメータとして管理します。

glTFのTransmission拡張はcoreマテリアルとは別の入力として扱います。現在の画面空間Transmissionへ接続するには、拡張機能のエネルギー配分とアルファ値1の扱いを専用の入力処理で定義します。

## SSRを環境反射と統合する

IBLの鏡面反射は画面外を含む環境を提供し、SSR（Screen Space Reflections：画面空間反射）は現在の画面に見える不透明表面を反射へ加えます。動く物体や近くの壁を画面内の反射へ反映する場合はSSRを組み合わせます。

単純にIBLとSSRを加算すると、同じ鏡面反射のエネルギーを二重に数えます。webgの`pbr-ssr`モードでは、遅延照明がIBLの鏡面反射だけを別の描画先へ出力します。SSRの交差が見つかった画素では、その鏡面反射を交差位置の放射輝度へ信頼度の分だけ置き換えます。

```text
出力
  = 基礎となるHDR色
    + (SSRの鏡面反射 - IBLの鏡面反射) × 信頼度
```

レイが交差しなかった場合や画面端では信頼度が0になり、元のIBLが残ります。固定色を代替値として加えず、環境反射と画面内反射の担当範囲を明示します。

## 透明物も同じBRDFで照明する

透明物はPBR G-bufferと分けて前方描画へ送り、照明には不透明物と同じPBRの意味を使います。`PbrForwardShader`は`PbrBrdf.js`を共有し、直接光、局所光、シャドウ、IBL、発光を同じマテリアル値で評価します。

不透明物の遅延描画と透明物の前方描画では、処理順の違いにより画像の見え方が変わります。透明物には奥から手前の合成、背景ぼかし、Transmissionが加わります。表面自身のGGX反射は同じ式で評価します。

## Transmissionで屈折と吸収を扱う

Transmissionは、透明表面の背後にあるHDRシーンを屈折位置から読みます。現在の方式は画面空間で二回の屈折を追跡します。

```text
入射面
  -> 空気から媒質へ屈折
  -> 透明物内部をレイ探索
  -> 射出面と法線を取得
  -> 媒質から空気へ屈折
  -> 不透明物のG-bufferへレイ探索
  -> 背景HDRを取得
  -> Beer-Lambert吸収
  -> 透明物のPBR表面を合成
```

内部を進んだ実光路長とattenuation distanceからBeer-Lambert吸収を求めます。厚い部分ほど強く色を吸収します。

画面空間手法が参照できるのは、画面内に見えている情報です。画面外の情報、見えない裏面、重なった複数体積、多層透明、全反射の内部reflectionは近似の範囲に含めます。背景交点へ到達できなかったレイには、`transmissionRayMissFallback`で`"auto"`、`"environment"`、`"clear"`、`"constant"`のいずれかを選びます。これは観測できない背景を何で表すかを明示する設定です。

**`"auto"`**

必要な入力：なし

背景交点なしの場合：radianceがあれば外向きレイ方向の環境色、なければclear color

入力が不足した場合：clear colorを使う

**`"environment"`**

必要な入力：environment radiance

背景交点なしの場合：外向きレイ方向の環境色

入力が不足した場合：初期化または実行時に例外とする

**`"clear"`**

必要な入力：`renderScene()`のclear color

背景交点なしの場合：clear color

入力が不足した場合：不足する追加入力はない

**`"constant"`**

必要な入力：`transmissionRayMissColor`

背景交点なしの場合：指定した固定色

入力が不足した場合：色がなければ例外とする

`"auto"`は環境のradianceがあれば外向きレイ方向のHDR環境色、なければ`renderScene()`へ渡したclear colorを使います。`"environment"`はradianceを必須とし、存在しない場合はclear colorへ黙って切り替えず例外になります。`"clear"`は常にclear color、`"constant"`は`transmissionRayMissColor`で指定した固定色を使います。clear colorと固定色は表示用sRGBで指定し、線形HDRへ変換してからTransmissionへ合成します。

内部境界を発見できない場合や、1回の内部reflection後の境界でも全反射して外向き方向を決められない場合は、`transmissionRayMissFallback`のmodeで色を選びます。`"constant"`は指定固定色、それ以外のmodeはclear colorまたは環境色を使います。各modeは画面内の情報を使った近似として動作します。

## トーンマッピングで表示へ変換する

PBR照明の結果は線形HDR色として保持し、トーンマッピングでHDRの光量関係を保ちながらディスプレイの表示範囲へ圧縮します。

測光単位系では、EV100による露出を最初に適用します。次にReinhardなどのトーンマッピングを行い、最後に正確なsRGB伝達関数で表示色へ変換します。

露出を上げると、光源そのものだけでなく、拡散光、鏡面反射、発光、環境背景が一緒に明るくなります。マテリアルが暗い問題を露出だけで隠すと、別のマテリアルや背景が白飛びします。調整は、光源、マテリアル、環境、露出の順に役割を分けて行います。

## 処理間で確認する入力と出力

描画内部を調べる際は、各段階が読み書きする座標、深度、色を追います。G-bufferは照明前の表面情報、照明・反射・透明合成は線形HDRの光量、トーンマッピング後は表示用の色を扱います。同じカメラフレームを共有すると、深度から復元する位置と描画した位置が一致します。

効果を並べる全体の順序とその理由は31章、JavaScriptから接続するコードは32章、描画結果を段階ごとに調べる方法は33章で説明します。ここでは、前節までの格納規則と照合して、渡す値の意味が処理間で保たれていることを確認します。

## まとめ

描画処理を組み合わせるときは、座標空間、カメラフレーム、深度規則、色形式、表示変換の位置を一つの基準へ揃えます。カメラ用Reverse-Zとシャドウ用Standard-Z、線形HDRと表示色、G-bufferと最終画像を分けることで、各パスの入力と出力を追跡できます。
物理計算の接触判定や安定化を内部から調べる場合は、42章「物理エンジンの詳細設計」へ進みます。
