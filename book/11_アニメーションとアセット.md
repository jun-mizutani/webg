# アニメーションとアセット

本章では、モデルアセットに含まれるアニメーションクリップを、パターン、アクション、状態へ結び付け、入力に応じて再生するまでの処理をサンプルから確認します。
姿勢が期待どおり切り替わらない場合に、アセット内のキー、再生区間、状態の選択、補間処理のどこを調べるかも整理します。
10章で説明した各層を、実際のアセットへ適用することが本章の目的です。

## この章の読み方

### この章を読む前に必要な知識

08章のModelAssetと10章のAnimationStateを知っていると読みやすくなります。

### 初回に読む範囲

サンプルの操作と表示、N0の区間を選ぶ例、条件評価と入力イベントの使い分けを先に読んでください。

### 必要になったときに読む範囲

startFromTo、startTimeFromTo、キー区間、hand.glbの姿勢対応は、特定アセットを調べるときに参照してください。

### この章を終えた時点でできること

アセットのクリップとキー区間を確認し、補間や再生位置の問題を切り分けられます。

## サンプルからアニメーション制御を理解する

まず`samples/animation_state/index.html`を開き、1〜6キーで希望する姿勢を選びます。HUDの目標状態、現在状態、アクション、パターンを見比べ、選んだ姿勢へ手が動くことを確認してください。次に`samples/janken/index.html`で、入力の瞬間に姿勢を選ぶ方法を確認します。

本章では、`samples/animation_state`と`samples/janken`を使い、GLB（glTFのバイナリ形式）が持つクリップの一部を`Action`として切り出し、`AnimationState`から再生する実践的な流れを確認します。
条件に応じて状態を選ぶ方法と、入力イベントから同じ状態を再始動する方法を比較し、アセットのキー区間をアプリケーションの操作へ結び付けます。

- **samples/animation_state**
  - 選択方法：毎フレームの条件評価
  - 主な入口：`update(context)`
  - 適する用途：目標状態から遷移先を決める
- **samples/janken**
  - 選択方法：入力イベントによるコマンド
  - 主な入口：`setState(..., { force: true })`
  - 適する用途：同じ状態の再始動を含む即時操作

10章で整理した各層を実際のサンプルへ対応付けるため、まずサンプルを操作し、N0の区間を選ぶ例と二つの状態選択方法を比較します。
その後、`samples/gltf_loader/hand.glb`のキー区間と`entryDurationMs`を確認し、アセット、状態選択、補間処理の問題を個別に切り分けます。

## `animation_state` の `N0` を使った具体例

`samples/animation_state` は、`Action` と `AnimationState` の連携を確認できる最短の参照サンプルです。
`main.js` では `hand.glb` のポーズ区間を `pattern` と `action` として登録し、`AnimationState` から `pose0` を開始させています。

```js
const pattern = { id: "N0", fromKey: 12, toKey: 13, entryDurationMs: 250 };
action.addPattern(pattern);
action.addAction(pattern.id, [pattern.id]);
animationState.setState("pose0", {
  context: {
    desiredPoseId,
    nowMs: app.space.now()
  },
  force: true
});
```

ここでは、キー範囲と再生時間を区別します。
`12 -> 13` は `pattern` のキー範囲です。
`250 ms` は、その区間の再生に割り当てる時間です。
`fromKey / toKey` は `clip` のキーを選ぶインデックスであり、`entryDurationMs` はランタイム側の補間時間です。

`animation_state` では、`AnimationState.update()` が内部で `action.play()` まで進めます。
サンプル側は、希望するステートを更新するだけで済みます。

`samples/janken` と `samples/animation_state` は、同じ `pattern` 定義を使います。
`AnimationState` が開始する `action` を選び、移動と回転の補間は `Action` $\rightarrow$ `Animation` $\rightarrow$ `Schedule` $\rightarrow$ `Task` $\rightarrow$ `CoordinateSystem` の順に進みます。

## `startFromTo()`系と`startTimeFromTo()`系

`webg` には、似た名称の `startFromTo()` と `startTimeFromTo()` が存在しますが、その役割は明確に異なります。
簡潔に言えば、`startFromTo()` はクリップのキー区間をそのまま再生する入口であり、`startTimeFromTo()` は現在姿勢から `fromKey` へ遷移するための時間を別途指定する入口です。

`Animation.startFromTo(keyFrom, keyTo)` の実装は以下の通りです。

```js
// キー区間を直接再生する
startFromTo(keyFrom, keyTo) {
  this.setPose(keyFrom);
  this.schedule.startFromTo(keyFrom * 2, keyTo * 2 - 1);
}
```

この動作は非常にシンプルです。
`setPose(keyFrom)` が `fromKey` の姿勢を即座に適用し、`schedule.startFromTo(keyFrom * 2, keyTo * 2 - 1)` が命令列の該当区間を `clip` 側の時間差で進行させます。
例えば `startFromTo(12, 13)` を呼び出した場合、`setPose(12)` の後に `schedule.startFromTo(24, 25)` が呼ばれます。
つまり、12の姿勢に到達した状態から、12 $\rightarrow$ 13の区間を `clip` 本来の時間差で再生します。`fromKey`へ至る区間は、指定されたキー間の補間として扱います。

対して `Animation.startTimeFromTo(time, keyFrom, keyTo)` は、`entryDurationMs` を別途指定することで、現在姿勢から `fromKey` へ至るための補間を先行して生成します。

```js
// 指定した時間でキーへ入り込む
startTimeFromTo(time, keyFrom, keyTo) {
  this.transitionTo(time, keyFrom, keyTo);
}
```

`transitionTo(250, 12, 13)` は、まず各ボーンの `this.poses[i][12]` を収集します。
次に `putRotTransByMatrix` を即時実行し、`doRotTrans` を250 msかけて実行します。
この処理は、現在姿勢からキー12へ移る段階と、キー12 $\rightarrow$ 13の `clip` 区間へ入る段階に分かれます。

`N0`のようなパターンでは、現在の姿勢から指定したキーの姿勢へ移る時間を設けます。この形式を使うと、入力の瞬間から次の姿勢へ向かう動きを、`entryDurationMs`で調整できます。
したがって、`startFromTo()` は `clip` 自体の動作確認に適しており、`startTimeFromTo()` は `idle` $\rightarrow$ `walk` や `rock` $\rightarrow$ `scissors` といった状態遷移に適しています。

## サンプルから見た入口の整理

実際のサンプルにおけるエントリーポイントを整理すると、以下のようになります。

`samples/animation_state/main.js` では、`Action` の `pattern` および `action` を組み立て、サンプル側は `desiredPoseId` を変更するのみとして、制御を `AnimationState` へ委譲しています。
`AnimationState.update()` を通じて、内部的に `Action.start()` と `action.play()` が進行します。

`samples/janken/main.js` では、ユーザー入力に応じて `AnimationState.setState(..., { force: true })` を呼び出し、同様に `Action` へ処理を流します。

以上の整理からわかる通り、サンプルから `startFromTo()` を直接呼び出す場面は限定されます。
`startFromTo()` は `Animation` 内部で `clip` 全体の再生や `Action` が生成したコマンド列を処理するための下位関数です。
開発者が意識すべきは、主に `Action.startPattern()`、`Action.start()`、`AnimationState.setState()` であり、それらが最終的に `startTimeFromTo()` 系へと遷移すると理解しておくのが効率的です。

## `animation_state` と `janken` の読み方

`samples/animation_state` は、glTF（3Dモデル交換形式）版の `hand.glb` を用いて `AnimationState` の条件評価型を確認するためのサンプルです。
サンプル側は目標状態を更新するのみとし、どの `action` を開始するかという判断を `AnimationState` に委譲しています。

もしサンプル側で `Action.start()` を直接呼ぶ構成にした場合、「どの `pattern` / `action` を開始するか」というロジックをサンプルコード自体が明示的に保持することになります。
対して `samples/animation_state` では、サンプル側が `desiredPoseId` を更新し、`AnimationState` が `pose0` から `pose5` のステートを管理し、それぞれに対応する `N0` から `N5` のアクションを開始させます。
この設計の差は、役割分担の考え方の違いです。
前者は「再生対象の選択」までサンプル側で行い、後者は「どの状態を望むか」という意図のみをサンプル側が保持します。
後者のアプローチは、状態遷移の条件を拡張したい場合に非常に整理しやすくなります。

また、本サンプルでは、`1`〜`6` キーで目標状態を変更し、`/` キーで次の目標状態へ進む、`P` キーで自動巡回させる、`@` キーで現在状態を再始動させるといった操作が可能です。
HUD（Head-Up Display：画面上へ重ねる情報表示）には現在状態、ターゲット状態、現在のアクション、現在のパターン、および直近の遷移が表示されるため、「望んだステート」と「実際に動作しているアクション」の相関関係を容易に追跡できます。

一方、`samples/janken` は `AnimationState` のコマンド型利用を確認するためのサンプルです。
この方式は、「入力があった瞬間にその手を出す」という動作へ適しています。入力イベントで次の状態を選び、毎フレームの更新では選んだ動きの再生を進めます。

`samples/animation_state` は、条件評価型の例です。
`desiredPoseId` を毎フレーム更新し、`update(context)` が `transitions` を評価して遷移先を決めます。

`samples/janken` は、コマンド型の例です。
入力イベントごとに `setState(choiceId, { force: true })` を呼び出します。
`update()` は、アクションの進行とステート情報の維持だけを担当します。

この違いは「判断のタイミング」にあります。
前者は「毎フレームの条件」に基づき、後者は「入力イベントそのもの」に基づき判断します。
じゃんけんのようなアプリケーションでは、毎フレーム条件を確認して `rock / scissors / paper` を選ぶよりも、`G`、`C`、`P` の入力を受けた瞬間に即座に反応させることが重要です。
また、同じ手を続けて出し直すケースもあるため、同じステートを `force` 付きで再始動できる仕組みが不可欠です。
したがって `janken` は、`AnimationState` が条件評価型以外でも有効に機能することを示す重要な例となっています。

## 姿勢と再生時間を順に確認する

姿勢を切り替える際は、希望する状態、選ばれたアクション、実際のキー区間、補間に使う時間を順に確認します。`AnimationState`で再生先を選び、`Action`と`Animation`でキー区間と姿勢の変化を扱います。

まずクリップを直接再生して、元の動きを確認します。次に`fromKey / toKey`で選んだ区間と、`entryDurationMs`の時間を確認します。姿勢間の距離が大きい場合は、遷移時間を確保すると途中の動きを見やすくなります。状態の選択はHUDや`getDebugInfo()`で確認し、再開直後の進み方は更新に使う時刻と経過時間を確認します。

この順序で、アセットの姿勢、区間の選び方、状態の判断、時間の進め方を個別に調べられます。後半の内部フローは、公開APIで確認した結果から、ボーンへ適用する計算まで追う際に参照してください。

## `AnimationState` から `Task` までの実フロー

`AnimationState` から実際の移動・回転に至るまでのフローを確認すると、各層の役割分担が明確に分かれていることがわかります。
`AnimationState` は「何を再生するか」を決定し、ボーンの座標値や補間式は下層の`Animation`、`Schedule`、`Task`が担当します。
その下の低水準な層において、再生対象の選択、区間の切り出し、時間補間、そして個々のボーンへの命令実行が順次行われます。

具体的な処理の流れは以下の通りです。

1. `AnimationState.update(context, deltaMs)` が現在のステートを更新し、必要に応じて遷移を選択します。`resolveTransition()` が真を返した場合は `setState()` が呼ばれ、`onExit` の実行、`currentState` の更新、`onEnter` の実行、そして `playStateTarget()` まで処理が進みます。
2. `playStateTarget()` はコントローラーの型に応じて `start()`、`startAction()`、`startAnimation()`、`restartAnimation()` のいずれかを呼び出します。`Action` をコントローラーに渡している場合は、ここで指定した `action` 名の再生が開始されます。
3. `Action.start(actionId, options)` は `action` から最初の `pattern` を取り出し、`currentPattern` を決定した上で `transitionToKey()` を呼び出します。`Action.play()` は、再生中の `pattern` が終了すると次の `pattern` へ進み、必要に応じてループ処理を行います。
4. `transitionToKey(entryDurationMs, fromKey, toKey)` は `Animation.js` の `startTimeFromTo()` を呼び出します。ここで `pattern` の区間と開始時の遷移時間が、実際の補間対象として設定されます。
5. `Animation.startTimeFromTo(time, keyFrom, keyTo)` は `transitionTo()` を呼び出し、`keyFrom` と `keyTo` のポーズを用いて `Schedule` へコマンドを送信します。`putRotTransByMatrix` で開始姿勢を設定し、その後 `doRotTrans` で時間補間を進めます。
6. `Animation.setData(skeleton, bind_shape_matrix)` では、ボーンごとに `Task` を生成し、各キー区間について `[0, putRotTransByMatrix, ...]` と `[time, doRotTrans, [1.0]]` のコマンドペアを登録します。これにより、補間の元となるコマンド列が組み立てられます。
7. `Schedule.directExecution()` は各ボーン用の `Task` に同じコマンドを配分し、`time > 0` の場合は `insertCurrentCommand()` で実行中のコマンド列へ差し込みます。`Schedule.doCommand()` は `delta_msec` を計算し、各 `Task.execute(delta_msec)` を実行します。
8. `Task.execute(delta_msec)` が `remaining_time` を監視しながらコマンドを実行し、`execCommand()` を通じて `CoordinateSystem.prototype.putRotTransByMatrix` や `CoordinateSystem.prototype.doRotTrans` を対象ボーンに対して呼び出します。ここが実際の移動・回転が適用される最終地点となります。

このように層を分離している理由は、ステートマシンと補間実行を切り離すためです。
`AnimationState` を「今どのアニメーションを見せたいか」という決定のみに特化させることで、入力条件やゲームプレイ上の条件変更があっても、補間処理のコードに影響を与えずに済みます。
また、`Task` は「命令を時間軸でどう刻むか」という点に集中しているため、アニメーション以外のコマンド列にも同様の仕組みを流用しやすくなります。

例えば `samples/janken` のようなコマンド駆動型では、入力を受けた瞬間に `setState()` で `action` を出し直し、その `action` が `Animation` と `Task` のコマンド列へと流れます。
一方、`samples/animation_state` のような条件評価型では、毎フレームのコンテキストからステートを選択し、そのステートが下層の `action` を開始させます。
どちらの場合も、実際にボーンを駆動させているのは `Task` です。

デバッグを行う際は、`AnimationState.getDebugInfo()` でステート遷移を確認し、`Action.getActionInfo()` で現在の `action` および `pattern` を確認してください。
さらに `Animation` の `getClipInfo()` や `Task` のコマンド列を追うことで、どの層で意図しない挙動が発生しているかを効率的に切り分けることができます。

## 補足：N0からボーンへの適用を追う

このときの内部的な呼び出し順序は以下の通りです。

1. `AnimationState.setState("pose0")` が `pose0` ステートを `currentState` に設定する。
2. `AnimationState.playStateTarget()` が `state.action === "N0"` を判定し、`Action.start("N0")` を呼び出す。
3. `Action.start("N0")` が先頭 `pattern` として `N0` を選択し、`transitionToKey(250, 12, 13)` を呼び出す。
4. `transitionToKey(250, 12, 13)` が `anim.startTimeFromTo(250, 12, 13)` を呼び出す。
5. `Animation.startTimeFromTo(250, 12, 13)` が `transitionTo(250, 12, 13)` を呼び出す。
6. `transitionTo()` は、各ボーンについて `this.poses[i][12]` を `args` に格納し、`ones` に `1.0` を設定する。
7. `Schedule.directExecution(0, CoordinateSystem.prototype.putRotTransByMatrix, args)` が、各 `Task` に開始姿勢を渡す。
8. `Schedule.directExecution(250, CoordinateSystem.prototype.doRotTrans, ones, 24, 25)` が、各 `Task` に `doRotTrans(1.0)` を250 msかけて流す。
9. `Task.execute(delta_msec)` が毎フレーム呼ばれ、`remaining_time` を減らしながら `doRotTrans(1.0)` を進行させる。
10. `CoordinateSystem.doRotTrans(1.0)` が `execRotation()` と `execTranslation()` を呼び出し、回転は `slerp`、移動は直線補間で反映される。

## `hand.glb` のキー区間と姿勢の対応

ハンド系のサンプルを確認する際、`fromKey / toKey` がどの姿勢を指しているか、また同じ姿勢が複数フレーム続いている理由について混乱することがあります。
本書で使用する`hand.glb`のポーズ保持区間は次のとおりです。別のモデルを使う際は、そのモデルのクリップ情報に合わせて区間を選びます。

| key区間 | 姿勢 | `animation_state` / `janken` のパターン |
| :--- | :--- | :--- |
| 0 | レストポジション | なし |
| 1 | グー | なし |
| 2-3 | 1本伸ばす | `N1: 2 -> 3` |
| 4-5 | チョキ | `N2: 4 -> 5` |
| 6-7 | 3本伸ばす | `N3: 6 -> 7` |
| 8-9 | 4本伸ばす | `N4: 8 -> 9` |
| 10-11 | パー | `N5: 10 -> 11` |
| 12-13 | グー | `N0: 12 -> 13` |

ここで定義されている `fromKey / toKey` は、`Action` がそのポーズを提示するための再生区間です。
`entryDurationMs: 250` は、その区間へ移行する際にランタイム側で0.25秒かけて姿勢を近づける指定です。

同じ姿勢を連続するキーへ置くことで、その姿勢を保持する区間を作れます。
これは、その姿勢を一定時間保持させ、次の姿勢へ移行する直前にバッファを設けることで、再生時の急激な跳ね上がりを抑え、遷移を安定させるためです。
例えば `4-5: チョキ` の場合、4から5の間でチョキの姿勢を保持し、そのポーズをサンプル側のステートから再利用できるようにしています。
連続するキーは、その姿勢の滞在時間を表しています。

この保持区間があることで、入力や目標状態の変化に応じた切り替えが自然に見えるようになり、将来的に `Action` の別の再生方法や `AnimationState` の拡張へ流用しやすくなります。
また、アセット側のキーフレーム構成として「どの姿勢をどのくらいの時間見せるか」を明確に定義できる利点もあります。

BlenderからglTF / GLBを出力する際の注意点についても触れます。
`samples/gltf_loader/hand.glb` のようにglTF / GLBを使用し、アニメーションをキーフレームベースで制御したい場合は、補間モードを`LINEAR`で出力すると、ランタイムのキー区間の補間へ合わせられます。

現在のインポーターは `CUBICSPLINE` を受け取った際、前後のtangentを読み飛ばし、中央の値のみを抽出して `LINEAR` として再生します。
`CUBICSPLINE`の入力も、読み込み後は`LINEAR`のキー列として扱います。元の曲線との違いは、アセットを作る段階で確認します。
そのため、Blenderから出力する際は `Sampling` を無効にし、必要なキーフレームを出力し、補間を `LINEAR` に設定することが最も安全です。
また、アーマチュアにおいて必要なボーン / アクションが適切にキーを持っていることを確認してください。

これらの条件が揃うことで、glTF / GLBを、元のキーフレーム列を保持した状態で扱えます。
`Sampling`を有効にしたり、補間を`CUBICSPLINE`のまま出力したりすると、`gltf_loader`側でtangentが破棄され、`LINEAR`に近似されます。厳密な曲線を再現する場合は、この変換条件を確認します。
現時点の `webg` において、ハンド系のglTFアニメーションは `LINEAR` 前提で考えるのが適切です。

## 参照アセットの識別とクリップ情報

キー番号はモデルごとに決まります。同じ名前のファイルを差し替えた場合は、`getClipInfo()`でクリップ名とキー数を確認してください。本書の姿勢表に対応するファイルを詳しく照合する際は、次の識別情報を使えます。

> **対象データ:** `samples/gltf_loader/hand.glb`のキー番号と姿勢の対応は、SHA-256が`8ae1ba4d9d5dcd170e2c009d8e55c7177ba80d38fcb8a2bdda88670550735c23`であるアセットに対応します。ファイルのハッシュが異なる場合は、次の確認コードでクリップ名とキー数を取得し、本文の表を再確認してください。

```js
const model = await app.loadModel("samples/gltf_loader/hand.glb", {
  format: "gltf",
  instantiate: false
});

for (const clipId of model.asset.getClipNames()) {
  console.log(model.asset.getClipInfo(clipId));
}
```

`getClipInfo()`は、`id`、`targetSkeleton`、`keyCount`、`trackCount`、`durationMs`を返します。
同じファイルかを確認する場合はハッシュを比較し、アセットを更新した場合はこの情報とサンプル側のパターン定義から表を作り直します。


## まとめ

サンプルの操作と表示を確認し、入力、再生対象の選択、キー区間、補間時間を順に対応付けると、アニメーションの使い方を理解できます。
`animation_state` は条件評価型の `AnimationState`、`janken` は入力駆動型の `AnimationState` を扱う実例です。

どのサンプルでも、サンプル側は「何を再生するか」を決定します。
実際の補間とボーンへの反映は、`Animation` $\rightarrow$ `Schedule` $\rightarrow$ `Task` $\rightarrow$ `CoordinateSystem` の流れが担当します。
この分担により、入力処理、状態選択、補間実行を独立して実装できます。

また、本章では `startFromTo()` と `startTimeFromTo()` の違い、`hand.glb` のキー区間の読み方、保持区間の意義、glTF / GLBのエクスポート条件を整理しました。
これらを把握しておくことで、アニメーション付きモデルの挙動に問題が生じた際、「キー区間の問題か」「遷移時間の問題か」「時間基準の問題か」を論理的に切り分けることができます。

続く12章では、これまで扱ってきたHUD、会話表示、パネルといった表示要素を、UI（User Interface：利用者との操作・表示の接点）設計という観点から体系的に整理していきます。
