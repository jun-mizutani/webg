# 高度な画面効果の基礎

本章では、G-buffer、深度、カメラ情報、HDR画像を共有し、複数のコンピュートパスで画面表現を追加する方法を説明します。
SSAOによる接地感、SSRによる反射、シャドウ、フォグ、DoF、ブルームなど、3Dシーンの情報を使う効果を先に扱い、照明後の画像へ適用する輪郭抽出やビネットと区別します。
また、GPU上で状態を更新して直接描画する大量のパーティクルも扱います。
各効果が必要とする入力、出力、実行順、主な負荷を判断できるようになることが本章の目標です。

## この章の読み方

### この章を読む前に必要な知識

21章のコンピュート接続と23章のポストプロセスを知っていると読みやすくなります。

### 初回に読む範囲

色だけのパス、分離ぼかし、画像ピラミッド、G-buffer（照明計算へ渡す画面単位の表面情報）、SSAO（Screen Space Ambient Occlusion：画面空間で求める環境遮蔽）の役割を先に読んでください。

### 必要になったときに読む範囲

カメラフレーム、遅延照明、シャドウ、SSR（Screen Space Reflections：画面空間反射）、フォグ、DoF（Depth of Field：被写界深度）、GPU（Graphics Processing Unit：画像処理装置）パーティクルは必要時に参照してください。

### この章を終えた時点でできること

画面効果を入力データの意味ごとに分け、必要な中間画像と計算量を見積もれます。

## 画面効果をシーン再評価へ広げる

この方法は、完成した色だけでは判断できない三次元的な関係を、画面効果から利用したいときに使います。
23章から25章で扱った色変換やブラーは入力画像の色だけを読んで新しい画像を作れましたが、SSAO（Screen Space Ambient Occlusion：画面空間で求める環境遮蔽）、スクリーンスペース反射、被写界深度、シャドウ評価には、各画素がどの面に属するか、カメラからどれだけ離れているか、表面がどちらを向くか、光をどの程度反射するかという情報が必要です。
これらを共通の中間データとして残せば、効果ごとに`Shape`を描き直したり、別々の基準で位置を推定したりせずに済みます。

`webg`では、この情報をG-bufferへまとめます。
G-bufferは完成画像ではなく、後段の処理が同じ画素を同じ意味で参照するための中間表現です。
通常のカメラ深度はReverse-Z、シャドウマップは通常Zという異なる規約を使うため、単なるテクスチャの集まりではなく、座標、深度、マテリアル、色空間の共通規則として扱う必要があります。

本章では個々のパスが何を入力し、何を出力するかを理解します。
複数の効果を実用的な順序で接続する方法は、31〜33章の`ComputeEffectPipeline`で扱います。

## 4つの前提を先に決めて手戻りを防ぐ

複数のパスを安全につなぐために、見た目の調整より前に、座標、カメラ深度、シャドウ深度、色の4つの意味を揃えます。
ここを最初に決めると、個々のシェーダーが正しくても組み合わせた途端に影が反転する、カメラを回したときだけ反射がずれる、ブルームへ渡す前に強い光が失われる、といった不具合を早い段階で防げます。

- **座標**
  - 基準：G-bufferの法線と位置復元はビュー空間
  - ずれた場合：カメラ回転で影や反射がずれる
- **カメラ深度**
  - 基準：`CAMERA_REVERSE_Z`、`depth32float`、`near`側=1、`far`側=0
  - ずれた場合：背景を物体と誤認する、距離復元が反転する
- **シャドウ深度**
  - 基準：`SHADOW_STANDARD_Z`、`near`側=0、`far`側=1
  - ずれた場合：影判定が全面反転する
- **色**
  - 基準：照明と効果は`rgba16float`、表示直前に`rgba8unorm`
  - ずれた場合：強い光が途中で飽和し、ブルームや反射が失われる

同じ`depth32float`でも、カメラ深度とシャドウ深度の数値の意味は反対です。
形式と深度規約を一組で確認してから処理へ渡します。
コアの各パスは深度規約の同一性を検証し、規約が不明な入力はエラーとして知らせます。

## 色だけのパスを軽量に保つ

ぼかし、ブルーム、トゥーン、ビネットのように色だけから結果を作れる効果は、G-bufferを用意せず、通常のフォワードレンダリング経路をオフスクリーンターゲットへ出力して処理できます。
法線、マテリアル、深度が不要な画面効果では、それらのアタッチメントを省き、メモリ使用量と描画準備を抑えた小さな構成で導入できます。
ブルームとトゥーンは線形HDR色、ビネットはトーンマッピング後の表示色を読むため、深度の要否に加えて入力形式と実行位置も効果ごとに定義します。

一方、フォグとDoF（Depth of Field：被写界深度）は色に加えてカメラ深度を読みます。
SSAO、SSR（Screen Space Reflections：画面空間反射）、形状の境界は深度と法線を読み、遅延ライティングはさらにマテリアルと可視性を必要とします。
必要な情報の範囲に応じて描画経路を選ぶことが、リソースの無駄と前提条件の混同を防ぎます。

### 分離ぼかしで参照を減らす

ぼかしは、被写界深度のボケ、ブルームの光の広がり、背景を曖昧にする演出など、近くの画素を混ぜて細部を弱めたいときに使います。
`ComputeBlurPass`は2次元のぼかしを水平方向と垂直方向に分けるため、広い範囲をぼかしても参照数を抑えられます。
半径$r$の正方形カーネルをそのまま評価すると、1画素あたり$(2r+1)^2$回の参照が必要ですが、水平と垂直に分ければ$2(2r+1)$回で済み、半径が大きいほど差が広がります。

```js
import ComputeBlurPass from "./webg/ComputeBlurPass.js";

const blurPass = new ComputeBlurPass(app.getGPU(), {
  label: "main-blur",
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await blurPass.ready;

app.getGPU().endPass();
const blurredColor = blurPass.encode(
  app.getGPU().commandEncoder,
  hdrSceneTarget,
  {
    radius: 3,
    iterations: 2
  }
);
```

入力と出力は`rgba16float`で、寸法も一致している必要があります。
`radius`は1方向の参照範囲、`iterations`は水平・垂直の組を何回反復するかを表します。
半径を増やすと参照数が増え、反復を増やすとディスパッチ回数が増えるため、見た目とGPU時間を両方確認して決めます。

### 画像ピラミッドで広いぼかしを作る

`ComputePyramidBlurPass`は、線形HDR画像を1/2、1/4、1/8、1/16へ連続して縮小し、1/16から元の解像度へ段階的に拡大します。
各縮小処理は13点の低域通過フィルター、各拡大処理は9点のテントフィルターを使います。
途中の段階を飛ばさずに処理するため、低い解像度で広い範囲へ到達しながら、離れた画素だけを直接読む間引きを避けられます。

```js
import ComputePyramidBlurPass from "./webg/ComputePyramidBlurPass.js";

const pyramidBlurPass = new ComputePyramidBlurPass(app.getGPU(), {
  label: "main-pyramid-blur",
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await pyramidBlurPass.ready;

app.getGPU().endPass();
const blurredColor = pyramidBlurPass.encode(
  app.getGPU().commandEncoder,
  hdrSceneTarget,
  {
    filterRadius: 1.0
  }
);
```

入力と出力の形式は`rgba16float`です。
既定の段階は`[2, 4, 8, 16]`で、1/16の低周波画像だけを1/8、1/4、1/2、元の解像度へ順番に拡大します。
途中の段階の色を加算せずにぼかしを再構成するため、光量を保ったまま出力できます。
`filterRadius`は縮小時と拡大時のサンプル間隔を表し、既定値は`1.0`、設定範囲は`0.25`から`3.0`です。
値を大きくしても段階数とディスパッチ回数は変わりませんが、各フィルターが参照する範囲が広がります。

`ComputeBlurPass`は元の解像度で水平方向と垂直方向のぼかしを反復したい場合に使います。
`ComputePyramidBlurPass`は低解像度の段階を利用して広いぼかしを作りたい場合に使います。

### 画像ピラミッドでブルームを構成する

ブルームは、発光体、照明の反射、非常に明るい空などが周囲へ光をにじませる見え方を加えるために使います。
明るい画素だけを抽出して元のシーン色へ重ねるため、暗部の細部を保ったまま、HDR画像に残された光量差を視覚的な広がりとして伝えられます。

`ComputeBloomPass`は、最初に元の解像度のHDRシーンへしきい値を一度だけ適用します。
抽出した光を`ComputeImagePyramid`で1/2、1/4、1/8、1/16、1/32へ順番に縮小し、最も低い解像度の段階から順に拡大します。
各段階の寄与を個別の重みで加えるため、光源付近の強いにじみと、遠くまで届く弱い光芒を一つの連続した画像として構成できます。

```text
線形HDRシーン
  -> `threshold`と`softKnee`で高輝度成分を抽出
  -> 1/2、1/4、1/8、1/16、1/32へ順番に縮小
  -> 1/32から元の解像度へ、重みを付けながら段階的に拡大
  -> `strength`を掛けて元の線形HDRシーンへ加算
```

```js
import ComputeBloomPass from "./webg/ComputeBloomPass.js";

const bloomPass = new ComputeBloomPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await bloomPass.ready;

const bloomedColor = bloomPass.encode(
  app.getGPU().commandEncoder,
  hdrSceneTarget,
  {
    threshold: 0.60,
    softKnee: 0.40,
    strength: 0.70,
    halfWeight: 0.45,
    quarterWeight: 0.28,
    eighthWeight: 0.17,
    sixteenthWeight: 0.10,
    thirtySecondWeight: 0.18,
    filterRadius: 1.00,
    enabled: true
  }
);
```

この例は`COMPUTE_BLOOM_DEFAULTS`と同じ値です。
各設定の意味は次のとおりです。

- `threshold`の既定値は`0.60`です。ブルームへ入れ始める線形HDR輝度を
  指定します。範囲は0.0から4.0で、1.0を超えるHDR値も指定できます。
- `softKnee`の既定値は`0.40`です。`threshold`付近で抽出量を滑らかに
  立ち上げる割合です。範囲は0.0から1.0で、0.0では境界が急になります。
- `strength`の既定値は`0.70`です。再構成したブルーム全体を元のシーンへ
  加える量です。範囲は0.0から4.0です。
- `halfWeight`の既定値は`0.45`です。1/2段階が表す光源近傍の成分を
  調整します。
- `quarterWeight`の既定値は`0.28`です。1/4段階の中距離成分を
  調整します。
- `eighthWeight`の既定値は`0.17`です。1/8段階の広い成分を
  調整します。
- `sixteenthWeight`の既定値は`0.10`です。1/16段階のさらに広い
  成分を調整します。
- `thirtySecondWeight`の既定値は`0.18`です。1/32段階が作る
  最も外側の弱い光芒を調整します。
- `filterRadius`の既定値は`1.00`です。段階的な拡大で使う
  テントフィルターの間隔を、拡大元の低解像度画像の画素単位で
  指定します。範囲は0.25から3.0です。
- `enabled`の既定値は`true`です。直接`ComputeBloomPass.encode()`を
  呼ぶ場合に、再構成したブルームを最終出力へ加えるかを指定します。

各段階の重みの範囲は、それぞれ0.0から4.0です。
重みは指定値をそのまま使います。合計を揃える場合は、利用側で正規化した値を渡します。
既定値では1/2から1/16までの合計を1.0とし、その外側へ1/32の0.18を追加しています。
近くのにじみを強くしたい場合は高解像度側、遠い光芒を強くしたい場合は低解像度側を少しずつ変更し、最後に`strength`で全体量を整えます。

`threshold`は0から1に正規化された表示色ではなく、トーンマッピング前の線形HDR輝度に対するしきい値です。
実装はRGBの輝度と最大成分を組み合わせて明るさを求め、しきい値を超えた割合だけ元のRGBをブルームの入力画像へ残します。
このため色相を保ったまま、しきい値付近の寄与を連続的に変えられます。

調整は`threshold`と`softKnee`で対象を決め、各段階の重みで広がりの形を決め、`filterRadius`で段階間の滑らかさを整え、最後に`strength`で加算量を決める順が分かりやすくなります。
これらの値は画像ピラミッドの段階数とディスパッチ回数を固定したまま、対象、広がり、滑らかさを調整します。
処理自体を省略したい場合は、`ComputeEffectPipeline`の`bloomEnabled`を`false`にします。

ブルームはトーンマッピング前の`rgba16float` HDRシーンに対して行います。
`rgba8unorm`へ変換すると1.0を超える光量差が圧縮されます。強い発光と白いマテリアルを区別するには、HDR区間を`rgba16float`で保持します。
最終表示用の露出はブルームの設定へ混ぜず、後段のトーンマッピングで一度だけ適用します。

## G-bufferで表面情報を一度だけ記録する

G-bufferは、同じ表面情報をSSAO、シャドウ、遅延ライティング、SSRなどから再利用するために使います。
`GeometryBufferPass`で不透明なShapeを一度描画して、照明前の色、法線、マテリアル、深度を同じ画素位置へ保存すれば、後段の効果ごとにジオメトリを描き直さず、しかもすべての効果が同じ時点の表面を参照できます。

ここでいう「不透明」とは、表面の奥にある形状を透かして表示せず、1画素に最も手前の1枚の表面情報を保存できるShapeのことです。
ガラスや半透明の粒子のように手前と奥の色を合成する表面は、透明Forward描画などの別経路で表現します。1組のG-buffer値は不透明表面の情報に使います。
そのような表現は、不透明表面を遅延照明した後にフォワードレンダリング経路で合成するなど、別の描画経路として設計します。

| アタッチメント | 形式 | 内容 |
| --- | --- | --- |
| アルベド | `rgba8unorm-srgb` | 照明前の基本色 |
| 法線 | `rgba8unorm` | ビュー空間法線を0〜1へ符号化した値 |
| マテリアル | `rgba8unorm` | specular、roughness、metallic、occlusion |
| 発光 | `rgba16float` | 線形HDRのemissive color |
| 深度 | `depth32float` | カメラ用Reverse-Z深度 |

アルベドは照明前の基本色としてG-bufferへ保存し、照明済みの色は遅延照明の出力へ分けます。
遅延ライティングがアルベドと表面マテリアルを一度だけ評価し、その後の効果へHDRシーン色を渡します。
この分離によって、SSAOは環境光の可視性、シャドウは直接光の可視性、SSRは反射成分として独立して扱えます。

4つのアタッチメントは同じ幅、高さ、同じカメラ、同じ描画時点で作ります。
例えば法線を前フレームから持ち越すと、各画素の深度が表す面と法線が表す面にずれが生じます。G-bufferの各成分を同じフレームで生成します。
G-bufferは4枚の独立した画像ではなく、同じ表面を説明する1組のひとまとまりの記録として扱います。

### 背景色をアプリケーションで指定する

G-bufferに形状が描かれなかった画素にも、最終画像へ渡す背景色が必要です。
`GeometryBufferPass.renderSpace()`へ渡す`clearColor`は、通常描画と同じ表示用sRGB色として解釈されます。
パスはこの値を線形色へ変換して、`rgba8unorm-srgb`のアルベドアタッチメントをクリアします。
アタッチメントは保存時にsRGBで符号化し、後段のシェーダーから読むときは線形色へ復号するため、形状のアルベドと背景の両方が同じ線形色として遅延ライティングへ届きます。

`DeferredLightingPass`はReverse-Z深度が0の画素を未描画の背景と判定します。
背景ではビュー空間位置を復元せず、AO、シャドウ、ローカルライトを評価せずに、クリア色をHDR出力へ引き継ぎます。
代わりにG-bufferのアルベドをそのまま線形HDR出力へ渡します。
この設計により、遅延ライティングが固定の青灰色やグラデーションを勝手に選ばず、背景色の決定を`clearColor`を指定したアプリケーションへ残せます。

`clearColor`は表示用sRGB色として解釈され、照明計算用の線形色へ変換されてから最終画面へ渡ります。
背景も形状と同じ線形HDR経路を通り、最後に露出、トーンマッピング、sRGB変換、彩度調整を受けます。
`mode: "reinhard"`では1未満の値も圧縮されるため、指定色より暗く見えることがあります。
照明モデルやマテリアル色を数値に近い状態で比較する場合は`mode: "linear"`を使い、0から1へ切り詰めた後のsRGB表示を確認します。
空、環境マップ、独自のグラデーションが必要な場合は、固定背景を遅延ライティングへ組み込むのではなく、アプリケーション側の背景描画または合成処理として追加します。

### ビュー空間法線で画面効果の座標を揃える

ビュー空間法線は、画面上の深度から復元した位置と、法線を使う効果の座標基準を揃えるために使います。
画面空間のエフェクトはカメラの奥行き方向と画面の水平・垂直方向を基準にするため、G-bufferの法線もビュー空間にすると、追加の座標変換を挟まずに内積や反射方向を計算できます。
ワールド空間法線を混ぜると、カメラを回転したときに照明、AO（Ambient Occlusion：環境遮蔽）、SSRの方向が画面に対してずれます。

法線は各成分が-1から1の範囲を取りますが、アタッチメントは`rgba8unorm`なので0から1へ符号化して保存します。
診断表示の色は実際のマテリアル色ではなく、法線のXYZ成分をRGBで見せたものです。
平らな面の色がカメラ回転に応じて連続的に変わることが、ビュー空間の動作確認になります。

### マテリアル値をそろえ照明結果を予測する

マテリアル値は、光沢、粗さ、金属らしさ、環境遮蔽を照明式へ正確に伝え、Shapeごとの見え方を予測可能にするために使います。発光は8 bitのmaterial attachmentへ詰めず、独立した`rgba16float` attachmentへ保存します。
G-bufferを使うShapeでは`roughness`や`metallic`を明示し、照明計算が読む表面情報をそろえます。
省略値を暗黙に補わず、入力漏れをその場で検出することで、設定不足が「それらしいが意図と異なるマテリアル」として残るのを防ぎます。

```js
shape.setMaterial("smooth-shader", {
  has_bone: 0,
  use_texture: 0,
  color: [0.18, 0.62, 0.88, 1.0],
  ambient: 0.0,
  specular: 0.72,
  roughness: 0.20,
  metallic: 0.12,
  power: 48.0,
  emissive: 0.0
});
```

`color`のアルファは色の一部として扱い、反射特性は表面アタッチメントの`specular`、`roughness`、`metallic`へ分けます。
この区別を保つと、反射率、透明度、基本色をそれぞれ独立した意味で調整できます。

## カメラフレームで視点を揃える

カメラフレームは、G-bufferを描くパスと、その深度から位置を復元するコンピュートパスに、同じ瞬間の視点と投影を共有させるために使います。
一つのフレームオブジェクトを受け渡すことで、カメラが動く場面でも、法線、深度、AO、反射、フォグ、照明が画素単位で一致し、パスごとに`near`、`far`、画角、行列を組み直す手間と取り違えを避けられます。

Reverse-Zの深度値だけから距離を復元するには、その深度を作ったnear、far、画角、アスペクト比が必要です。
カメラ位置だけを後から読み直すと、G-buffer生成時の投影との一致を確認しにくくなります。生成時の`cameraFrame`を後段へ共有します。

`WebgApp`は描画直前に完全な`cameraFrame`を確定し、`onBeforeDraw`と`onAfterDraw3d`へ同じオブジェクトを渡します。
個別のG-buffer系パスでは、この同じオブジェクトを描画とコンピュートの両方へ渡します。

```js
app.start({
  onBeforeDraw: ({ cameraFrame }) => {
    gbuffer.renderSpace(app.space, cameraFrame, app.clearColor);
  },

  onAfterDraw3d: ({ cameraFrame }) => {
    app.getGPU().endPass();
    const ao = ssaoPass.encode(
      app.getGPU().commandEncoder,
      gbuffer.getBindingResources(),
      { cameraFrame, enabled: true }
    );
  }
});
```

ここでは、利用側が受け取った`cameraFrame`をそのまま`SsaoPass`へ渡します。`SsaoPass`はそのフレームから投影パラメータを作り、カメラ用Reverse-Zであることを検証します。
near、far、画角、eyeのワールド行列を個別に再構成すると、G-bufferを作った時点と異なるカメラ状態を混入させる余地が生まれます。

## SSAOで接地感と隅の奥行きを補う

SSAOは、物体同士の接触部、壁と床の境目、形状の入り組んだ隅などへ、周囲から届く光が減る様子を加えるために使います。
シャドウマップでは表しにくい局所的な遮蔽を、すでに作成したG-bufferの法線と深度から近似できるため、ジオメトリを別の視点から描き直さずに接地感と奥行きの手掛かりを補えます。

SSAOが返すのは完成したシーン色ではなく、0から1の環境遮蔽の可視率です。
1は遮蔽なし、0へ近づくほど環境光が届きにくいことを表します。
色と分離しておくと、マテリアル色や直接光を暗くせず、遅延ライティングで環境光の成分だけへ作用させられます。

```js
import { GeometryBufferPass } from "./webg/GeometryBufferPass.js";
import SsaoPass from "./webg/SsaoPass.js";

const gbuffer = new GeometryBufferPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  colorMode: "material",
  normalSpace: "view"
});

const ssaoPass = new SsaoPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  radius: 22,
  strength: 1.55,
  bias: 0.045,
  samples: 12,
  resolutionScale: 0.7
});

await Promise.all([gbuffer.ready, ssaoPass.ready]);
```

`radius`は画面上の探索半径、`strength`は遮蔽の強さ、`bias`は同じ面を自己遮蔽として数えないための許容値、`samples`は探索方向数です。
`resolutionScale`はAOの計算だけを低解像度化し、最終可視率は法線と深度を使うbilateral処理でフル解像度へ戻します。

SSAOの各画素では、まずカメラ用Reverse-Z深度をカメラフレームのnear、far、画角、アスペクト比で復元し、ビュー空間の表面位置を得ます。
その周囲を複数方向に参照し、中心の法線と参照先の奥行きから、環境光を遮る形状があるかを近似します。
画面の深度から得られるのはカメラから見える最前面です。SSAOはこの可視面を入力に、物体の裏側や画面外の遮蔽を含まない画面空間の近似として計算します。

低解像度のAOを単に線形拡大すると、手前の物体の暗さが奥の背景へ滲みます。
bilateral処理は、近い画素でも深度差が大きい場合や法線が大きく異なる場合に重みを下げます。
これにより、低解像度化したAOを物体の輪郭を越えにくい形でフル解像度へ戻せます。
倍率を下げすぎると元のAOサンプルが欠けるため、後段の拡大で補える情報量も減ります。低解像度化と品質のバランスを実測します。

SSAO単体を学習用に表示する場合は、返された可視率テクスチャを`FullscreenPass`へ渡します。

```js
onAfterDraw3d: ({ cameraFrame }) => {
  const gpu = app.getGPU();
  gpu.endPass();

  const aoVisibility = ssaoPass.encode(
    gpu.commandEncoder,
    gbuffer.getBindingResources(),
    {
      cameraFrame,
      enabled: true,
      radius: 22,
      strength: 1.55,
      bias: 0.045,
      samples: 12
    }
  );

  app.screen.beginPresentPass({
    clearColor: app.clearColor,
    colorLoadOp: "clear"
  });
  copyPass.draw(aoVisibility);
  app.screen.clearDepthBuffer();
}
```

色との合成はSSAOではなく、遅延ライティングが環境光成分へ可視率を適用する段階で行います。
SSAOの診断オプションは遮蔽計算の入力と結果を対象にし、完成色の表示は後段の合成結果として確認します。
完成テクスチャをキャンバスへ転送するときは深度なしの`beginPresentPass()`を使い、後続の `Font` やHUD（Head-Up Display：画面上へ重ねる情報表示）のために`clearDepthBuffer()`でReverse-Z深度付きパスを再開します。

実行可能な全体例は`examples/34_01.html`で確認できます。
既定表示はAO可視率そのものではなく、G-bufferから求めたAOを遅延ライティングの環境光へ適用し、トーンマッピングまで終えた完成画像です。
AキーでSSAOの有無を比較できるため、物体の色と直接光を保ったまま、隅や接地部に対するAOの作用を観察できます。

AO可視率だけを調べたい場合はVキーで診断表示へ切り替えます。
このとき白は遮蔽なし、暗い部分は環境光が届きにくい領域です。
診断画像を既定の完成画像にせず明示操作へ分けることで、SSAOの出力と遅延ライティング後のシーン色を混同せずに確認できます。

## まとめ

高度な画面効果は、完成色だけでなくG-buffer、深度、法線、カメラ情報、HDRシーンなどの中間データを読みます。必要な入力を明確にし、単独パスの出力と統合後の完成画像を分けて確認すると、座標や色形式の不一致を早く見つけられます。
照明、シャドウ、SSR、フォグの個別処理は続く35章で、DoF、画風、GPUパーティクルは36章で詳しく扱います。
