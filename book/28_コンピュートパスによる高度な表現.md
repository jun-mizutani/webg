# コンピュートパスによる高度な表現

本章では、画面上の色を整えるだけでは作れない、接地感、反射、影、距離による霧、焦点、発光の広がり、大量の粒子といった表現を組み立てます。
また、照明計算が終わった表示画像へ輪郭やビネットを適用し、最終画面の見せ方を整える方法も扱います。
複数の効果が同じシーン情報を共有するように設計すると、効果ごとにシーンを描き直さずに済み、見た目の追加と描画負荷の管理を両立しやすくなります。
そのために必要なG-buffer、カメラフレーム、可視性、HDR（High Dynamic Range：広い輝度範囲）、深度規約の役割を、効果ごとの利用目的から順に説明します。

## 画面効果をシーン再評価へ広げる

この方法は、完成した色だけでは判断できない三次元的な関係を、画面効果から利用したいときに使います。
前章の色変換やブラーは入力画像の色だけを読んで新しい画像を作れましたが、SSAO（Screen Space Ambient Occlusion：画面空間で求める環境遮蔽）、スクリーンスペース反射、被写界深度、シャドウ評価には、各画素がどの面に属するか、カメラからどれだけ離れているか、表面がどちらを向くか、光をどの程度反射するかという情報が必要です。
これらを共通の中間データとして残せば、効果ごとに`Shape`を描き直したり、別々の基準で位置を推定したりせずに済みます。

`webg`では、この情報をG-bufferへまとめます。
G-bufferは完成画像ではなく、後段の処理が同じ画素を同じ意味で参照するための中間表現です。
通常のカメラ深度はReverse-Z、シャドウマップは通常Zという異なる規約を使うため、単なるテクスチャの集まりではなく、座標、深度、材質、色空間の共通規則として扱う必要があります。

本章では個々のパスが何を入力し、何を出力するかを理解します。
複数の効果を実用的な順序で接続する方法は、第29章の`ComputeEffectPipeline`で扱います。

## 4つの前提を先に決めて手戻りを防ぐ

複数のパスを安全につなぐために、見た目の調整より前に、座標、カメラ深度、シャドウ深度、色の4つの意味を揃えます。
ここを最初に決めると、個々のシェーダーが正しくても組み合わせた途端に影が反転する、カメラを回したときだけ反射がずれる、ブルームへ渡す前に強い光が失われる、といった不具合を早い段階で防げます。

- **座標**
  - 基準：G-bufferの法線と位置復元はビュー空間
  - ずれた場合：カメラ回転で影や反射がずれる
- **カメラ深度**
  - 基準：`CAMERA_REVERSE_Z`、`depth32float`、`near`側=1、`far`側=0
  - ずれた場合：背景を物体と誤認する、距離復元が反転する
- **シャドウ深度**
  - 基準：`SHADOW_STANDARD_Z`、`near`側=0、`far`側=1
  - ずれた場合：影判定が全面反転する
- **色**
  - 基準：照明と効果は`rgba16float`、表示直前に`rgba8unorm`
  - ずれた場合：強い光が途中で飽和し、ブルームや反射が失われる

同じ`depth32float`でも、カメラ深度とシャドウ深度の数値の意味は反対です。
形式だけを見て同じ処理へ渡してはいけません。
コアの各パスは深度規約の同一性を検証し、規約が不明な入力を通常Zなどへ読み替えません。

## 色だけのパスを軽量に保つ

ぼかし、ブルーム、トゥーン、ビネットのように色だけから結果を作れる効果は、G-bufferを用意せず、通常のフォワードレンダリング経路をオフスクリーンターゲットへ出力して処理できます。
必要のない法線、材質、深度のアタッチメントを作らないため、メモリ使用量と描画準備を抑えられ、単純な画面効果を小さな構成で導入できます。
ただし、ブルームとトゥーンは線形HDR色、ビネットはトーンマッピング後の表示色を読むため、深度が不要でも入力形式と実行位置は同じではありません。

一方、フォグとDoF（Depth of Field：被写界深度）は色に加えてカメラ深度を読みます。
SSAO、SSR（Screen Space Reflections：画面空間反射）、形状の境界は深度と法線を読み、遅延ライティングはさらに材質と可視性を必要とします。
必要な情報の範囲に応じて描画経路を選ぶことが、リソースの無駄と前提条件の混同を防ぎます。

### 分離ぼかしで参照を減らす

ぼかしは、被写界深度のボケ、ブルームの光の広がり、背景を曖昧にする演出など、近くの画素を混ぜて細部を弱めたいときに使います。
`ComputeBlurPass`は2次元のぼかしを水平方向と垂直方向に分けるため、広い範囲をぼかしても参照数を抑えられます。
半径$r$の正方形カーネルをそのまま評価すると、1画素あたり$(2r+1)^2$回の参照が必要ですが、水平と垂直に分ければ$2(2r+1)$回で済み、半径が大きいほど差が広がります。

```js
import ComputeBlurPass from "./webg/ComputeBlurPass.js";

const blurPass = new ComputeBlurPass(app.getGPU(), {
  label: "main-blur",
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await blurPass.ready;

app.getGPU().endPass();
const blurredColor = blurPass.encode(
  app.getGPU().commandEncoder,
  hdrSceneTarget,
  {
    radius: 3,
    iterations: 2
  }
);
```

入力と出力は`rgba16float`で、寸法も一致している必要があります。
`radius`は1方向の参照範囲、`iterations`は水平・垂直の組を何回反復するかを表します。
半径を増やすと参照数が増え、反復を増やすとディスパッチ回数が増えるため、見た目とGPU時間を両方確認して決めます。

### 画像ピラミッドで広いぼかしを作る

`ComputePyramidBlurPass`は、線形HDR画像を1/2、1/4、1/8、1/16へ連続して縮小し、1/16から元の解像度へ段階的に拡大します。
各縮小処理は13点の低域通過フィルター、各拡大処理は9点のテントフィルターを使います。
途中の段階を飛ばさずに処理するため、低い解像度で広い範囲へ到達しながら、離れた画素だけを直接読む間引きを避けられます。

```js
import ComputePyramidBlurPass from "./webg/ComputePyramidBlurPass.js";

const pyramidBlurPass = new ComputePyramidBlurPass(app.getGPU(), {
  label: "main-pyramid-blur",
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await pyramidBlurPass.ready;

app.getGPU().endPass();
const blurredColor = pyramidBlurPass.encode(
  app.getGPU().commandEncoder,
  hdrSceneTarget,
  {
    filterRadius: 1.0
  }
);
```

入力と出力の形式は`rgba16float`です。
既定の段階は`[2, 4, 8, 16]`で、1/16の低周波画像だけを1/8、1/4、1/2、元の解像度へ順番に拡大します。
途中の段階の色を加算しないため、ぼかしの再構成によって光量は増えません。
`filterRadius`は縮小時と拡大時のサンプル間隔を表し、既定値は`1.0`、設定範囲は`0.25`から`3.0`です。
値を大きくしても段階数とディスパッチ回数は変わりませんが、各フィルターが参照する範囲が広がります。

`ComputeBlurPass`は元の解像度で水平方向と垂直方向のぼかしを反復したい場合に使います。
`ComputePyramidBlurPass`は低解像度の段階を利用して広いぼかしを作りたい場合に使います。

### 画像ピラミッドでブルームを構成する

ブルームは、発光体、照明の反射、非常に明るい空などが周囲へ光をにじませる見え方を加えるために使います。
明るい画素だけを抽出して元のシーン色へ重ねるため、暗部の細部を保ったまま、HDR画像に残された光量差を視覚的な広がりとして伝えられます。

`ComputeBloomPass`は、最初に元の解像度のHDRシーンへしきい値を一度だけ適用します。
抽出した光を`ComputeImagePyramid`で1/2、1/4、1/8、1/16、1/32へ順番に縮小し、最も低い解像度の段階から順に拡大します。
各段階の寄与を個別の重みで加えるため、光源付近の強いにじみと、遠くまで届く弱い光芒を一つの連続した画像として構成できます。

```text
線形HDRシーン
  -> `threshold`と`softKnee`で高輝度成分を抽出
  -> 1/2、1/4、1/8、1/16、1/32へ順番に縮小
  -> 1/32から元の解像度へ、重みを付けながら段階的に拡大
  -> `strength`を掛けて元の線形HDRシーンへ加算
```

```js
import ComputeBloomPass from "./webg/ComputeBloomPass.js";

const bloomPass = new ComputeBloomPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await bloomPass.ready;

const bloomedColor = bloomPass.encode(
  app.getGPU().commandEncoder,
  hdrSceneTarget,
  {
    threshold: 0.60,
    softKnee: 0.40,
    strength: 0.70,
    halfWeight: 0.45,
    quarterWeight: 0.28,
    eighthWeight: 0.17,
    sixteenthWeight: 0.10,
    thirtySecondWeight: 0.18,
    filterRadius: 1.00,
    enabled: true
  }
);
```

この例は`COMPUTE_BLOOM_DEFAULTS`と同じ値です。
各設定の意味は次のとおりです。

- `threshold`の既定値は`0.60`です。ブルームへ入れ始める線形HDR輝度を
  指定します。範囲は0.0から4.0で、1.0を超えるHDR値も指定できます。
- `softKnee`の既定値は`0.40`です。`threshold`付近で抽出量を滑らかに
  立ち上げる割合です。範囲は0.0から1.0で、0.0では境界が急になります。
- `strength`の既定値は`0.70`です。再構成したブルーム全体を元のシーンへ
  加える量です。範囲は0.0から4.0です。
- `halfWeight`の既定値は`0.45`です。1/2段階が表す光源近傍の成分を
  調整します。
- `quarterWeight`の既定値は`0.28`です。1/4段階の中距離成分を
  調整します。
- `eighthWeight`の既定値は`0.17`です。1/8段階の広い成分を
  調整します。
- `sixteenthWeight`の既定値は`0.10`です。1/16段階のさらに広い
  成分を調整します。
- `thirtySecondWeight`の既定値は`0.18`です。1/32段階が作る
  最も外側の弱い光芒を調整します。
- `filterRadius`の既定値は`1.00`です。段階的な拡大で使う
  テントフィルターの間隔を、拡大元の低解像度画像の画素単位で
  指定します。範囲は0.25から3.0です。
- `enabled`の既定値は`true`です。直接`ComputeBloomPass.encode()`を
  呼ぶ場合に、再構成したブルームを最終出力へ加えるかを指定します。

各段階の重みの範囲は、それぞれ0.0から4.0です。
重みは自動的に正規化されません。
既定値では1/2から1/16までの合計を1.0とし、その外側へ1/32の0.18を追加しています。
近くのにじみを強くしたい場合は高解像度側、遠い光芒を強くしたい場合は低解像度側を少しずつ変更し、最後に`strength`で全体量を整えます。

`threshold`は0から1に正規化された表示色ではなく、トーンマッピング前の線形HDR輝度に対するしきい値です。
実装はRGBの輝度と最大成分を組み合わせて明るさを求め、しきい値を超えた割合だけ元のRGBをブルームの入力画像へ残します。
このため色相を保ったまま、しきい値付近の寄与を連続的に変えられます。

調整は`threshold`と`softKnee`で対象を決め、各段階の重みで広がりの形を決め、`filterRadius`で段階間の滑らかさを整え、最後に`strength`で加算量を決める順が分かりやすくなります。
これらの値を変えても画像ピラミッドの段階数とディスパッチ回数は変わりません。
処理自体を省略したい場合は、`ComputeEffectPipeline`の`bloomEnabled`を`false`にします。

ブルームはトーンマッピング前の`rgba16float` HDRシーンに対して行います。
`rgba8unorm`へ変換した後では、1.0を超える光量差が失われ、強い発光と白い材質を区別できません。
最終表示用の露出はブルームの設定へ混ぜず、後段のトーンマッピングで一度だけ適用します。

## G-bufferで表面情報を一度だけ記録する

G-bufferは、同じ表面情報をSSAO、シャドウ、遅延ライティング、SSRなどから再利用するために使います。
`GeometryBufferPass`で不透明なShapeを一度描画して、照明前の色、法線、材質、深度を同じ画素位置へ保存すれば、後段の効果ごとにジオメトリを描き直さず、しかもすべての効果が同じ時点の表面を参照できます。

ここでいう「不透明」とは、表面の奥にある形状を透かして表示せず、1画素に最も手前の1枚の表面情報を保存できるShapeのことです。
ガラスや半透明の粒子のように、手前と奥の色を合成する必要がある表面は、1組のG-buffer値だけでは表せません。
そのような表現は、不透明表面を遅延照明した後にフォワードレンダリング経路で合成するなど、別の描画経路として設計します。

| アタッチメント | 形式 | 内容 |
| --- | --- | --- |
| アルベド | `rgba8unorm-srgb` | 照明前の基本色 |
| 法線 | `rgba8unorm` | ビュー空間法線を0〜1へ符号化した値 |
| マテリアル | `rgba8unorm` | specular、roughness、metallic、emissive |
| 深度 | `depth32float` | カメラ用Reverse-Z深度 |

照明済みの色をアルベドへ焼き込む経路はありません。
遅延ライティングがアルベドと表面マテリアルを一度だけ評価し、その後の効果へHDRシーン色を渡します。
この分離によって、SSAOは環境光の可視性、シャドウは直接光の可視性、SSRは反射成分として独立して扱えます。

4つのアタッチメントは同じ幅、高さ、同じカメラ、同じ描画時点で作ります。
例えば法線だけ前フレームのものを残すと、各画素の深度が表す面と法線が表す面が一致しません。
G-bufferは4枚の独立した画像ではなく、同じ表面を説明する1組のひとまとまりの記録として扱います。

### 背景色をアプリケーションで指定する

G-bufferに形状が描かれなかった画素にも、最終画像へ渡す背景色が必要です。
`GeometryBufferPass.renderSpace()`へ渡す`clearColor`は、通常描画と同じ表示用sRGB色として解釈されます。
パスはこの値を線形色へ変換して、`rgba8unorm-srgb`のアルベドアタッチメントをクリアします。
アタッチメントは保存時にsRGBで符号化し、後段のシェーダーから読むときは線形色へ復号するため、形状のアルベドと背景の両方が同じ線形色として遅延ライティングへ届きます。

`DeferredLightingPass`はReverse-Z深度が0の画素を未描画の背景と判定します。
背景ではビュー空間位置を復元せず、AO、シャドウ、ローカルライトも評価しません。
代わりにG-bufferのアルベドをそのまま線形HDR出力へ渡します。
この設計により、遅延ライティングが固定の青灰色やグラデーションを勝手に選ばず、背景色の決定を`clearColor`を指定したアプリケーションへ残せます。

ただし、`clearColor`の数値が最終画面へ無変換でコピーされるわけではありません。
背景も形状と同じ線形HDR経路を通り、最後に露出、トーンマッピング、sRGB変換、彩度調整を受けます。
`mode: "reinhard"`では1未満の値も圧縮されるため、指定色より暗く見えることがあります。
照明モデルや材質色を数値に近い状態で比較する場合は`mode: "linear"`を使い、0から1へ切り詰めた後のsRGB表示を確認します。
空、環境マップ、独自のグラデーションが必要な場合は、固定背景を遅延ライティングへ組み込むのではなく、アプリケーション側の背景描画または合成処理として追加します。

### ビュー空間法線で画面効果の座標を揃える

ビュー空間法線は、画面上の深度から復元した位置と、法線を使う効果の座標基準を揃えるために使います。
画面空間のエフェクトはカメラの奥行き方向と画面の水平・垂直方向を基準にするため、G-bufferの法線もビュー空間にすると、追加の座標変換を挟まずに内積や反射方向を計算できます。
ワールド空間法線を混ぜると、カメラを回転したときに照明、AO（Ambient Occlusion：環境遮蔽）、SSRの方向が画面に対してずれます。

法線は各成分が-1から1の範囲を取りますが、アタッチメントは`rgba8unorm`なので0から1へ符号化して保存します。
診断表示の色は実際の材質色ではなく、法線のXYZ成分をRGBで見せたものです。
平らな面の色がカメラ回転に応じて連続的に変わることが、ビュー空間の動作確認になります。

### 完全な材質値で照明結果を予測可能にする

材質値は、光沢、粗さ、金属らしさ、発光を照明式へ正確に伝え、Shapeごとの見え方を予測可能にするために使います。
G-bufferを使うShapeでは`roughness`や`metallic`を省略できません。
省略値を暗黙に補わず、入力漏れをその場で検出することで、設定不足が「それらしいが意図と異なる材質」として残るのを防ぎます。

```js
shape.setMaterial("smooth-shader", {
  has_bone: 0,
  use_texture: 0,
  color: [0.18, 0.62, 0.88, 1.0],
  ambient: 0.0,
  specular: 0.72,
  roughness: 0.20,
  metallic: 0.12,
  power: 48.0,
  emissive: 0.0
});
```

`color`のアルファは色の一部として扱い、反射特性は表面アタッチメントの`specular`、`roughness`、`metallic`へ分けます。
この区別を保つと、反射率を変えても透明度や基本色の意味が変わりません。

## カメラフレームで視点を揃える

カメラフレームは、G-bufferを描くパスと、その深度から位置を復元するコンピュートパスに、同じ瞬間の視点と投影を共有させるために使います。
一つのフレームオブジェクトを受け渡すことで、カメラが動く場面でも、法線、深度、AO、反射、フォグ、照明が画素単位で一致し、パスごとに`near`、`far`、画角、行列を組み直す手間と取り違えを避けられます。

Reverse-Zの深度値だけから距離を復元するには、その深度を作ったnear、far、画角、アスペクト比が必要です。
カメラ位置だけを後から読み直しても、G-buffer生成時の投影と同じである保証はありません。

`WebgApp`は描画直前に完全な`cameraFrame`を確定し、`onBeforeDraw`と`onAfterDraw3d`へ同じオブジェクトを渡します。
個別のG-buffer系パスでは、この同じオブジェクトを描画とコンピュートの両方へ渡します。

```js
app.start({
  onBeforeDraw: ({ cameraFrame }) => {
    gbuffer.renderSpace(app.space, cameraFrame, app.clearColor);
  },

  onAfterDraw3d: ({ cameraFrame }) => {
    app.getGPU().endPass();
    const ao = ssaoPass.encode(
      app.getGPU().commandEncoder,
      gbuffer.getBindingResources(),
      { cameraFrame, enabled: true }
    );
  }
});
```

ここで`cameraFrame`のプロパティを利用側が組み替える必要はありません。
`SsaoPass`は受け取ったフレームから投影パラメータを作り、カメラ用Reverse-Zであることを検証します。
near、far、画角、eyeのワールド行列を個別に再構成すると、G-bufferを作った時点と異なるカメラ状態を混入させる余地が生まれます。

## SSAOで接地感と隅の奥行きを補う

SSAOは、物体同士の接触部、壁と床の境目、形状の入り組んだ隅などへ、周囲から届く光が減る様子を加えるために使います。
シャドウマップでは表しにくい局所的な遮蔽を、すでに作成したG-bufferの法線と深度から近似できるため、ジオメトリを別の視点から描き直さずに接地感と奥行きの手掛かりを補えます。

SSAOが返すのは完成したシーン色ではなく、0から1の環境遮蔽の可視率です。
1は遮蔽なし、0へ近づくほど環境光が届きにくいことを表します。
色と分離しておくと、材質色や直接光を暗くせず、遅延ライティングで環境光の成分だけへ作用させられます。

```js
import { GeometryBufferPass } from "./webg/GeometryBufferPass.js";
import SsaoPass from "./webg/SsaoPass.js";

const gbuffer = new GeometryBufferPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  colorMode: "material",
  normalSpace: "view"
});

const ssaoPass = new SsaoPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  radius: 22,
  strength: 1.55,
  bias: 0.045,
  samples: 12,
  resolutionScale: 0.7
});

await Promise.all([gbuffer.ready, ssaoPass.ready]);
```

`radius`は画面上の探索半径、`strength`は遮蔽の強さ、`bias`は同じ面を自己遮蔽として数えないための許容値、`samples`は探索方向数です。
`resolutionScale`はAOの計算だけを低解像度化し、最終可視率は法線と深度を使うbilateral処理でフル解像度へ戻します。

SSAOの各画素では、まずカメラ用Reverse-Z深度をカメラフレームのnear、far、画角、アスペクト比で復元し、ビュー空間の表面位置を得ます。
その周囲を複数方向に参照し、中心の法線と参照先の奥行きから、環境光を遮る形状があるかを近似します。
画面の深度から得られるのはカメラから見える最前面だけなので、物体の裏側や画面外の遮蔽は計算できません。

低解像度のAOを単に線形拡大すると、手前の物体の暗さが奥の背景へ滲みます。
bilateral処理は、近い画素でも深度差が大きい場合や法線が大きく異なる場合に重みを下げます。
これにより、低解像度化したAOを物体の輪郭を越えにくい形でフル解像度へ戻せます。
ただし倍率を下げすぎると元のAOサンプル自体が欠けるため、後段の拡大だけでは回復できません。

SSAO単体を学習用に表示する場合は、返された可視率テクスチャを`FullscreenPass`へ渡します。

```js
onAfterDraw3d: ({ cameraFrame }) => {
  const gpu = app.getGPU();
  gpu.endPass();

  const aoVisibility = ssaoPass.encode(
    gpu.commandEncoder,
    gbuffer.getBindingResources(),
    {
      cameraFrame,
      enabled: true,
      radius: 22,
      strength: 1.55,
      bias: 0.045,
      samples: 12
    }
  );

  app.screen.beginPresentPass({
    clearColor: app.clearColor,
    colorLoadOp: "clear"
  });
  copyPass.draw(aoVisibility);
  app.screen.clearDepthBuffer();
}
```

色との合成はSSAOではなく、遅延ライティングが環境光成分へ可視率を適用する段階で行います。
そのためSSAOのオプションに完成色を選ぶ`view: "composite"`はありません。
完成テクスチャをキャンバスへ転送するときは深度なしの`beginPresentPass()`を使い、後続の `Font` やHUD（Head-Up Display：画面上へ重ねる情報表示）のために`clearDepthBuffer()`でReverse-Z深度付きパスを再開します。

実行可能な全体例は 28_01.html で確認できます。
既定表示はAO可視率そのものではなく、G-bufferから求めたAOを遅延ライティングの環境光へ適用し、トーンマッピングまで終えた完成画像です。
AキーでSSAOの有無を比較できるため、物体の色と直接光を保ったまま、隅や接地部に対するAOの作用を観察できます。

AO可視率だけを調べたい場合はVキーで診断表示へ切り替えます。
このとき白は遮蔽なし、暗い部分は環境光が届きにくい領域です。
診断画像を既定の完成画像にせず明示操作へ分けることで、SSAOの出力と遅延ライティング後のシーン色を混同せずに確認できます。

## 遅延照明で多数の光源を評価する

遅延ライティングは、多数の動的な光源が複雑なジオメトリを照らすシーンで、光源を追加するたびに同じShapeを描き直す処理を避けるために使います。
まず照明を計算せずに不透明なShapeを一度だけG-bufferへ描き、次に画面の各画素でアルベド、法線、材質、深度を読み、その画素に作用する光源を評価して照明済みのHDRシーン色を作ります。
光源数が増えても、頂点変換、ラスタライズ、マテリアルアタッチメントの生成といったジオメトリ処理は一度のままであり、ジオメトリの複雑さとライティングの複雑さを分けて管理できることが大きな利点です。

ただし、光源を増やしても負荷が変わらないわけではありません。
現在の`DeferredLightingPass`は各画素で有効なローカルライトを順に評価する基本構成なので、照明段階の計算量は画素数と光源数に応じて増えます。
それでも、光源ごとにシーン全体を再描画する方式と比べれば、ジオメトリの再処理を避けられます。
多数の光源を使うときは`lightCount`と描画解像度を計測し、さらに大規模なシーンではタイル分割やクラスタリングを別の最適化課題として検討します。

`DeferredLightingPass`は、アルベド、表面マテリアル、ビュー空間法線、カメラの深度、AO可視率、シャドウ可視率、光源を読みます。
各可視率を先に色へ乗算して受け渡すのではなく、環境光と直接光のどちらへ作用するかを照明式の中で区別します。
そのため、AOで環境光だけを弱め、シャドウで直接光だけを遮り、発光成分はどちらにも暗くされないという、入力の役割に沿った合成ができます。

ここで使うBRDF（Bidirectional Reflectance Distribution Function：双方向反射率分布関数）は、光の入射方向、視線方向、法線、材質から、表面がどの方向へどれだけ光を反射するかを求める式です。
`DeferredLightingPass`は、微小な面の向きの分布を仮定するGGX反射モデルで、拡散反射と鏡面反射をまとめて評価します。

概念上の関係は次のようになります。
環境光にもFresnel反射と金属度による拡散成分の減少を適用するため、完全な金属へアルベド由来の拡散環境光を加えることはありません。

```text
F0 = mix（0.04 × specular, アルベド, metallic）
環境拡散光 = アルベド × 環境光 × AO可視率 × 環境光の拡散割合
直接光 = GGX BRDF（アルベド、法線、視線、光、表面材質）× シャドウ可視率
発光 = アルベド × emissive
HDRシーン色 = 環境拡散光 + 直接光 + 発光
```

### 標準シェーダーから材質値を読み替える

標準の`SmoothShader`から遅延ライティングへ移るときは、同じ名前の材質値を同じ数値のまま渡せば同じ見え方になる、と考えないことが重要です。
二つの経路は同じ`Shape`を描画できますが、`SmoothShader`はPhong型の簡潔な照明式を使い、`DeferredLightingPass`はGGX型の材質モデルを使います。
パラメーターの役割を読み替えることで、暗さやハイライトの違いを不具合と材質モデルの違いに切り分けられます。

- **color**
  - `SmoothShader`：入力された基本色をPhong型の照明計算へ使う
  - 遅延ライティング：sRGB色から線形アルベドへ変換し、G-bufferへ保存する
- **ambient**
  - `SmoothShader`：Shapeごとの最低照度と、直接拡散光との配分を決める
  - 遅延ライティング：G-bufferへ保存せず、照明パス全体の環境光強度を`encode()`へ渡す
- **specular**
  - `SmoothShader`：白いハイライトを加える強度として使う
  - 遅延ライティング：非金属の法線入射反射率F0を`0.04 × specular`で求める
- **power**
  - `SmoothShader`：Phong型ハイライトの鋭さを決める
  - 遅延ライティング：使用しない
- **roughness**
  - `SmoothShader`：使用しない
  - 遅延ライティング：GGX反射の粗さを決める
- **metallic**
  - `SmoothShader`：使用しない
  - 遅延ライティング：アルベドを拡散色と金属の鏡面反射色へ配分する
- **emissive**
  - `SmoothShader`：照明に依存しない基本色へ近づけ、鏡面反射を弱める
  - 遅延ライティング：`アルベド × emissive`を通常照明へ加算する

`color`は利用者から見ると、どちらの経路でも物体の基本色です。
ただし、計算途中の扱いは異なります。
`SmoothShader`は入力値をそのまま照明式へ使います。
G-buffer経路は`color`とカラーテクスチャをsRGB色として受け取り、それぞれを線形色へ戻してから乗算します。
遅延ライティング、SSR、ブルームなどは線形HDR色を処理し、最後のトーンマッピングで表示用sRGB色へ戻します。
このため、同じ`color`でも、照明式だけでなく色空間と最終表示変換の違いが見え方へ現れます。

`ambient`は、特に混同しやすい値です。
`SmoothShader`では、概念上、次のように暗部の最低照度を確保しながら、残りを直接拡散光へ割り当てます。

```text
拡散係数 = ambient + max（法線・光方向の内積, 0）×（1 - ambient）
```

正面から光を受ける非発光面では、環境光と直接拡散光を合わせた係数が概ね1になります。
一方、遅延ライティングの`ambient`は、直接光から独立した線形の環境光強度です。
AO可視率、Fresnel反射、`metallic`による拡散成分の減少を適用してから、直接光へ加えます。
したがって、標準経路の`ambient: 0.18`と遅延ライティングの`ambient: 0.18`は同じ明るさを意味しません。

`specular`も数値の尺度が異なります。
`SmoothShader`の`specular: 0.6`は、最大0.6の白いハイライトを基本色へ加える係数です。
非金属の遅延ライティングでは、同じ0.6からF0を次のように求めます。

```text
F0 = 0.04 × 0.6 = 0.024
```

この0.024は、光が面へ正面から入ったときに鏡面反射へ配分する割合です。
`metallic`を上げると、F0は`0.04 × specular`からアルベドへ近づき、同時に拡散反射が減ります。
そのため、遅延ライティングでハイライトを強くする目的だけで`specular`を標準経路と同じ値へ揃えても、同じ結果にはなりません。

ハイライトの広がりは、標準経路では`power`、遅延ライティングでは`roughness`で調整します。
大きな`power`と小さな`roughness`は、どちらも狭いハイライトを作ります。
ただし、Phong型とGGX型では、ハイライトの中心、裾の広がり、斜めから見たときの変化が異なるため、両者を正確に相互変換する一つの式はありません。
見た目を比較するときは、`power`と`roughness`を同じ数値へ揃えるのではなく、ハイライトの幅が近くなる組み合わせを基準にします。

同じShapeを両方の経路で使う場合は、片方が読まない値も含めて材質を完全に設定できます。
次の例では、`ambient`と`power`を`SmoothShader`が使い、`roughness`と`metallic`をG-bufferと遅延ライティングが使います。
`color`、`specular`、`emissive`は両方が読みますが、前述のように照明式の中での意味は同一ではありません。

```js
shape.setMaterial("smooth-shader", {
  has_bone: 0,
  use_texture: 0,
  color: [0.72, 0.24, 0.10, 1.0],
  ambient: 0.18,   // SmoothShaderが読むShapeごとの値
  specular: 0.60,  // 両方が読むが、反射モデル内の意味は異なる
  power: 40.0,     // SmoothShaderのPhong型ハイライト
  roughness: 0.42, // 遅延ライティングのGGX反射
  metallic: 0.0,   // 遅延ライティングの金属度
  emissive: 0.0
});
```

遅延ライティングの環境光はShapeの`ambient`から取得せず、照明を実行するときに別途指定します。
次の0.035は一例であり、0.18から機械的に換算した値ではありません。
シーンの光量、背景、露出、トーンマッピングを含めて調整します。

```js
const comparisonHdrScene = deferredPass.encode(
  app.getGPU().commandEncoder,
  {
    ...gbuffer.getBindingResources(),
    shadowVisibility,
    spotShadowVisibility,
    ambientOcclusion: aoVisibility
  },
  {
    cameraFrame,
    directionalLight: null,
    spotLight: null,
    ambient: 0.035,
    lights,
    lightCount: lights.length,
    view: "lighting"
  }
);
```

`emissive`は両方の経路で発光寄りの見え方を作りますが、合成方法が異なります。
`SmoothShader`では値を1へ近づけるほど通常照明を弱め、照明に依存しない基本色へ近づけます。
遅延ライティングでは`アルベド × emissive`を環境光と直接光の結果へ加算するため、`emissive: 1.0`でも直接光は残ります。
経路を切り替えるアプリでは、発光値を共有する前に、どちらの合成を意図するかを確認してください。

実際の差は`samples/materials`で確認できます。
4×4の球体を表示し、行方向で`roughness`と`power`、列方向で`specular`と`metallic`を変えます。
コマンドパレットから描画経路と各値を切り替えられるため、標準経路が`roughness`と`metallic`を読まないこと、遅延ライティングが`power`を読まないことも確認できます。
このサンプルでは照明モデルの比較へReinhard変換の圧縮を混ぜないよう、遅延ライティングの最終表示を線形切り詰めにしています。

ローカルライトは全方向の`point`と、放射方向を持つ`cone`を同じ配列で扱います。

```js
import DeferredLightingPass from "./webg/DeferredLightingPass.js";

const deferredPass = new DeferredLightingPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  maxLights: 128
});
await deferredPass.ready;

const lights = [{
  type: "point",
  position: [0.0, 2.5, -4.0],
  color: [1.0, 0.55, 0.18],
  radius: 9.0,
  intensity: 3.2
}, {
  type: "cone",
  position: [4.0, 6.0, -2.0],
  direction: [0.0, -1.0, 0.0],
  color: [0.45, 0.72, 1.0],
  radius: 12.0,
  intensity: 2.4,
  innerAngle: 32.0,
  outerAngle: 48.0
}];

const hdrScene = deferredPass.encode(
  app.getGPU().commandEncoder,
  {
    ...gbuffer.getBindingResources(),
    shadowVisibility,
    spotShadowVisibility,
    ambientOcclusion: aoVisibility
  },
  {
    cameraFrame,
    directionalLight: {
      direction: [0.35, -1.0, -0.25],
      color: [1.0, 0.96, 0.88],
      intensity: 1.0
    },
    spotLight: null,
    ambient: 0.10,
    lights,
    lightCount: lights.length,
    view: "lighting"
  }
);
```

`directionalLight`と`spotLight`は、使わない場合もオプション自体を省略せず`null`で明示します。
これにより、光源の設定漏れと、意図して使わない場合を区別できます。

ローカルライトは`type`、`position`、`color`、`radius`、`intensity`が必須です。
`position`はワールド座標で渡し、パスがカメラフレームを使ってカメラ相対なビュー空間へ変換します。
`type: "cone"`ではさらにワールド方向の`direction`と、度単位の`innerAngle`、`outerAngle`を渡します。
角度は`0 < innerAngle < outerAngle <= 90`である必要があり、inner内は係数1、innerからouterの間は滑らかに減衰し、outer外は0になります。
不完全な光円錐がポイントとして処理されることはありません。

### ローカルライトを調整する

照明が暗いときは、画面全体を一度に補正する前に、暗い原因が光量、到達距離、照射角、環境光のどれにあるかを分けます。
各値は似た見た目を作る場合がありますが、変化する範囲と負荷の意味が異なります。
一つずつ変更すると、材質やトーンマッピングの影響と混同せずに調整できます。

- **intensity**
  - 変化：現在の`radius`と光円錐に入っている画素の直接光を強くする
  - 注意：到達距離と照射角は変わらない
- **radius**
  - 変化：光の打ち切り距離を伸ばし、同じ距離にある面の減衰も弱くする
  - 注意：光円錐の角度は変わらず、対象画素が増える場合がある
- **outerAngle**
  - 変化：コーンライトの外縁を広げ、光が届く方向範囲を増やす
  - 注意：`innerAngle`内の強度は変わらない
  - 制約：`innerAngle < outerAngle <= 90`を保つ
- **lighting.ambient**
  - 変化：ローカルライトが弱い場所を含め、シーン全体の環境拡散光を増やす
  - 注意：直接光の到達距離は変わらない
  - 影響：AO、Fresnel反射、`metallic`による拡散成分の減少を受ける

ローカルライトの距離減衰は、距離を$d$、半径を$r$として、$d < r$の範囲で概念上次のように計算します。

```text
距離減衰 = max（1 - d / r, 0）²
直接光の放射輝度 = light color × intensity × 距離減衰 × 角度減衰
```

このため`radius`を上げると、単に遠方へ光が届くだけでなく、同じ距離の面も明るくなります。
明るさだけを変えたい場合は`intensity`を使い、照明の切れ目や光源間の暗い区間を広げたい場合は`radius`を使います。

コーンライトでは、`innerAngle`内の角度減衰は1です。
`innerAngle`から`outerAngle`の間で0へ滑らかに減衰し、`outerAngle`の外側は0になります。
中心の明るい範囲を広げる場合は`innerAngle`、光が届く外縁を広げる場合は`outerAngle`を調整します。
角度を広げるほど多くの画素が直接光の評価対象になり得るため、見た目だけでなくGPU時間も確認します。

遅延ライティングの環境光は、Shapeの`ambient`ではなく、`DeferredLightingPass.encode()`または`ComputeEffectPipeline.encode()`の`lighting.ambient`へ渡します。
アプリケーション側で`DEFERRED_AMBIENT`のような定数を用意する場合も、その名前はアプリ固有であり、APIへ渡す値の意味は`lighting.ambient`です。
環境光を上げても発光や直接光の代わりにはならず、完全な金属にはアルベド由来の拡散環境光を加えません。

調整は、次の順序で行うと原因を切り分けやすくなります。

1. 光が届いている面だけが暗い場合は、`intensity`を上げます。
2. 光源と光源の間で照明が途切れる場合は、`radius`を上げます。
3. コーンの横方向だけが暗い場合は、`outerAngle`を上げます。
4. 光が届かない場所を含めて全体の基礎照度が不足する場合は、`lighting.ambient`を上げます。
5. 最後に露出とトーンマッピングを調整し、照明値の問題を表示変換だけで隠していないか確認します。

光円錐が表すのは光の放射形状であり、幾何学的な遮蔽ではありません。
光円錐内の壁に光を遮らせるには、別途シャドウ可視率が必要です。
`view`を`"albedo"`、`"normal"`、`"depth"`、`"shadow"`、`"ao"`、`"roughness"`などへ切り替えると、照明の後からでは見分けにくい入力を個別に調べられます。

## シャドウマップで直接光の遮蔽を表す

シャドウマップは、光源から見て別の物体に隠れている表面へ直接光を届かせず、物体が床や壁へ落とす影を表すために使います。
SSAOが画面に見えている近傍から環境光の遮蔽を近似するのに対し、シャドウマップはライトビューからシーンを描くため、カメラから直接見えない遮蔽物も影へ反映できます。
照明色と分離した可視率として解決すれば、遅延ライティングで直接光だけへ適用できます。

方向光とスポットライトのシャドウマップは、ライトビューから見た最短深度を保存します。
通常カメラはReverse-Zですが、`ShadowMapPass`と`SpotShadowMapPass`は意図的に`SHADOW_STANDARD_Z`を使います。

```text
カメラ深度: depth32float / クリア値0 / greater / near側1 / far側0
シャドウ深度: depth32float / クリア値1 / less / near側0 / far側1
```

シャドウresolveは、カメラ用Reverse-Z深度から影を受ける面のビュー空間位置を復元し、それをライトビューへ変換して通常Zのシャドウ深度と比較します。
2枚の深度テクスチャを同じ式で線形化したり、シャドウマップを一括置換で`greater`へ変えたりしてはいけません。

方向光の範囲を固定する場合は`createDirectionalLightMatrices()`を使います。
カメラの視錐台へ追従させる場合、統合パイプラインの`shadow.directional.fitMode: "frustum-fit"`を使うと、カメラの8頂点を光源空間へ移したAABB（Axis-Aligned Bounding Box：軸平行境界ボックス）から投影範囲を作り、テクセル単位で安定化できます。
`fitFar`はカメラの`far`以下でなければならず、範囲外の値は縮めて続行せず例外になります。

低水準APIでは、まず`ShadowMapPass`がライトビューからシャドウ深度を作り、次に`ComputeShadowPass`がG-bufferの影を受ける面と比較して可視率を作ります。
色を出力するのではなく可視性だけを出力するため、遅延ライティングは直接光にだけ影を適用できます。

```js
const shadowVisibility = shadowPass.encode(
  app.getGPU().commandEncoder,
  {
    normal: gbufferResources.normal,
    depth: gbufferResources.depth,
    ...shadowMap.getBindingResources()
  },
  {
    cameraFrame,
    lightViewProjection: lightMatrices.viewProjection,
    lightDirection: [0.35, -1.0, -0.25],
    bias: 0.0015,
    normalBias: 0.003,
    pcfRadius: 1,
    enabled: true
  }
);
```

`bias`はシャドウ深度比較の数値誤差を吸収し、`normalBias`は法線方向へ影を受ける面をずらして表面が自分自身を遮るシャドウアクネを減らします。
大きすぎると影が物体から浮くため、解像度とシーンスケールに合わせて決めます。
`pcfRadius`は0から2で、大きくするほど影の端が柔らかくなる一方、参照数が増えます。

## SSRで画面内の反射を低コストに加える

SSR（Screen Space Reflection、画面空間反射）は、床、金属、水面などへ、現在の画面に映っている物体や光の反射を加えるために使います。
別のカメラでシーンを描いた反射テクスチャを用意せず、G-bufferと照明済みのHDRシーン色を再利用するため、動く物体や照明を反映した反射を比較的小さな追加構成で作れます。

SSRはビュー空間位置と法線から反射レイを作り、カメラ用Reverse-Z深度との交差を画面上で探索します。
出力RGBは反射色、アルファは交差判定、材質反射率、距離、画面端の減衰を含む反射ウェイトです。
反射だけを独立したテクスチャへ出すことで、材質に応じた`mix`、演出的な`add`、診断表示を、シーン色の生成から分けて選べます。

反射レイは、表面に入る視線方向をG-bufferの法線で反転して作ります。
レイ上の点をカメラ投影で画面座標へ戻し、その画素の深度から復元した表面と奥行きを比べます。
一致する範囲へ入ったら交差とみなし、照明済みのHDRシーン色を反射色として読みます。

```text
ビュー空間の位置と法線
  -> 反射レイ
  -> カメラ投影で画面上のUV座標へ戻す
  -> カメラ用Reverse-Z深度と交差判定
  -> 交差位置のHDRシーン色を取得
  -> 材質と画面端で反射の重みを減衰
```

深度テクスチャは立体の厚みを持たないため、`thickness`で交差とみなす許容幅を与えます。
小さすぎるとステップ間に面を通り過ぎ、大きすぎると本来は離れている面を交差判定と誤認します。
そのため`distance`、`steps`、`thickness`は別々の強さではなく、シーンスケールに対する一組の探索条件として調整します。

SSRは画面に存在する情報だけを使うため、画面外の物体、別の物体に完全に隠れた面、カメラと反対を向く面は反射できません。
これは不具合ではなく画面空間手法の制約です。
欠けを隠すために常に強い色を補うのではなく、環境マップなど別の反射情報と役割を分けます。

反射レイで得た色は、そのまま全材質へ同じ鋭さで適用しません。
`ComputeSsrPass`は反射結果から1/2、1/4、1/8の画像ピラミッドを作り、G-bufferの`roughness`に応じて元の反射と隣接する段階を補間します。
滑らかな面では鋭い反射を保ち、粗い面ほど低い解像度の反射色を選びます。
反射の重みを保存するアルファは現在の画素の値を保つため、周囲の面の反射率がぼけて流入することを避けられます。

```js
import ComputeSsrPass from "./webg/ComputeSsrPass.js";

const ssrPass = new ComputeSsrPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight(),
  resolutionScale: 0.7,
  reflectivityThreshold: 0.05
});
await ssrPass.ready;

const reflection = ssrPass.encode(
  app.getGPU().commandEncoder,
  {
    scene: hdrScene,
    normal: gbufferResources.normal,
    depth: gbufferResources.depth,
    material: gbufferResources.material
  },
  {
    cameraFrame,
    intensity: 0.82,
    distance: 42.0,
    thickness: 0.42,
    steps: 48,
    resolutionScale: 0.7,
    reflectivityThreshold: 0.05,
    view: "reflection",
    enabled: true
  }
);
```

`distance`はレイの最大探索距離、`steps`は粗い探索の基準ステップ数、`thickness`は深度面と交差したとみなす厚みです。
距離やステップを増やせば必ず正しくなるわけではなく、探索距離に対してステップが粗すぎると薄い物体を通り過ぎます。
`reflectivityThreshold`は反射性の小さい画素でレイマーチングを始めないための早期終了値です。
`resolutionScale`は反射レイ、`roughness`用の画像ピラミッド、最終反射の描画先へ適用され、G-bufferは元の解像度のまま参照されます。

反射は`rgba16float`で保持し、`ComputeEffectComposer`でHDRシーンへ`mix`または`add`合成します。
自然な材質反射には`mix`、発光的な加算表現には`add`が適します。
合成後もトーンマッピングまではHDRを維持します。

## フォグで距離に応じた空気の厚みを表す

フォグは、カメラから遠い表面ほどシーン色を霧の色へ近づけ、空気の厚み、遠近感、天候を画面全体へ加えるために使います。
形状ごとのシェーダーで同じ計算を繰り返す代わりに、`ComputeFogPass`は照明と半透明合成を終えた線形HDRシーンを一度だけ処理します。
遅延レンダリング経路では、フォワード描画側のフォグを重ねず、画面全体のフォグをこのパスへ集約します。

フォグの入力は、`rgba16float`のシーン色と、G-bufferに保存されたカメラ用Reverse-Z深度です。
深度を作ったものと同じ`cameraFrame`からビュー空間位置を復元し、その位置の長さをカメラから表面までの距離として使います。
出力も`rgba16float`なので、フォグを適用した後にトゥーン、DoF、ブルームを続け、最後にトーンマッピングできます。

```js
import ComputeFogPass from "./webg/ComputeFogPass.js";

const fogPass = new ComputeFogPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await fogPass.ready;

const foggedColor = fogPass.encode(
  app.getGPU().commandEncoder,
  {
    scene: transparentComposite,
    depth: gbufferResources.depth
  },
  {
    cameraFrame,
    mode: "linear",
    color: [0.10, 0.15, 0.20],
    near: 20.0,
    far: 80.0,
    density: 0.03,
    enabled: true
  }
);
```

`mode`は`"linear"`または`"exp"`です。
`"linear"`では、`near`まで元のシーン色を保ち、`far`へ近づくほど霧色の割合を増やします。
現在の実装では`density`も線形フォグの適用量へ使い、`density * 50`を0から1へ制限した値で、算出した霧の割合を弱めます。
既定の`density: 0.03`ではこの係数が1になるため、`near`と`far`で定めた線形変化がそのまま適用されます。
`density`を0.02より小さくすると、同じ距離範囲でもフォグが弱くなります。

ここでの`near`と`far`はカメラの投影面ではなく、フォグを変化させるための距離です。
カメラの`projectionNear`と`projectionFar`は`cameraFrame`を介して深度復元に使われますが、フォグの開始距離と終了距離はシーンの尺度と演出に合わせて別に指定します。

`"exp"`では、可視率を$e^{-density \times distance}$で求めます。
`density`を大きくすると短い距離でも霧が濃くなります。
このモードの見た目は`near`と`far`では変わりませんが、パスの共通入力契約として`near >= 0`、`far > near`を満たす値を指定します。
`color`は3成分の線形フォグ色で、各成分は0以上です。

| 設定値 | 既定値 | 意味 |
| --- | ---: | --- |
| `mode` | `"linear"` | 距離から可視率を求める方式 |
| `color` | `[0.1, 0.15, 0.1]` | 線形HDR区間で混合するフォグ色 |
| `near` | `20.0` | 線形フォグが始まる距離 |
| `far` | `80.0` | 線形フォグがフォグ色へ到達する距離 |
| `density` | `0.03` | 指数フォグの密度、または線形フォグの適用量 |
| `enabled` | `false` | フォグを適用するかどうか |

フォグは半透明合成後に置きます。
これにより、ガラスや半透明の粒子を別のフォワードフォグで再描画せず、合成済みシーン全体へ一回の全画面処理として適用できます。
ただし、参照する深度は不透明なG-buffer深度だけです。
半透明面はこの深度を書き換えないため、半透明画素では背後の不透明面までの距離を使う近似になります。

背後にも不透明面がなく、深度が背景値0の画素では、距離を無限遠などへ読み替えません。
その画素の透明合成済みシーン色をそのまま出力します。
このため、背景を一律にフォグ色へ染める処理ではありません。
空や独自背景にもフォグを適用したい場合は、その背景の距離または別の合成規則をアプリケーション側で定義する必要があります。
複数の半透明層ごとに固有のフォグ距離を評価する処理も、このパスの対象外です。

1.0の標準フォワード描画で`WebgApp.setFog()`を使っていたアプリケーションを遅延レンダリングへ移す場合は、その設定を`ComputeFogPass`または第29章の`ComputeEffectPipeline`へ移します。
両方を有効にすると、フォワード描画された面と全画面処理でフォグが二重に適用されるため、同じシーンではどちらか一方がフォグを担当するようにします。

## DoFで焦点と奥行きを伝える

DoF（Depth of Field、被写界深度）は、焦点を合わせた距離を鮮明に保ち、その手前と奥をぼかすことで、注目させたい対象とシーンの奥行きを伝えるために使います。
すでに描いたHDRシーンとカメラ用Reverse-Z深度を使うため、距離ごとにシーンを描き分けずに焦点表現を追加でき、焦点距離をフレームごとに変える演出にも対応できます。

`ComputeDofPass`は深度からカメラまでの距離を復元し、焦点面との差をCircle of Confusion（CoC、錯乱円）の段階へ変換します。
シーン色、近景、遠景、CoCの補助情報の4系統について、1/2、1/4、1/8、1/16の画像ピラミッドを作ります。
合焦範囲を外れた形状は、距離に応じて隣接する低周波の段階を選び、鮮明な元画像を残さず置き換えます。

近景と遠景は、アルファ乗算済みの色と形状の被覆率へ分離します。
遠景のぼけは焦点面や近景の後ろへ置き、近景のぼけは焦点面、遠景、背景の手前へ重ねます。
CoCの補助情報を被覆率と別に保持するため、物体の輪郭外へぼけを広げながら、どの段階を選ぶかを独立して制御できます。

```js
import ComputeDofPass from "./webg/ComputeDofPass.js";

const dofPass = new ComputeDofPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await dofPass.ready;

const focusedColor = dofPass.encode(
  app.getGPU().commandEncoder,
  {
    scene: hdrScene,
    depth: gbufferResources.depth
  },
  {
    cameraFrame,
    focusDistance: 36.0,
    focusRange: 7.0,
    cocScale: 1.0,
    debugView: "composite",
    sharpnessWidth: 0.15,
    sharpnessPower: 1.0,
    blurRadius: 1.0,
    enabled: true
  }
);
```

この例は`COMPUTE_DOF_DEFAULTS`と同じ値です。
各設定の意味は次のとおりです。

- `focusDistance`の既定値は`36.0`です。カメラから合焦面までの
  ビュー空間での距離で、0より大きい値を指定します。
- `focusRange`の既定値は`7.0`です。焦点面の近くを鮮明に保つ幅と、
  画像ピラミッドの段階が一つ進む距離の基準になります。0より大きい値を
  指定します。
- `blurRadius`の既定値は`1.0`です。画像ピラミッドの各段階を作る
  13点ローパスフィルターのサンプル間隔です。範囲は0.25から3.0で、
  大きくすると同じ段階でもぼけが広がります。
- `cocScale`の既定値は`1.0`です。焦点面との差から求めたCoCを
  拡大または縮小します。範囲は0.0から2.0で、大きくすると同じ
  距離差でも低い解像度の段階へ早く進みます。
- `sharpnessWidth`の既定値は`0.15`です。合焦帯から最初の低周波
  段階へ移る境界幅を指定します。範囲は0.0から0.95です。
- `sharpnessPower`の既定値は`1.0`です。隣接する低周波の段階間の
  補間カーブを調整します。0より大きい値を指定します。
- `debugView`の既定値は`"composite"`です。`"depth"`では復元距離、
  `"focus"`では合焦状態、`"composite"`では完成色を出力します。
- `enabled`の既定値は`true`です。DoF合成を有効にします。

調整は、最初に`focusDistance`で被写体へ焦点を合わせ、`focusRange`で鮮明に保つ奥行きを決めます。
次に`cocScale`で距離差に対するぼけの進み方を整え、`blurRadius`でぼけの空間的な広さを調整します。
最後に`sharpnessWidth`と`sharpnessPower`で段階間の移行を確認します。

DoFがカメラ移動に追従しないときは、ぼけの設定より先に、`scene`と`depth`が同じフレームのものか、G-bufferの描画に使った同じ`cameraFrame`を渡しているかを確認します。
未描画の背景自体には距離がないため、背景全体を一律にぼかさず、近景または遠景のフィルター処理済みの被覆率が届いた範囲だけを更新します。

## トゥーンと輪郭を分けて画風を調整する

トゥーンと輪郭は、物理的に滑らかな陰影をイラストやセル画のような明暗帯と線へ置き換え、写実表現とは異なる画風を作るために使います。
明るさの段階化と輪郭線の検出を別のパスにすると、色面の数と線の太さを独立に調整でき、輪郭だけを通常の照明へ加える、トゥーンだけを使って線を省く、といった使い分けもできます。

`ComputeToonPass`は照明済みのHDRシーンを少数の明暗帯へ変換します。
RGBを個別に丸めると色相が変わるため、パスはRGBの最大値を強度として段階化し、元のRGB全体へ同じ倍率をかけます。
これにより、元の材質色を保ったまま陰影だけを整理できます。

HDRの値を0から1へ切り詰めてから段階化すると、1.0を超える輝度がすべて同じ白帯になります。
そこで強度を0.5〜1、1〜2、2〜4のよう2倍ごとの露出区間へ分け、各区間の内側を`levels`段階へ量子化します。
これにより、発光部の値を1.0へ切り詰めず、後段のブルームとトーンマッピングへ光量差を残せます。
`floor`は1.0未満の暗部だけに適用され、HDR側の明るさを引き上げません。

```js
import ComputeToonPass from "./webg/ComputeToonPass.js";

const toonPass = new ComputeToonPass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await toonPass.ready;

const toonColor = toonPass.encode(
  app.getGPU().commandEncoder,
  hdrScene,
  {
    levels: 4,
    strength: 1.0,
    gamma: 1.0,
    floor: 0.28,
    enabled: true
  }
);
```

`levels`は明暗の段階数、`strength`は元の色と段階化した色の混合率、`gamma`は帯の境界を暗部または明部寄りへ移す値、`floor`は最暗帯の明るさです。
照明値の意味が残っているトーンマッピング前に適用すると、強い光を含むHDRの範囲から明暗帯を作れます。

### 色の境界と形状の境界を目的で使い分ける

色の境界は画像として見える色や明るさの境界を線にしたいとき、形状の境界は物体の外形や面の折れ目を安定して線にしたいときに使います。
目的に合う情報を選べば、模様まで積極的に線へ含めることも、照明の変化に影響されにくい輪郭だけを描くこともできます。

`ComputeEdgePass`は、シーン色の輝度差を読む色の境界と、G-bufferの法線差・深度差を読む形状の境界を持ちます。
色の境界は模様や照明の切り替わりも拾いやすく、形状の境界は物体の外形や面の折れ目を拾いやすいという違いがあります。

```js
import ComputeEdgePass from "./webg/ComputeEdgePass.js";

const edgePass = new ComputeEdgePass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await edgePass.ready;

const outlined = edgePass.encode(
  app.getGPU().commandEncoder,
  displayColor,
  {
    normal: gbufferResources.normal,
    depth: gbufferResources.depth,
    cameraFrame,
    strength: 1.0,
    threshold: 0.16,
    mix: 1.0,
    thickness: 2,
    blendMode: "black-multiply",
    colorEnabled: false,
    geometryEnabled: true,
    normalWeight: 1.0,
    depthWeight: 1.0,
    enabled: true
  }
);
```

形状の境界では`normal`、`depth`、`cameraFrame`をひとまとめに渡します。
色の境界だけならこれらは不要です。
`thickness`は検出後の輪郭を周囲へ広げる幅、`threshold`は差を輪郭とみなす判定値です。
`black-multiply`は元色を残した黒線、`black-subtract`はより強い黒線、`white-add`は発光的な白線に適します。

輪郭抽出へ渡す`displayColor`は、トーンマッピング後の`rgba8unorm`、または標準描画先と同じ`bgra8unorm`である必要があります。
`ComputeEdgePass`は表示色の輝度差を読む処理であり、線形HDRの`rgba16float`は入力として受け付けません。
遅延照明の結果へ輪郭を加える場合は、先に`ComputeEffectToneMapPass`で表示色へ変換します。
フォワードレンダリング経路の`RenderTarget`へ適用する場合は、`bgra8unorm`のまま渡せます。

入力形式を二つ認める一方、`ComputeEdgePass`が内部で生成して保持する出力ストレージテクスチャは`rgba8unorm`です。
これは、キャンバスと同じ形式で作られる通常のレンダーターゲットが`bgra8unorm`であっても、ストレージ書き込みに使う内部出力の形式まで同じとは限らないためです。
入力と出力の形式を同一と仮定せず、パスが返した出力ターゲットを最終表示へ渡してください。

## ビネットで画面周辺の見せ方を整える

ビネットは、画面の中心付近を保ちながら周辺を減光または着色し、視線を注目領域へ導くために使います。
三次元位置や材質を再評価する効果ではなく、完成した表示画像に対する画面構成上の調整です。
そのため`ComputeVignettePass`は、トーンマッピングと任意の輪郭抽出が終わった`rgba8unorm`表示色を入力に取り、同じ形式の最終テクスチャを返します。

```js
import ComputeVignettePass from "./webg/ComputeVignettePass.js";

const vignettePass = new ComputeVignettePass(app.getGPU(), {
  width: app.screen.getWidth(),
  height: app.screen.getHeight()
});
await vignettePass.ready;

const finalColor = vignettePass.encode(
  app.getGPU().commandEncoder,
  outlinedDisplayColor,
  {
    center: [0.5, 0.5],
    radius: 0.9,
    softness: 0.35,
    strength: 0.65,
    tint: [0.0, 0.0, 0.0],
    enabled: true
  }
);
```

`center`は正規化した画面座標で表す効果の中心です。
`[0.5, 0.5]`は画面中央であり、被写体が中央から外れている構図では中心を移動できます。
`radius`は周辺効果が完了する外側半径、`softness`は効果が立ち上がる幅です。
内側半径は`radius - softness`で求められるため、`softness`は0より大きく、`radius`以下である必要があります。

`strength`は0から1の範囲で、周辺へ`tint`をどれだけ作用させるかを決めます。
処理は周辺係数と`strength`から求めた割合で、入力RGBへ白から`tint`までの係数を乗算します。
既定の黒い`tint`では周辺減光になります。
色を持つ`tint`では、その色を単純に上塗りするのではなく、入力色の各成分を乗算して周辺の色調を変えます。
アルファは入力値を保持します。

| 設定値 | 既定値 | 意味 |
| --- | ---: | --- |
| `center` | `[0.5, 0.5]` | 正規化画面座標で表す効果の中心 |
| `radius` | `0.9` | 効果が完了する外側半径 |
| `softness` | `0.35` | 内側から外側へ変化する幅 |
| `strength` | `0.65` | 周辺へ`tint`を作用させる割合 |
| `tint` | `[0.0, 0.0, 0.0]` | 入力色へ乗算する周辺色 |
| `enabled` | `false` | ビネットを適用するかどうか |

画面の幅と高さが異なる場合に正規化座標の距離をそのまま使うと、円形に意図した効果が横長または縦長に歪みます。
`ComputeVignettePass`は中心からの水平方向の差へ画面のアスペクト比を掛けてから距離を求めます。
この補正により、キャンバスをリサイズしても効果の距離基準を画面上で保ちます。
パス自体の出力ターゲットは、他の全画面パスと同様に新しいキャンバス寸法へ`resize()`する必要があります。

ビネットは深度、法線、材質、`cameraFrame`を読みません。
したがってG-bufferを持たないフォワードレンダリング経路の表示色にも個別パスとして接続できます。
一方、線形HDR色は入力として受け付けません。
露出やトーンマッピングより前へ置かず、最終表示色を作った後に一度だけ適用します。

HUD（Head-Up Display、画面上の情報表示）をビネットで暗くしたくない場合は、ビネット後のテクスチャを画面へ提示してからHUDを描きます。
第29章の統合経路では、「トーンマッピング、輪郭抽出、ビネット、最終表示、HUD」の順序になります。
アプリケーションがすでに独自のビネットを最終表示の直前へ持っている場合は、統合パイプライン側と二重に有効化せず、設定を一方へ集約します。

## HDR効果を順につなぐ

効果の順序は、1.0を超えるHDRの光量を必要な処理まで残し、同じ色変換を二重に適用しないために決めます。
正しい順序でつなぐと、非常に明るい光だけをブルームで広げ、DoFで発光の明るさを保ったままぼかし、最後に表示可能な範囲へトーンマッピングできます。
順序を誤ると、各パスが正常でも強い光の差が消え、ブルームや反射が平坦に見えます。

ブルームはHDRシーンから明るい部分を抽出します。
トーンマッピング後に実行すると強い光が表示範囲へ圧縮済みとなり、ブルームの入力差が失われます。
DoFもHDRシーンをぼかすことで、合焦外の発光が自然な明るさを保ちます。
フォグ、トゥーン、DoF、ブルームはトーンマッピングより前、最終表示色へ輪郭と周辺調整を重ねる輪郭抽出とビネットはトーンマッピング後が基本です。

標準順序は次のとおりです。

```text
G-buffer
  -> 可視率（シャドウ / SSAO）
  -> 遅延ライティング
  -> SSRと効果合成
  -> `TransparencyPass`
  -> フォグ
  -> トゥーン / DoF / ブルーム
  -> トーンマッピング
  -> 輪郭抽出
  -> ビネット
  -> 最終表示
```

`TransparencyPass`は、G-bufferへ入れなかった半透明三角形を合成済みのHDRシーンへ加えます。
不透明シーンから1/2、1/4、1/8の画像ピラミッドを作り、粗さのマスク値に対応する隣接段階を補間して背景ぼけを作った後、全`Shape`から集めて奥から手前へ並べた透明表面をアルファ合成します。
利用側が個別に`encode()`することを前提としたパスではなく、通常は第29章の`ComputeEffectPipeline`が半透明三角形を検出したフレームだけ実行します。

`ComputeFogPass`は透明合成後のHDRシーン全体を処理しますが、距離の基準には不透明なG-buffer深度だけを使います。
`ComputeVignettePass`はトーンマッピングと輪郭抽出を終えた表示色を処理し、最終表示へ渡すテクスチャを作ります。
フォグとビネットはいずれも既定では無効であり、統合パイプラインでは有効なときだけ標準順序へ挿入されます。

## GPUパーティクルを更新する

GPUパーティクルは、火花、煙、雨、群れのような多数の粒子を毎フレーム動かしながら、CPUとGPUの間で全粒子の状態を往復させないために使います。
`GpuParticleEmitter`は粒子状態をストレージバッファで更新し、そのバッファを頂点シェーダーから直接読むため、粒子数が多いほどCPUで個別更新して転送する方式との差が大きくなります。

この自由度と引き換えに、粒子レイアウトと座標の意味は利用側WGSL（WebGPU Shading Language：WebGPU用シェーディング言語）が定義します。
G-buffer系の画面空間のエフェクトのように共通のアタッチメントから意味を復元するのではなく、コンピュートシェーダーのWGSLとレンダーシェーダーのWGSLの間で、位置、速度、寿命、色などの配置を一致させます。

通常カメラへ直接描く場合は、Emitter生成時に座標と深度を明示します。

```js
import GpuParticleEmitter from "./webg/GpuParticleEmitter.js";
import { CAMERA_REVERSE_Z } from "./webg/DepthConvention.js";

const emitter = new GpuParticleEmitter(app.getGPU(), {
  particleCount: 32768,
  floatsPerParticle: 12,
  computeCode,
  renderCode,
  coordinateSpace: "camera-relative",
  depthConvention: CAMERA_REVERSE_Z,
  targetFormat: app.getGPU().format
});
```

宣言だけをReverse-Zにして、WGSLが通常Zの深度を出力する状態は正しくありません。
頂点シェーダーが作るクリップ位置、描画パイプラインの比較、深度クリア値が同じ規約であることを確認します。
パーティクルバッファにどのフィールドが位置を表すかをコアが推測して書き換えることはありません。

### ピンポンバッファで並列更新を安定させる

ピンポンバッファは、全粒子が同じ時点の入力状態を読み、並列実行の順序に左右されない更新結果を得るために使います。
同じストレージバッファを入力と出力にすると、ワークグループの実行順によって更新前と更新後の値が混ざる可能性があります。
`GpuParticleEmitter`は2つの状態バッファを交互に使い、そのフレームの入力を読み、反対側のバッファへ出力します。
描画は更新後のバッファを頂点シェーダーから直接読むため、CPUへ読み戻して書き戻す必要もありません。

```text
frame N:     state A --compute--> state B --draw--> screen
frame N + 1: state B --compute--> state A --draw--> screen
```

`floatsPerParticle`はWGSL側の構造体と一致している必要があります。
位置、速度、寿命、色などの配置はアプリケーションのWGSLが定めます。
レイアウトがずれた場合に、位置らしい値を探して補正することはできません。
コンピュートシェーダーのWGSLとレンダーシェーダーのWGSLが同じ配置を読んでいることを、粒子数を少なくした診断表示で確認します。

## リサイズ時のずれとリークを防ぐ

リサイズと破棄を担当するパスを明確にするのは、ウィンドウ寸法の変更後も各テクスチャの画素対応を保ち、不要になったGPUリソースを確実に破棄するためです。
関連するパスを同じタイミングで更新し、作成した側だけが破棄する規則を守れば、画像のずれ、古いテクスチャの参照、二重破棄、メモリリークを防げます。

キャンバスの寸法が変わると、入力と出力が同じ画素を表すパスはまとめてリサイズする必要があります。
G-bufferだけが新しい寸法で、SSAOとSSRが前の寸法のままでは、テクスチャの座標対応が壊れます。

```js
function resizeEffects(width, height) {
  gbuffer.resize(width, height);
  ssaoPass.resize(width, height);
  deferredPass.resize(width, height);
  ssrPass.resize(width, height);
  fogPass.resize(width, height);
  dofPass.resize(width, height);
  bloomPass.resize(width, height);
  toonPass.resize(width, height);
  edgePass.resize(width, height);
  vignettePass.resize(width, height);
}

app.start({
  onUpdate: ({ screen }) => {
    resizeEffects(screen.getWidth(), screen.getHeight());
  }
});
```

各`resize()`は同じ寸法ならリソースを作り直しません。
フレームの途中ではなく`onUpdate`で同期し、その後の`onBeforeDraw`から新しいターゲットを使います。
破棄時は、ターゲットを生成したパスの`destroy()`を呼びます。
同じテクスチャを複数のパスへ入力していても、入力として参照するだけのパスから破棄してはいけません。
この管理が煩雑になるほど効果を組み合わせる場合は、第29章の`ComputeEffectPipeline`へリソースの生成、更新、破棄をまとめる方が安全です。

## 中間結果を意味ごとに見て原因を絞る

G-bufferや可視率などの中間結果を個別に表示すると、最終画像だけでは同じに見える入力不足、座標の不一致、合成順序の誤りを切り分けられます。
複数のパスを一度に調整する代わりに、情報が最初に不正になる段階を特定できるため、シェーダーの数が増えても原因を推測だけで追わずに済みます。
次の順で観測します。

1. アルベドが照明前の色になっているか。
2. 法線を色表示したとき、カメラ回転に対してビュー空間として変化するか。
3. 深度背景が0で、near側ほど明るいか。
4. マテリアルの4成分がspecular、roughness、metallic、emissiveとして入っているか。
5. AOとシャドウの可視率が白を「遮蔽なし」としているか。
6. 遅延ライティングの出力がHDRのままか。
7. 反射アルファが交差判定しない領域で0か。
8. フォグが背景深度0を距離として扱わず、透明合成後のHDR色を
   読んでいるか。
9. トーンマッピング、sRGB表示変換、追加のガンマ調整が表示前の1回だけか。
10. ビネットが輪郭抽出の後、最終表示とHUDの前に一度だけ
    適用されているか。

画面が黒い場合は、効果の式だけでなくパスの接続も確認します。
たとえば、全画面コピーをカメラ用Reverse-Z深度付きパスへ描くと、アタッチメントが一致しないことがあります。
深度なしの最終表示パスを開いたまま、`Font`のパイプラインへ進んだ場合も同様です。
この不一致は、コマンドバッファー全体を無効にすることがあります。

WebGPUの`uncaptured error`（捕捉されなかった検証エラー）を確認し、最終表示からHUD描画への切り替えを`beginPresentPass()`と`clearDepthBuffer()`の対で構成します。

## 画質への影響が小さい順に負荷を下げる

負荷調整では、効果そのものを削る前に、中間の描画先の解像度、1画素あたりの参照数、適用範囲の順で見直します。
ぼかしやバイラテラルフィルターによる拡大を前提にした派生描画先から解像度を下げれば、輪郭や材質を保持するG-bufferを壊さずに、大きな計算量を減らせるためです。

画面空間のエフェクトの負荷は、おおむね処理画素数、1画素あたりのサンプル数、パス数の積で決まります。
最初に`resolutionScale`を下げ、次にレイステップやサンプル数を調整し、最後に効果の有効範囲を狭めます。
解像度倍率は縦横へ効くため、1.0から0.7への変更でも処理画素数は約49%になります。

ただし、G-bufferのアタッチメントを効果ごとに別解像度へ変更してはいけません。
アルベド、法線、マテリアル、深度は同じ画素を表す必要があります。
低解像度化はSSAO生ターゲットやSSR反射など、各パスが内部で生成して管理する派生ターゲットへ適用します。

フォグとビネットは最終的な画素対応を保つ全画面効果なので、現在の実装には`resolutionScale`がありません。
どちらも1画素につき少数のテクスチャ参照と算術処理で完了しますが、有効にすれば画面解像度分のディスパッチと出力テクスチャが追加されます。
統合パイプラインで無効にした場合は、そのパスの`encode()`自体を省略します。
負荷を測るときは、強度を0へ近づけた状態ではなく、効果の有効状態を切り替えてGPU時間を比較します。

## まとめ

本章のパスは、少ない描画の再実行で、光源、遮蔽、反射、フォグ、焦点、発光の広がり、画風、画面周辺の演出を追加したいときに使います。
色だけで作れる効果には軽い画面外描画の経路を選び、三次元的な関係が必要な効果にはG-bufferを一度作って共有することが、構成と負荷を必要以上に増やさない基本方針です。

高度なコンピュート表現で重要なのは、個々のシェーダーの複雑さより、入力と出力の意味を保つことです。
カメラ用Reverse-ZのG-buffer、通常Zのシャドウマップ、可視率としてのAOとシャドウ、HDRのライティング、反射、フォグ、表示用のトーンマッピング、表示色の輪郭抽出とビネットを分けると、効果を追加しても同じ情報を二重に評価せずに済みます。

個別パスは仕組みの理解や新しい効果の研究に適しています。
複数の効果を製品の描画順序として接続するときは、同じカメラフレームと、リソースの生成、更新、破棄を一括管理する第29章の統合パイプラインを使用します。
