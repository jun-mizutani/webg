# webg 1.0から2.0への移行

この付録は、webg 1.0で作成したアプリケーションやシェーダーを、第2版で扱うwebg 2.0へ移行する読者のためのものです。
webgを初めて使う場合は、この付録を先に読む必要はありません。
新しくアプリケーションを作る場合は、各章に掲載されたwebg 2.0のコードを出発点にしてください。

現行APIの仕組み、設定値、既定値、制限事項は本編を正本とします。
この付録では、1.0の実装から変更する箇所と移行時の注意点を示し、現行APIの詳細は対応する本編の節を参照します。

1.0から2.0までの主な変更領域は次のとおりです。

- 通常カメラのReverse-Z化と、シャドウマップ用Standard-Zとの分離
- カメラフレーム、カメラ相対レンダリング、`renderFrameToken`の導入
- G-buffer、遅延ライティング、SSAO（Screen Space Ambient Occlusion、
  画面空間の環境遮蔽）、シャドウ、SSR（Screen Space Reflection、
  画面空間反射）を統合する
  `ComputeEffectPipeline`の導入
- 線形HDR中間色、トーンマッピング、sRGBの最終表示境界の明確化
- コンピュート版のフォグ、DoF、ブルーム、トゥーン、輪郭抽出、
  ビネットなどの画面効果と、GPU計算先行方式（compute-first）の
  実行基盤の追加
- `Shape`の複数マテリアル化と、三角形単位で自動分類・合成する半透明描画の追加

webg 2.0は、従来のアプリケーション構造をコンピュートシェーダー専用へ置き換えたものではありません。
アプリケーションの中心は引き続き`WebgApp`であり、`Space`、`Node`、`Shape`、`ModelAsset`で組み立てる3D形状も、標準フォワード描画と遅延レンダリングで共通です。

第2版で大きく増えたのは、同じ3Dシーンに対して照明と最終描画の経路を選べることと、描画とは別にGPU上の状態を先に更新するGPU計算先行方式のフレームを選べることです。
全体の切り分けは次のようになります。

```text
WebgApp
  ├─ 共通基盤
  │    └─ 初期化、更新ループ、カメラ、入力、
  │       UI（User Interface、利用者向け操作画面）
  ├─ 共通の3Dシーン
  │    └─ Space、Node、Shape、ModelAsset
  └─ フレーム処理の選択
       ├─ 3Dシーンを描画する通常フレーム
       │    ├─ 標準フォワード描画
       │    │    └─ SmoothShaderによる直接照明
       │    └─ 遅延レンダリング
       │         └─ G-buffer + ComputeEffectPipeline
       └─ GPU状態を先に更新するGPU計算先行方式
            └─ computeFrame + ComputePass / GpuParticleEmitter
```

標準フォワード描画と遅延レンダリングの大きな違いは、形状の作り方ではなく、照明と画面効果をどこで解決するかです。
前者は`SmoothShader`が形状の描画時に直接照明を計算します。
後者は形状の表面情報をG-bufferへ保存し、`ComputeEffectPipeline`が照明と画面効果を後段で処理します。

GPU計算先行方式は、この照明経路の二者択一とは別の拡張です。
粒子、布、物理計算、テクスチャ生成のように、GPU状態の更新順序そのものをアプリケーションが決め、必要なGPUコマンドを自分で記録したい場合に使います。
GPU計算先行方式のフレーム内で更新結果を描画することもできますが、`WebgApp`による標準シーン描画は自動では行われません。

この図を移行の出発点にすると、既存コードをすべて書き直す必要はありません。
まず現在のアプリケーションがどの経路に属するかを判断し、共通規則とその経路に固有の規則だけを確認します。

## まず既存アプリケーションを分類する

### 標準フォワード描画だけを使う場合

`WebgApp`、`Space`、標準シェーダーを使う通常のアプリケーションは、構造を維持したまま移行できます。
標準入口は、カメラ用Reverse-Z、カメラ相対レンダリング、同一フレームのカメラ状態を内部で扱います。

この場合は、まず1.0のコードを大きく変更せずに起動し、次を確認します。

- 独自シェーダーが古い深度規則を前提にしていないか
- 独自の描画パスが`depth24plus`や`less`を固定していないか
- カメラ位置をWGSL内で巨大なワールド座標から減算していないか
- 完成テクスチャの表示を独自に管理していないか

該当しなければ、コンピュート関連のクラスを導入する必要はありません。
半透明材質も`Shape`の`alpha`から自動分類されるため、単純なシーンでは透明用レンダーパスを追加せず、この構成を維持できます。

### 遅延レンダリングへ移行する場合

同じ`Space`と`Shape`を使いながら、G-buffer、SSAO、シャドウ、遅延照明、SSR、DoF、ブルームなどを組み合わせる場合は、`ComputeEffectPipeline`を中心に構成します。

この経路では、形状の材質情報、カメラ深度、`cameraFrame`、線形HDR、最終表示が、決められた入力形式と実行順序でつながります。
個々のパスだけを正しく呼び出しても、フレームや色空間が異なれば正しい画像にはなりません。

半透明三角形はG-bufferへ書かれませんが、利用側が別のレンダーパスを挿入する必要はありません。
`ComputeEffectPipeline`が不透明照明とSSRの後に自動合成し、合成済みHDRシーンへフォグ、トゥーン、DoF、ブルームを適用します。
その後にトーンマッピング、輪郭抽出、ビネットを適用して表示用テクスチャを返します。

### 個別の画面効果だけを接続する場合

レンダーシェーダー版`DofPass`のように、通常フレームへ個別の効果を手動接続する構成も維持できます。
この場合は、完全なカメラ状態を渡す`cameraFrame`ではなく、同一フレームであることを証明する`renderFrameToken`を使うAPIがあります。

色だけを処理するぼかしやビネットは、カメラ深度を読まない限り、`cameraFrame`や`renderFrameToken`を必要としません。
必要性はコンピュートシェーダーを使うかどうかではなく、深度から位置や距離を復元するかどうかで判断します。

### GPU計算先行方式へ移行する場合

GPUパーティクル、布、物理シミュレーション、テクスチャ生成のように、コンピュートパスの結果を同じフレームのレンダーパスで利用する場合は、`WebgApp({ computeFrame: true })`と`onComputeFrame`を使います。

この経路ではアプリケーションがコマンドエンコーダーを作り、コンピュートパス、レンダーパス、計測処理を必要な順に記録し、最後に送信します。
通常フレームの`onBeforeDraw`や`onAfterDraw3d`へ処理を分散させません。

## 全経路で共有する移行規則

描画経路が異なっても、カメラ深度、座標空間、カメラ状態の意味と、各GPUリソースをどのクラスが生成、保持、リサイズ、破棄するかは共通の基盤です。
独自パイプラインや独自WGSLを持つアプリケーションは、ここから確認してください。

## EyeRigの姿勢と親子関係を確認する

1.0でCameraのrollはすでに`EyeRig`のorbit rod姿勢へ移っています。
2.0ではさらに、Orbit、First Person、Followの各modeで、base、rod、eyeが担当する姿勢を分離しました。
Cameraを独自Node階層へ組み込んでいる場合は、数値だけを移すのではなく、どのNodeが親の移動と回転を継承するかを確認します。

Orbitでは、baseが周回中心、rodがyaw、pitch、roll、eyeが距離を担当します。
回転する物体の子へbaseを置けば、その物体の姿勢もCameraへ継承されます。
親の位置だけを使い、回転を継承したくない場合は、アプリケーション側で独立したCamera anchorを作ります。

First Personでは、bodyの進行方向を`bodyYaw`、視線だけの左右回転を`lookYaw`として分けます。
ドラッグで周囲を見ても、`W / A / S / D`の移動方向を不用意に変えません。
Cameraの前方はlocal `-Z`なので、モデルの前方軸が`+Z`なら、親子関係または`bodyYaw`で明示的に一致させます。

Followでは、baseを追跡対象の位置へコピーしません。
baseはCameraを設置した親階層に残り、eyeのlocal quaternionが実際のtarget位置へ滑らかに向きます。
`targetOffset`はtarget Nodeのlocal座標として解釈されます。
1.0のFollowでbaseがtargetへ追従することを移動処理として利用していた場合は、追跡対象とCamera anchorを別Nodeとして構成し直します。
具体例は`samples/eye_rig`で、回転する親の下のOrbit、独立視線を持つFirst Person、姿勢追跡するFollowを比較できます。

## 通常カメラをReverse-Zへ移行する

通常カメラの深度は、形式、クリア値、比較関数、投影行列をまとめてカメラ用Reverse-Zへ変更します。
どれか一つだけを変更すると、描画パスとパイプラインが一致しないか、形状が背景に隠れます。

webg 1.0の通常カメラ用パイプラインに`depth24plus`、クリア値1、`less`または`less-equal`が残っている場合は、`CAMERA_REVERSE_Z`を基準に書き換えます。

```js
import { CAMERA_REVERSE_Z } from "./webg/DepthConvention.js";

const pipeline = device.createRenderPipeline({
  // 頂点処理、フラグメント処理などは省略
  depthStencil: {
    format: CAMERA_REVERSE_Z.format,
    depthWriteEnabled: true,
    depthCompare: CAMERA_REVERSE_Z.compare
  }
});
```

4引数の`Matrix.makeProjectionMatrix(near, far, vfov, aspect)`も、通常カメラ用Reverse-Z投影として扱います。
独自パイプラインの深度設定と投影行列を同じ規則へ揃えてください。

深度形式、クリア値、比較関数、`compareEqual`、背景深度、距離復元、画面固定表示での`always`、規則オブジェクトの検証は、第27章「通常カメラではReverse-Zを使う」を参照してください。
投影行列の数式と第5引数によるシャドウ用投影は、第3章「透視投影行列と視野角」を参照してください。

## シャドウ深度はStandard-Zのまま扱う

通常カメラをReverse-Zへ移行しても、方向光とスポットライトのシャドウマップは`SHADOW_STANDARD_Z`を使います。
1.0で通常カメラとシャドウマップが同じ深度設定を共有している場合は、カメラを`CAMERA_REVERSE_Z`、シャドウを`SHADOW_STANDARD_Z`へ分離します。
両方とも`depth32float`ですが、クリア値、比較関数、nearとfarの意味は反対です。

二つの深度規則と規則オブジェクトの同一性検証は、第27章「通常カメラではReverse-Zを使う」を参照してください。
方向光とスポットライトのシャドウを統合する方法は、第28章「シャドウマップで直接光の遮蔽を表す」を参照してください。

## ワールド座標をカメラ相対座標へ変換する

広いワールドを扱う場合は、ワールド座標の差をJavaScript側で先に求め、GPUへカメラ付近の小さな座標を渡します。
GPUの`float32`行列上で巨大な物体位置とカメラ位置を相殺すると、差を求める前に細かな位置情報が失われます。

webg 2.0では、ワールド位置の差をJavaScriptの`Number`で計算してから、カメラ相対のモデルビュー行列をGPUへ渡します。
標準の`Space.draw()`と`WebgApp`は、この変換を内部で行います。
独自WGSLで巨大な`worldPosition - cameraPosition`を計算している場合は、標準のカメラ相対モデルビュー行列を受け取る構成へ移します。

メッシュ頂点、ボーンパレット、Node、物理、音源と、GPUへ渡すカメラ相対座標の境界は、第27章「カメラ相対座標へ変換してからGPUへ渡す」を参照してください。

## Space.setEyeによる1.0互換経路を使う

webg 2.0の`Space`は、`WebgApp`を使わないwebg 1.0の低水準なアプリケーションを移行できるよう、`Space.setEye(eye)`と引数なしの`Space.draw()`を互換機能として維持します。

```js
const space = new Space();
const eye = space.addNode(null, "eye");
eye.setPosition(0.0, 0.0, 10.0);

space.setEye(eye);

const drawFrame = () => {
  screen.clear();
  space.draw();
  screen.present();
  requestAnimationFrame(drawFrame);
};
drawFrame();
```

この呼び出し順を維持する場合は、`setEye()`を削除する必要はありません。
新しいコードで視点を明示する場合は`space.draw(eye)`も使用できます。

既定の視点、明示引数の優先、視点がない場合の例外、`cameraFrame`および`renderFrameToken`との使い分けは、第22章「既定の視点とSpace.draw()」を参照してください。

## 同じcameraFrameを描画パス間で共有する

G-bufferと深度依存パスを接続するときは、描画直前に確定した同一の`cameraFrame`を共有します。
1.0のコードが各パスで視点、`near`、`far`、画角、投影行列を作り直している場合は、その処理を削除します。
`WebgApp`の同じコールバックから受け取った`cameraFrame`を、`renderScene()`と`encode()`へそのまま渡します。

`cameraFrame`が保持する情報と`renderFrameToken`との違いは、第27章「カメラフレームで描画状態を確定する」を参照してください。
`ComputeEffectPipeline`への接続コードと同一オブジェクトの検証は、第29章「同じカメラフレームで描画と位置復元を一致」を参照してください。

## 手動接続ではrenderFrameTokenを共有する

完全なカメラフレームを公開する必要がない手動接続では、`renderFrameToken`を使います。
1.0の手動DoF接続が視点や投影値を個別に渡している場合は、同じコールバックの`renderFrameToken`をシーン開始、`Space.draw()`、DoF合成へ渡す構成へ移します。

トークンの性質と必要になる条件は、第27章「カメラフレームで描画状態を確定する」を参照してください。
レンダーシェーダー版`DofPass`の完全な接続コードは、第20章「DofPassの実装と活用」を参照してください。

## 遅延レンダリング固有の移行規則

標準フォワード描画では、`SmoothShader`が形状ごとに照明を計算します。
遅延レンダリングでは、`GeometryBufferPass`が同じ`Shape`の表面情報をG-bufferへ保存し、`DeferredLightingPass`が後から照明を計算します。
この違いによって、G-bufferへ必ず渡す材質値と、各処理段階で使える色形式が増えます。

## G-buffer用の材質情報を完成させる

遅延レンダリングへ渡す`Shape`には、照明前のアルベド、法線、鏡面反射、粗さ、金属度、発光を指定します。
不足値をG-buffer側で推測させません。
1.0の材質へ`specular`、`roughness`、`metallic`、`emissive`がない場合は、各表面の意味に応じた有限値を追加します。
`color`の4番目の値へSSRの反射率を格納している場合は、色と反射特性を独立した材質値へ分けます。

標準フォワード描画と遅延ライティングで各材質値の意味がどう変わるかは、第28章「標準シェーダーから材質値を読み替える」を参照してください。
統合パイプラインへ渡す完全な材質のコード例と検証は、第29章「完全なG-buffer材質で照明結果を安定させる」を参照してください。

## Shapeの複数マテリアルへ移行する

1.0の`Shape`は、`setMaterial()`で設定した一つの材質を`Shape`全体へ使用していました。
2.0では一つの`Shape`が連続した材質スロット配列を持ち、各三角形が使用するスロット番号を保持します。
マテリアル境界のためだけに頂点を複製する必要はありません。

既存コードとの互換性のため、`setMaterial()`、`getMaterial()`、`updateMaterial()`は材質スロット0を操作します。
`addTriangle()`と`addPolygon()`の材質番号を省略した場合も0です。
したがって、1.0の`Shape`作成コードは、一つのスロット0を全三角形で使うコードとしてそのまま動きます。

追加材質は、0から途切れないスロット番号で登録します。

```js
const shape = new Shape(gpu);

shape.setMaterial("smooth-shader", {
  color: [0.84, 0.28, 0.10, 1.0],
  alpha: 1.0,
  specular: 0.6,
  roughness: 0.32
});

shape.setMaterialAt(1, "smooth-shader", {
  color: [0.15, 0.65, 1.0, 1.0],
  alpha: 0.42,
  specular: 1.0,
  roughness: 0.18,
  power: 128
});

shape.addTriangle(a, b, c);     // 材質スロット0
shape.addTriangle(a, c, d, 1);  // 材質スロット1
shape.endShape();
```

設定済みの材質スロットの参照と差分更新には`getMaterialAt(index)`と`updateMaterialAt(index, params)`を使います。
すでに追加した三角形の割り当ては、`endShape()`より前なら`setTriangleMaterial(triangleIndex, materialIndex)`で変更できます。
材質スロットを飛ばした登録、存在しないスロット番号、範囲外の`alpha`は、スロット0へ補正されず例外になります。

描画透明度は材質の独立した`alpha`で指定します。
`color[3]`は1.0互換のテクスチャ混合率という従来の意味を保つため、透明度として読み替えません。
`alpha`を省略した既存材質は1.0、すなわち不透明として扱われます。

材質スロットの設定、取得、差分更新、`getMaterialAt(index)`が返す浅い複製、インスタンスごとの独立性は、第7章「一つのShapeで複数マテリアルを使う」を参照してください。
三角形への材質番号の割り当てと`endShape()`で確定される描画情報は、第23章「三角形ごとに材質スロットを指定する」を参照してください。

## 半透明を自動描画へ移行する

1.0で`Shape`全体を不透明または半透明へ分類している処理は削除し、材質スロットごとの`alpha`へ移します。
`alpha === 1.0`は不透明、`0.0 <= alpha < 1.0`は半透明として、2.0が三角形単位で自動分類します。
`color[3]`は従来のテクスチャ混合率のまま保ち、描画透明度へ読み替えません。

標準フォワード描画では、半透明三角形の収集、奥から手前への整列、アルファ合成を`Space`へ任せます。
遅延レンダリングでは、利用側が透明用レンダーパスや`FrostedGlassPass`を挿入せず、`ComputeEffectPipeline`内部の`TransparencyPass`へ任せます。
すりガラスの背景ぼけは材質の`roughness`で指定し、旧ぼかし半径や反復回数を移行先の設定として残しません。

材質の`alpha`と`color[3]`、自動分類の基本は、第7章「マテリアル設定の仕組み」を参照してください。
標準描画と統合パイプラインの透明処理、すりガラス、制限事項は、第20章「ComputeEffectPipelineでは半透明を自動合成する」と第29章「半透明を材質から自動統合する」を参照してください。

移行確認には`samples/opacity`を使います。
一つの`Shape`に不透明と半透明の材質スロットを持たせた状態、`Shape`をまたぐ三角形の整列、`alpha`が1.0での経路切り替え、`roughness`による透明背景と鏡面反射の変化を確認できます。

## SSAOとシャドウを可視率として渡す

1.0でSSAO（Screen Space Ambient Occlusion、画面空間の環境遮蔽）またはシャドウの処理が完成色を返している場合は、2.0では可視率を返す処理へ移します。
可視率は1が遮蔽なし、0が完全な遮蔽を表し、材質色や発光色を含みません。
環境遮蔽と直接光の遮蔽を色へ反映する処理は`DeferredLightingPass`へ集約します。

SSAOの入力、可視率、設定値は、第28章「SSAOで接地感と隅の奥行きを補う」を参照してください。
シャドウ可視率と照明への結合は、第28章「シャドウマップで直接光の遮蔽を表す」を参照してください。
環境光、直接光、発光の役割は、第28章「遅延照明で多数の光源を評価する」を参照してください。

## ローカルライトの種類を明示する

1.0の光源情報に種類がない場合は、2.0で各光源へ`type: "point"`または`type: "cone"`を追加します。
種類がない光源を点光源として推測させません。
コーン光源へ移す場合は、`direction`、`innerAngle`、`outerAngle`も明示します。

各設定値の意味、許容範囲、点光源とコーン光源の使い分けは、第28章「ローカルライトを調整する」を参照してください。
光源と材質を結合する処理は、第28章「遅延照明で多数の光源を評価する」を参照してください。

## 線形HDRと表示色を分離する

1.0の各処理が中間色へ個別に露出、ガンマ補正、0から1への切り詰めを行っている場合は削除します。
2.0では遅延照明からブルームまでを`rgba16float`の線形HDR（High Dynamic Range、広い輝度範囲）で接続し、露出、トーンマッピング、sRGB変換を最終表示の境界で一度だけ行います。
表示値を格納した`rgba8unorm`をさらに`rgba8unorm-srgb`へ書き込み、sRGB変換を二重に適用してはいけません。

各テクスチャ形式と色の意味は、第27章「接続前に確認する4つの前提条件」を参照してください。
線形HDRから表示までの処理順序は、第29章「出力の意味に沿って統合順序を決める」を参照してください。
トーンマッピング、sRGB変換、背景色、輪郭抽出の接続条件は、第29章「色の意味を保ったまま表示へ渡す」を参照してください。

## フォグを統合パイプラインへ移行する

1.0の標準フォワード描画では、`WebgApp.setFog()`で設定したフォグを`SmoothShader`が形状の描画中に評価します。
遅延レンダリングへ移行する場合は、フォワード描画側のフォグを無効にし、設定を`ComputeEffectPipeline`の`fog`へ移します。
両方を同じシーンへ適用すると距離減衰が二重になるため、フォグを担当する経路を一つにします。

統合パイプラインでは`fogEnabled`または`fog.enabled`で有効化し、`mode`、`color`、`near`、`far`、`density`を`fog`へ渡します。
フォグは透明合成後の線形HDRシーンへ一度だけ適用され、距離は同じ`cameraFrame`と不透明なG-buffer深度から復元されます。

設定値の意味、既定値、線形方式と指数方式の違い、透明面と背景深度の制限は、第28章「フォグで距離に応じた空気の厚みを表す」を参照してください。
`ComputeEffectPipeline`内での位置と二重適用を避ける方法は、第29章「透明合成後のフォグを一つのパスへ集約する」を参照してください。

## ビネットを統合パイプラインへ移行する

1.0アプリケーションが最終表示の直前に独自の`VignettePass`を接続していた場合は、統合パイプラインのビネットと二重に有効化しません。
設定値を`ComputeEffectPipeline`の`vignette`へ移し、ビネットを一つに集約します。

統合パイプラインでは`vignetteEnabled`または`vignette.enabled`で有効化し、`center`、`radius`、`softness`、`strength`、`tint`を渡します。
ビネット後の最終テクスチャを`beginPresentPass()`で表示し、その後にHUD用の深度付きパスへ戻します。

設定値の意味、既定値、画面の縦横比補正は、第28章「ビネットで画面周辺の見せ方を整える」を参照してください。
統合順序とHUDへの影響を避ける方法は、第29章「ビネットを最終表示の直前へ集約する」を参照してください。

## コンピュート版DoFの距離復元を揃える

1.0のDoFが投影値や`near`、`far`を個別に受け取っている場合は、距離復元の基準を同じフレームの`cameraFrame`へ移します。
`ComputeDofPass`には、線形HDRのシーン色、カメラ用Reverse-Z深度、同じG-buffer描画に使った`cameraFrame`を渡します。
DoF専用の投影値を重複して組み立てません。

レンダーシェーダー版`DofPass`を手動接続する場合は、同じ`renderFrameToken`をシーン開始、`Space.draw()`、DoF合成へ渡します。
`ComputeDofPass`は完全なカメラ状態を共有し、`DofPass`は手動接続した描画とのフレーム同一性を証明する、という違いがあります。

`ComputeDofPass`の画像ピラミッド、コード例、設定値の意味、既定値、範囲、診断表示は、第28章「DoFで焦点と奥行きを伝える」を参照してください。
統合パイプラインでの有効化と処理順序は、第29章「効果の状態を一箇所に集めて安全に切り替える」を参照してください。

## ブルームを線形HDRへ接続する

1.0の表示色または個別の露出設定を使うブルームは、トーンマッピング前の線形HDRシーンを入力とする`ComputeBloomPass`または`ComputeEffectPipeline`へ移します。
露出と表示色変換はブルームへ含めず、最終トーンマッピングで一度だけ行います。

既存コードに段階別のしきい値、強度、ぼかし回数がある場合は削除し、現行APIの設定値へ置き換えます。
現行ブルームでは`threshold`と`softKnee`で抽出対象を決め、1/2から1/32までの各段階の重みで広がりを決め、`filterRadius`と`strength`で滑らかさと全体量を調整します。

`ComputeBloomPass`の画像ピラミッド、コード例、全設定値の意味、既定値、範囲、調整順序は、第28章「画像ピラミッドでブルームを構成する」を参照してください。
統合パイプラインで処理自体を省略する方法は、第29章「派生ターゲットの解像度から計算量を調整する」を参照してください。

## 完成テクスチャをキャンバスへ表示する

遅延レンダリングやポストプロセスの完成テクスチャは、`Screen.beginPresentPass()`でキャンバスへ表示します。
`Screen.beginPass({ depthView: null })`を最終表示の代用にしません。

```js
app.screen.beginPresentPass({
  clearColor: app.clearColor,
  colorLoadOp: "clear"
});

copyPass.draw(finalColor);
app.screen.clearDepthBuffer();
```

画面固定表示やHUDを後から描く場合は、表示パスの後に`clearDepthBuffer()`で深度付きパスへ戻します。
最終出力をキャンバスへ直接コピーできる場合でも、フォーマットと色空間が一致することを確認します。

表示パスの完全な接続例、負荷を減らす直接コピー、HUDを後置する理由は、第29章「beginPresentPass()で表示する」を参照してください。

## GPU計算先行方式に固有の移行規則

GPU計算先行方式では、`WebgApp`は初期化、入力、UI、時刻、カメラ、`Screen`を引き続き提供します。
ただし標準の`Space.draw()`は実行せず、`onComputeFrame`の中でコマンドエンコーダーを作成し、コンピュートパスとレンダーパスを必要な順に記録して、最後に一度だけ送信します。

```js
const app = new WebgApp({
  computeFrame: true
});

app.start({
  onComputeFrame: ({ cameraFrame, deltaSec }) => {
    const gpu = app.getGPU();
    const encoder = gpu.device.createCommandEncoder();

    simulation.encode(encoder, resources, { deltaSec });
    renderer.encode(encoder, cameraFrame);

    // フレーム全体の送信はアプリケーション側で行う
    gpu.queue.submit([encoder.finish()]);
  }
});
```

`ComputePass.encode()`は、指定されたコマンドエンコーダーへコンピュートパスを追加しますが、送信は行いません。
コンピュート処理と描画の実行順、タイムスタンプ問い合わせ、交互に使うリソースの切り替えを呼び出し側が管理します。

通常フレームとの違い、`computeFrame`、`onComputeFrame`、一括送信の設計は、第27章「コンピュート-first（計算先行）」を参照してください。

### GPUパーティクルの宣言を明示する

`GpuParticleEmitter`へは、粒子バッファの座標空間と描画先の深度規則を明示します。
値がない場合に旧挙動を推測させません。

```js
const gpu = app.getGPU();
const emitter = new GpuParticleEmitter(gpu, {
  targetFormat: gpu.format,
  depthConvention: CAMERA_REVERSE_Z,
  coordinateSpace: "camera-relative",
  // 粒子数、WGSL、uniform定義などは省略
});
```

`depthConvention`は描画先の深度アタッチメントと一致させます。
`coordinateSpace: "camera-relative"`は、ストレージバッファの位置をカメラ相対座標として扱うことを宣言します。
更新WGSLと描画WGSLでも、同じ座標の意味を維持します。

粒子の更新アルゴリズムや物理規則はアプリケーション固有です。
`GpuParticleEmitter`はバッファ、パイプライン、各パスへの記録、破棄を内部で行います。
ただし、フレーム全体のコマンドエンコーダーは作成せず、`queue.submit()`も呼びません。

宣言項目、交互に使うバッファ、更新と描画の接続例は、第28章「GPUパーティクルを更新する」を参照してください。

## 追加APIは必要な場合だけ採用する

2.0で追加されたすべてのクラスを、1.0のアプリケーションへ導入する必要はありません。
`CommandPalette`はキャンバス上の設定変更とコマンド実行をまとめる利用者向け操作画面、`FrameTimer`はGPUタイムスタンプとJavaScript時間の計測、`ComputePass`と`StorageTargetFactory`はコンピュートパイプラインとストレージリソースの構築、`PingPongBuffer`、`PingPongTexture`、`PingPongTarget`は反復計算の入出力交換を共通化するための追加APIです。

既存の`OverlayPanel`、DOM（Document Object Model）を使う独自操作画面、通常のレンダーパスを使うアプリケーションは、それだけを理由に書き換えません。
新しいAPIは、同じリソース管理、検証、記録順序をアプリケーションごとに重複している場合に採用します。

## Shapeの法線とUV継ぎ目を確認する

1.0の`Shape`を移行した後にUV継ぎ目だけが暗くなる場合は、照明処理を変更する前に、自動法線と手動法線を混在させていないか確認します。
`setAutoCalcNormals(false)`を使う形状では、すべての頂点へ有限な単位法線を渡し、UV継ぎ目で複製した頂点にも同じ完成法線を設定します。

自動法線の蓄積と正規化、手動法線の契約、UV継ぎ目での複製処理、症状別の確認方法は、第23章「法線の正規化とシーム処理」を参照してください。

## resizeとdestroyの呼び出し先を決める

第2版では中間テクスチャやストレージバッファが増えるため、生成だけでなく再生成と破棄も移行対象です。
同じリソースを複数の箇所で生成または破棄すると、古い寸法のテクスチャビュー、破棄後のバッファ、二重破棄が残ります。

`ComputeEffectPipeline`を生成して保持するアプリケーションは、キャンバスの実ピクセルが変わったときに`resize(width, height)`を呼びます。
アプリケーション終了時や構成の作り直しでは、パイプラインを生成して保持する箇所から一度だけ`destroy()`を呼びます。
個別の処理を直接生成する場合も、所有する箇所を一つに決め、同じリソースをパイプライン側と利用側の両方から破棄しません。

個別の処理を安全にリサイズする方法は、第28章「リサイズ時のずれとリークを防ぐ」を参照してください。
統合パイプラインの所有権と一括破棄は、第29章「リソースの生成と破棄を集約する」を参照してください。

## 1.0の実装から移行箇所を見つける

既存コードを検索するときは、API名だけでなく、古い前提を表す値も探します。

- `depth24plus`、クリア値1、`less`：通常カメラなら
  `CAMERA_REVERSE_Z`へ移行する
- 通常カメラとシャドウで同じ深度設定：カメラ用Reverse-Zと
  シャドウ用Standard-Zへ分離する
- WGSL内の巨大な`worldPosition - cameraPosition`：JavaScript側の
  カメラ相対モデルビュー変換へ移す
- パスごとに作る投影配列：同じ`cameraFrame`を共有する
- 手動接続のDoFへ渡す`view`や`cameraFrame`：
  同じ`renderFrameToken`を渡す
- G-buffer材質の固定補完：`Shape`または材質ローダーで
  `specular`、`roughness`、`metallic`、`emissive`を完成させる
- `Shape`全体を透明として扱う独自分岐：材質の`alpha`と三角形の
  材質スロットへ移し、`Space`の自動分類を使う
- `color[3]`を描画透明度として使う処理：従来のテクスチャ混合率のまま保持し、
  独立した`alpha`へ移す
- 半透明用レンダーパスや`FrostedGlassPass`の手動挿入：
  `ComputeEffectPipeline`内部の`TransparencyPass`へ任せる
- 遅延レンダリングへ残した`WebgApp.setFog()`や`SmoothShader`のフォグ：
  フォワード側との二重適用をやめ、統合パイプラインの`fog`へ設定を移す
- トーンマッピング後に手動接続した`VignettePass`：
  統合パイプラインの`vignette`へ設定を移し、
  `ComputeVignettePass`と二重に適用しない
- SSAOやシャドウが返す完成色：可視率を返し、遅延照明で色と結合する
- 種類のないローカルライト：`type: "point"`または`type: "cone"`を付ける
- 中間パスの`exposure`やガンマ変換：最終トーンマッピングへ集約する
- SSRをアルベドのalphaへ格納：独立したHDR反射テクスチャへ分ける
- `Screen.beginPass({ depthView: null })`による最終表示：
  `beginPresentPass()`へ移行する
- 独自GPU粒子の暗黙の座標と深度：`coordinateSpace`と
  `depthConvention`を明示する
- 各コンピュートパス内の`queue.submit()`：コマンドエンコーダーを作成した
  フレーム処理の
  最後へ集約する
- リサイズ時に再生成しない中間テクスチャ：そのテクスチャを生成したクラスの
  `resize()`で更新する

## 描画条件を順番に確認する

複数の規則を同時に変更すると原因を切り分けにくいため、次の順で確認します。

1. アプリケーションが標準フォワード、遅延レンダリング、
   GPU計算先行方式のどれを使うか分類する
2. `WebgApp`、`Space`、`Shape`など共通基盤を維持できる範囲を確認する
3. 通常カメラの形式、クリア値、比較関数、投影をReverse-Zへ揃える
4. シャドウ深度をStandard-Zとして分離する
5. ワールド座標とカメラ相対座標の境界を確認する
6. 深度依存パスへ同じ`cameraFrame`または`renderFrameToken`を渡す
7. 遅延レンダリングでは材質、可視率、ライト種別を完成させる
8. 複数マテリアルでは材質スロットを連続登録し、三角形へ正しい
   スロット番号を割り当てる
9. 半透明では`color[3]`ではなく独立した`alpha`と`roughness`を設定する
10. フォグは透明合成後のHDRシーンへ適用し、不透明G-buffer深度を共有する
11. 線形HDRから表示sRGBまでの変換をトーンマッピングで一度だけ行う
12. ビネットはトーンマッピングと輪郭抽出の後、最終表示とHUDの前へ置く
13. GPU計算先行方式では一つのフレーム処理でエンコーダーを作り、
    順番に記録して送信する
14. `resize()`と`destroy()`は、そのリソースを生成して保持するクラスから呼ぶ
15. 形状、深度、法線、照明、背景、透明合成、画面効果を段階的に有効化する

不足項目を固定値で補う、異なる深度規則を形式だけで同一視する、フレーム識別を値の比較で代用するといった暗黙のフォールバックは、移行途中の誤りを見えにくくします。
webg 2.0の例外は、どの引数が不足し、どの形式や値が必要なのかを呼び出し側へ示します。
例外を固定値で回避せず、呼び出し側の入力を修正してください。

## 移行結果を三つの層で確認する

移行後の確認は、一種類のテストだけで完結させません。
目的の異なる三つの層を使い分けます。

- `headless_tests/core/`：深度規則、引数検証、色形式、各リソースを生成・破棄する
  クラスなど、人が画面を操作しなくても判定できるコアの必須条件を確認する
- `unittest/`：ブラウザで人が操作し、入力や表示を確認する小規模なPOCを使う
- `samples/`：実際のアプリケーション規模で、複数機能の統合と画面結果を確認する

標準フォワードと遅延レンダリングの切り替えは`materials`、手動接続のDoFは`dof`、統合された遅延レンダリングは`compute_deferred_lighting`や`compute_effect`が参考になります。
GPU計算先行方式は`compute_particles`、`compute_cloth`、`compute_physics_bounce`、`compute_texture`で、GPU更新と描画をどの順序で記録し、どの箇所で送信するかを確認できます。

複数マテリアルと半透明の確認には`opacity`を使います。
標準フォワードの単純な用途でも材質の`alpha`による分類は自動ですが、このサンプルでは`ComputeEffectPipeline`への透明統合、粗さのマスクによるすりガラス背景、半透明合成後のフォグ、トゥーン、DoF、ブルーム、トーンマッピング、輪郭抽出、ビネットまで確認できます。

フォグとビネットを含む統合パイプライン全体の移行確認には`compute_effect`を使います。
`CommandPalette`からフォグの`mode`、色、距離、`density`と、ビネットの`center`、`radius`、`softness`、`strength`、`tint`を変更でき、透明合成後のフォグとHUD前のビネットを同じシーンで比較できます。
