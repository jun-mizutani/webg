# 物理イベント、設定、更新

## この章の読み方

### 初回に読む範囲

### 必要になったときに読む範囲

## 接触イベントとクエリAPI

`PhysicsSpace` は、直近のステップで発生した接触情報を保持しており、これをアプリケーション側で利用できます。

```js
physics.step(deltaMs);

for (const contact of physics.getLastContacts()) {
  console.log(
    contact.bodyA.getName(),
    contact.bodyB.getName(),
    contact.normal,
    contact.penetration
  );
}
```

また、接触の開始、継続、終了をリスナーで受け取ることも可能です。

```js
const offBegin = physics.onBeginContact((event) => {
  console.log("begin", event.bodyA.getName(), event.bodyB.getName());
});

const offEnd = physics.onEndContact((event) => {
  console.log("end", event.bodyA.getName(), event.bodyB.getName());
});

// 不要になったら解除する
offBegin();
offEnd();
```

なお、トリガーボディ（`isTrigger: true`）は接触イベントへ記録し、物理的な押し戻しや反発を伴わないセンサーとして扱います。
ゴール判定や範囲侵入判定、センサーなどの用途に適しています。

```js
const sensor = space.addPhysicsNode(null, "sensor", {
  bodyType: "static",
  isTrigger: true
});
sensor.setCollider(new BoxCollider([6.0, 3.0, 6.0]));
physics.addBody(sensor);
```

### 物理空間への問い合わせAPI

接触解決とは別に、物理空間の状態を調べるための問い合わせAPIが提供されています。

#### `raycast()` と `raycastAll()`

レイキャストは、始点から方向ベクトルへ線を伸ばし、最初の物体またはすべての物体を距離順に調べるために使います。
視点からの選択や、進行方向に障害物があるかを調べる用途に適します。

```js
const hit = physics.raycast(
  [0.0, 10.0, 20.0],
  [0.0, -0.2, -1.0],
  {
    maxDistance: 100.0,
    includeTriggers: false,
    layerMask: 0xffffffff
  }
);

if (hit) {
  console.log(hit.body.getName(), hit.position, hit.normal, hit.distance);
}
```

`raycast()` は最初にヒットした物体を返し、`raycastAll()` は条件に合うすべてのヒットを距離順に返します。

#### `queryAabb()`

`queryAabb()`は、軸平行境界ボックスの範囲へ重なるボディをまとめて取得するために使います。
広い領域から候補を絞り、後段で詳細な条件を調べる用途に適します。

```js
const bodies = physics.queryAabb(
  [-5.0, 0.0, -5.0],
  [ 5.0, 8.0,  5.0],
  {
    includeTriggers: true
  }
);
```

`queryAabb()` は、指定したAABB領域と重なるボディを返します。

#### `overlapSphere()`

`overlapSphere()`は、中心と半径で表す球形範囲へ重なるボディを調べるために使います。
爆発範囲、近接判定、球形センサーのように方向を持たない範囲検索に適します。

```js
const overlaps = physics.overlapSphere(
  [0.0, 4.0, 0.0],
  6.0,
  {
    triggerOnly: true
  }
);
```

`overlapSphere()` は、球状の範囲内に重なるボディを返します。
範囲攻撃や近接判定に有用です。

各クエリでは、`includeTriggers`、`triggerOnly`、`layerMask`、`filter` などのオプションを併用して対象を絞り込むことができます。

## コリジョンレイヤーとマスク

物理接触や問い合わせの対象を効率的に制御するために、コリジョンレイヤー（collision layer）とマスク（mask）を使用します。

```js
const PLAYER = 1 << 0;
const ENEMY = 1 << 1;
const SENSOR = 1 << 2;

player.setCollisionLayer(PLAYER);
player.setCollisionMask(ENEMY | SENSOR);

enemy.setCollisionLayer(ENEMY);
enemy.setCollisionMask(PLAYER);
```

2つのボディが接触候補になるには、双方のマスクが相手のレイヤーを含んでいる必要があります。

クエリ側では、`layerMask` オプションを使用して対象レイヤーを限定できます。

```js
const enemyHits = physics.overlapSphere(player.getPosition(), 12.0, {
  layerMask: ENEMY
});
```

## SceneYAMLによる物理設定の宣言

SceneYAMLでは、作品全体の重力や固定時間刻みを`physics.space`へ、各物体の質量や初速度を`objects[].physics`へ記述します。表示用のマテリアルと、反発・摩擦を表す物理マテリアルを分けて設定します。09章の`WebgSceneApp`が、定義の読み込みからCompute物理の更新、GPU状態の読み戻し、Node同期までを接続します。

次の例を`scene.yaml`へ保存すると、高さ8mから球が落下します。床は表示用のBoxと高さ0の物理Planeを組み合わせ、球には横方向の初速度とY軸まわりの角速度を与えます。

```yaml
format: webg-scene
version: 1

physics:
  space:
    gravity: [0.0, -9.8, 0.0]
    fixedTimeStepMs: 8.3333333333
    maxSubSteps: 8
    maxBodies: 1
    solverIterations: 10
    defaultRestitution: 0.0
    defaultFriction: 0.4
    planes:
      - normal: [0.0, 1.0, 0.0]
        planeDistance: 0.0

objects:
  - id: floor
    shape: {type: box, size: [20.0, 0.2, 20.0]}
    transform: {position: [0.0, -0.1, 0.0]}
    material: {color: [0.25, 0.3, 0.4, 1.0], metallic: 0.0, roughness: 0.5}
  - id: ball
    shape: {type: sphere, radius: 1.0}
    transform: {position: [0.0, 8.0, 0.0]}
    material: {color: [0.9, 0.3, 0.1, 1.0], metallic: 0.0, roughness: 0.25}
    physics:
      bodyType: dynamic
      mass: 1.0
      linearVelocity: [2.0, 0.0, 0.0]
      angularVelocity: [0.0, 90.0, 0.0]
      material: {restitution: 0.7, friction: 0.05}

renderer:
  profile: studio
  environment:
    preset: dark-studio
    resolution: {width: 128, height: 64}
```

`linearVelocity`は長さ／秒、`angularVelocity`は度／秒で指定します。この例では球がY軸まわりに毎秒90度で回転を始めます。初速度を省略した場合はゼロから開始します。

球の表示寸法と衝突寸法は`shape`を共有します。inline meshや外部モデルへ物理を付ける場合は、`physics.shape`へBox・Sphere・Capsuleを明示します。配置を増やす場合は、物理body数に合わせて`maxBodies`も設定します。Planeはこのbody数に含めません。

JavaScriptではシーンを生成して更新ループを開始します。初期化の完了後、内部のフレーム処理が固定stepと表示同期を進めます。

```js
import { createWebgSceneApp } from "../../webg/app/index.js";

const sceneApp = await createWebgSceneApp({
  project: "./scene.yaml",
  physics: {enabled: true, paused: false},
  camera: {target: [0.0, 2.0, 0.0], distance: 18.0}
});
sceneApp.start();
```

この節はSceneYAMLからCompute物理を使う方法です。次節ではCPU版`PhysicsSpace.step(deltaMs)`の内部更新順序を説明します。

## 物理更新のパイプライン

物理更新の順序は、フレームレートが変動しても同じ時間刻みで状態を進め、候補抽出、接触判定、応答、スリープを一貫した状態へ適用するために決まります。
この流れを理解すると、負荷を下げる対象と精度を上げる対象を段階ごとに選べます。
ここでは`PhysicsSpace.step(deltaMs)`の内部処理を順に説明します。

### 固定タイムステップの管理

ブラウザの `requestAnimationFrame` は実行間隔が一定ではないため、`PhysicsSpace` は `deltaMs` をアキュムレータ（蓄積変数）に溜め、`fixedTimeStepMs` ごとに `stepFixed(dtSec)` を実行します。
これにより、フレームレートの変動に関わらず物理挙動の安定性を維持しています。

### ブロードフェーズ（広域判定）

ブロードフェーズは、「衝突する可能性があるペア」を粗く抽出する段階です。

既定では `sweepAabb` モードが採用されており、有限なコリジョンをx軸方向にソートしてスキャンすることで、効率的に候補を絞り込みます。
検証用に全組み合わせを確認する `bruteForce` モードも提供されています。
`PlaneCollider` のような無限平面は特殊形状として扱い、常に候補に残るように制御されています。

### ナローフェーズ（詳細判定）

詳細判定では、広域判定で抽出された候補に対し、実際の接触法線とめり込み量を算出します。

`webg`では、一般的な形状ペアの接触計算をコリジョンクラス側（`Collider.buildContactWith()`）へ委譲しています。
一方、Box/BoxとPlane/BoxはCPUによるBox接触を使う形状ペアです。形状が混在する`PhysicsSpace`では`PhysicsContactDispatcher`がこのpairを明示的に選び、BoxとPlaneだけのSpaceでは`CpuBoxPhysicsAdapter`が同じ接触処理を`CpuBoxPhysicsSolver`へ接続します。Box/BoxのSATと代表接触点は`BoxContact.js`、Plane/Boxの支持点は`PlaneBoxContact.js`で計算します。
この分け方により、一般形状の追加と、CPUによるBox接触を同じ処理へ曖昧に混ぜずに拡張できます。

### ソルバー（解決器）

ソルバーは、ナローフェーズで得られた接触情報を基に、位置と速度を補正します。

1. トリガーボディを物理応答から除外。
2. 必要に応じてスリープ状態のボディをウェイク（wake）させる。
3. めり込み量に応じて位置を押し戻す（位置補正）。
4. 接触点速度 `v + omega x r` を用いて、法線方向の反発インパルスを適用。
5. 接線方向の速度に対し、摩擦インパルスを適用。
6. 線形速度、角速度、支持接触、接触速度の静止条件に基づき、スリープ候補を更新。

`solverIterations`（反復回数）を増やすことで、複数の物体が積み重なった際の安定性が向上しますが、計算負荷は増加します。

### スリープとウェイク

ボディが支持接触を持ち、線形速度、角速度、接触速度が一定のしきい値以下になった状態が`sleepStepsThreshold`回続くと、そのボディはスリープ状態に入ります。
`sleepAngularThreshold`の単位は度/秒です。
スリープ中のボディは積分処理から除外されるため、計算量を大幅に削減できます。
活動中の動的ボディやキネマティックボディと接触すると、再び起きて物理計算へ復帰します。

CPUによるBox接触では、Planeの支持点数、Box同士の支持接触、壁から受ける上向きの摩擦支持をsleep条件へ反映します。箱の姿勢を別の安定姿勢へ回転させる処理は行わず、接触solverが計算した位置、速度、角速度をそのまま次の判定へ渡します。
全dynamic bodyがスリープした場合は、保存済みの接触とイベントを利用してSpace全体のfast pathへ移ります。Space内に活動中のbodyが残る場合は、通常の接触探索とsolverを継続します。

## 現状の機能範囲と制限事項

本物理エンジンで効率的に実現できるのは、以下のような用途です。

- 床へ落下する箱や球体。
- 低い壁に囲まれた範囲で跳ねる球体。
- 反発係数や摩擦による挙動の検証。
- トリガー領域によるイベント判定。
- レイキャストやAABBまたは球体のオーバーラップによる空間問い合わせ。
- SceneYAMLによる物理ボディと空間設定の宣言。

一方で、以下の項目は現在の実装範囲外であり、将来的な拡張候補として検討しています。

- `BoxCollider` のブロードフェーズにおける完全なOBB最適化（現在は外接AABBを使用）。
- 任意の形状ペアを対象に、複数接点を一括して連立計算する解法。Compute版のBox面接触は、最大4点を順に処理する構成です。
- 非対角慣性テンソルの完全なサポート。
- 連続衝突判定（Continuous Collision Detection: CCD）。
- Jointのmotor、limit、break条件、ラグドール（Ragdoll）機能。

## 確認用ユニットテスト

物理挙動の正しさを検証するため、役割別に分かれたユニットテストを提供しています。

- `headless_tests/core/physics_node`: `PhysicsNode` 単体APIの規約確認。
- `headless_tests/core/physics_space`: 重力、固定タイムステップ、接触、クエリ、スリープ、レイヤーマスクなどの機能確認。
- `user/joint/core_test.js`: CPU版PhysicsSpaceへ四種類のXPBD Jointを登録し、位置補正、衝突抑止、body削除規則を確認する独立テスト。
- `unittest/physics_node_fall`: ボックスが落下して床で停止する最小構成の視覚確認。
- `unittest/physics_node_rotate`: 角速度、トルク、回転固定（fixedRotation）の視覚確認。
- `samples/physics_bounce`: 複数の球体が床や壁、球体同士で跳ねる公開サンプル。反発と相互作用を直感的に確認でき、`?count=1000` で負荷検証も可能です。
- `samples/compute_physics_bounce`: 球体の線形運動と相互衝突をコンピュートシェーダーで処理する比較用サンプル。GPU上の読み取り用と書き込み用を交互に交換するストレージバッファから直接インスタンス描画し、`?count=512`まで負荷を確認できます。
- `examples/27_01.html`: CPU版`PhysicsSpace`で床に箱を落下させる最小例。
- `examples/27_02.html`: Compute版`ComputePhysicsSpace`の計算結果をreadbackして通常の`Node`へ同期する、利用者側のWGSLが不要な基本例。
- `examples/27_03.html`: CPUとGPU間の転送を削減できるCompute版の高速化構成。`ComputePhysicsSpace`の`BodyState`を描画用WGSLから直接参照し、Computeと描画をGPU内で続ける例。
- `samples/project_app/project_app_sphere_plane_project.yaml`: SceneYAMLの表示形状、物理Plane、Compute bodyの設定例。
- `unittest/scene_mesh/check.mjs`: SceneYAMLのinline meshと明示した衝突形状の検査。

特に `samples/physics_bounce` は、物理エンジンらしい挙動を網羅的に確認できるため、動作検証の基準として活用してください。

### コンピュートシェーダー版との比較

`samples/compute_physics_bounce` は、GPU内での状態更新を理解するために球体へ範囲を絞ったCompute物理の例です。回転、スリープ、接触イベント、レイヤー、クエリAPIを含む汎用的な`PhysicsSpace`とは責務を分け、球体の状態更新と描画をGPU内で完結させています。

現在の`ComputePhysicsSpace`は、この比較用サンプルとは別に、Box、Sphere、local Y軸をクォータニオンで回転するCapsule、Planeを組み合わせた物理計算を公開APIとして提供します。
予測AABB、XZ Grid、body別candidate bitset、combined local solver、永続的なスリープ状態を持つため、CPU版との共通点を保ちながら、GPU上の多数bodyを対象にした処理フローを構成できます。
Compute版の利用方法と描画方法は、本章の「Compute版の物理エンジン」と`examples/27_02.html`、`examples/27_03.html`を参照し、WGSLとGPU処理の一般的な仕組みは20〜22章で確認してください。

コンピュートシェーダーでは、1つのインボケーションが1球体を担当します。
すべてのインボケーションが同じ前状態バッファを読み、自分の次状態だけを別バッファへ書きます。
読み取り用と書き込み用を交互に交換するピンポン方式により、複数のインボケーションが同じ球体へ同時に速度を書き込む競合を避けています。

球体同士の判定は理解しやすさを優先した全組み合わせの走査であり、計算量は球数を $N$ とすると $O(N^2)$ です。
そのため、大量球体向けの完成されたGPU物理エンジンではなく、次の項目を確認するための応用例です。

- 固定上限を持つストレージバッファ上の剛体状態。
- 重力、減衰、位置積分。
- 球体と平面・壁との衝突。
- 等質量球体間の反発インパルスと簡易摩擦。
- ピンポンバッファを使った競合回避。
- コンピュート結果をCPUへ戻さないインスタンス描画。

CPU版 `physics_bounce` は接触イベントやスリープを含むアプリケーション向けの物理機能を確認し、コンピュートシェーダー版は多数の独立状態をGPUで並列更新するデータフローを確認する、という役割の違いがあります。

## まとめ

`PhysicsSpace`は、物理ステップの結果を接触イベント、問い合わせ、スリープ状態としてアプリケーションへ返します。固定タイムステップ、レイヤー、Joint、CPU版とCompute版の比較を個別に確認すると、表示更新と物理更新の違いを整理できます。
物理計算の形状判定や接触ソルバーの内部処理を調べる場合は、42章「物理エンジンの詳細設計」を参照します。
