# UI Display Design

This chapter explains how to choose among a GPU-rendered HUD, DOM panels made from HTML elements, and touch controls that generate key input when adding information and controls to a 3D view. Use the length of the text, update frequency, whether the user interacts with it, and how much of the 3D view it covers to select an appropriate presentation method. This chapter organizes the UI types and selection criteria before implementation.

## How to read this chapter

### Prerequisites

### What to read first

Start with the criteria for choosing `Message`, `OverlayPanel`, a HUD (heads-up display), or the DOM (Document Object Model) according to the information being shown.

## Choose a UI Based on the Information

Different UI components suit frequently updated status, text that users need time to read, and input from the user. This chapter explains how to choose among a GPU-rendered HUD, DOM panels, command selection, and diagnostics based on information volume, update frequency, and interaction.

This is a design chapter about choosing UI components by purpose. Chapter 13 covers DOM options and combined implementations. Chapter 14 explains how to connect keyboard, pointer, and touch input to the same actions.

## Principles for Designing Text Displays

Dynamic visual experiences are a major attraction of 3D applications. To make them useful as well as engaging, combine the 3D objects with clear information presentation.

Explain the controls, show the current state, and describe loading progress or diagnostic results. You may also present dialogue, a story, or a tutorial. These elements help an application become an easy-to-use tool or an immersive experience.

Although all of these features display text, they have different requirements for update frequency, typography, and input. The information itself determines the features and update rates that a display needs. Examples include:

- A score or FPS (frames per second) value that changes every frame
- A concise control guide at the edge of the screen
- Multi-line help with multilingual text
- An error message when loading fails
- A detailed diagnostic report
- A briefing with buttons or choices
- A state record to share with developers or analysis tools
- On-screen buttons that replace keyboard input on touch devices

Managing all of these through one mechanism can make the UI cumbersome and reduce readability. Creating a separate class for every use case can also make it difficult to decide which API to use.

This chapter organizes text display in `webg` around the nature of the information. Rather than memorizing API names, use questions such as: Is this a short HUD value, text the user should read carefully, an interactive panel, or a record that should be saved?

## Overview of Display Paths

The UI display paths in `webg` fall into three broad groups:

- **Canvas HUD (`Text`, `Message`)**: Draws short Latin text, numbers, and symbols directly on the same canvas as the 3D scene.
- **DOM overlays (`OverlayPanel`, `CommandPalette`)**: Places multilingual text, longer content, buttons, choices, and scrollable panels over the scene.
- **Records and development tools (`Diagnostics`, `DebugDock`)**: Organizes internal state as reports that can be shared with developers or analysis tools.

| Information | Main components | Display surface |
|---|---|---|
| Score and short status | `Text`, `Message` | Canvas |
| Multilingual explanations and choices | `OverlayPanel`, `CommandPalette` | DOM |
| Diagnostic records and development state | `Diagnostics`, `DebugDock` | Report, development UI |

`Touch` also displays buttons on the screen, but it is an input API rather than a text-display API. Its buttons may look like those in an `OverlayPanel` or `CommandPalette`; their purpose is to replace key input. The later chapter on input explains it in detail.

Use these criteria when selecting an API:

- **Choose `Message`** for scores, lives, FPS, and other concise status values. As a lightweight canvas HUD, it suits frequent updates.
- **Choose `OverlayPanel`** for multilingual control instructions, help, errors, and longer text. Its DOM implementation supports Unicode text, variable-width fonts, scrolling, and buttons.
- **Choose `OverlayPanel` with an application controller** for button prompts, choices, and briefings when presentation and flow logic should remain separate.
- **Choose `CommandPalette`** for a temporary command menu over the canvas or simple setting changes that users open with a specific action.
- **Choose `Diagnostics` or `DebugDock`** for investigation logs and state records to share with analysis tools. Their purpose is recording and sharing, as well as display.
- **Choose `Touch`** for a touch interface that provides input in place of a keyboard.

## HUD and DOM Fundamentals

The distinction between HUD and DOM helps place frequently updated status and readable, interactive information on suitable surfaces. It keeps long text out of the GPU render path and avoids sending per-frame values through unnecessary DOM updates.

A HUD originally projected information into an aircraft pilot's field of view so it could be read without looking away from the forward view. Computer graphics and games use the same idea: scores, health, FPS, and other supporting information appear in the foreground while the user keeps watching the 3D scene.

The DOM is a tree structure that lets a browser expose an HTML document to JavaScript. Elements such as `<div>` and `<button>` are managed as DOM nodes. JavaScript can change their content and styles and attach click handlers.

The 3D scene in `webg` is drawn to the canvas used by WebGPU. Code refers to this element as `canvas`. It is a pixel-based drawing surface: 3D models, the background, and the canvas HUD appear as part of its rendered image. Explanations, buttons, and error panels can instead be placed outside or above the canvas as HTML elements. This chapter calls that path a DOM overlay.

Canvas HUDs and DOM overlays both appear on top of the scene to the user, but their internal paths differ. A canvas HUD is part of WebGPU rendering and can be drawn alongside the 3D scene. The standard text path is intended for short Latin text, numbers, and symbols. `Message` suits short canvas text. Choose the browser-backed `OverlayPanel` for multilingual typography, variable-width fonts, text selection, scrolling, or buttons.

DOM overlays use the browser's HTML rendering, so they naturally support multilingual and longer text, buttons, scrolling, copyable text, and input fields.

This gives a clear division of work: use the canvas HUD for short status and the DOM for readable explanations and interactive UI. Choose based on rendering flow and purpose, rather than only on which element appears visually on top.

## Use `Message` for Lightweight Status

`Message` manages concise text over the canvas as a HUD. It wraps the lower-level `Text` class, which directly handles the character grid, in a more convenient API. It provides concepts such as an `id`, an `anchor` position, and multi-line blocks. In typical applications, `app.message.setLines()` is the usual entry point.

For example, show the current score and elapsed time in the upper-left corner:

```js
app.message.setLines("status", [
  `score=${score}`,
  `time=${elapsedSec.toFixed(1)} sec`
], {
  anchor: "top-left",
  x: 0,
  y: 0
});
```

Create a separate block with a different `id` for a control guide at the bottom of the screen:

```js
app.message.setLines("guide", [
  "Drag: orbit camera",
  "Wheel: zoom",
  "R: reset camera"
], {
  anchor: "bottom-left",
  x: 0,
  y: -2,
  width: 36,
  wrap: true
});
```

Use `Message` for short, intuitive information that can stay visible without obstructing the view: score, lives, current mode, debug state, camera distance, or selected coordinates.

Place the following information in `OverlayPanel`, which can use browser DOM features:

- Detailed multilingual explanations
- Long error messages
- Stack traces and detailed diagnostic reports
- Interactive UI with buttons or choices
- Text that users need to scroll through

`Message` is a lightweight HUD based on a standard font atlas and character grid. Use a DOM overlay for multilingual text and characters outside the HUD font atlas.

## Use `OverlayPanel` for Readable Information

`OverlayPanel` is a DOM panel displayed over the scene. It handles multilingual explanations, help, errors, long reports, briefings, buttons, and choices.

`OverlayPanel` is a general-purpose display surface, rather than a help-only or error-only class. Options express differences between use cases.

Here is a minimal help panel:

```js
app.showOverlayPanel({
  id: "help",
  title: "Help",
  lines: [
    "Drag: orbit camera",
    "Wheel: zoom",
    "H: hide help"
  ],
  anchor: "top-left",
  format: "plain",
  collapsible: true,
  closable: false
});
```

Use `text` for one string or `lines` for an array of lines. Supplying both makes the content ambiguous, so `OverlayPanel` reports an error.

```js
app.showOverlayPanel({
  id: "note",
  title: "Note",
  text: "Use this form when passing one string",
  anchor: "bottom-left"
});
```

Set `format: "pre"` to preserve whitespace and line breaks, as in an error log:

```js
app.showOverlayPanel({
  id: "load-error",
  title: "Load Error",
  text: error.message,
  anchor: "bottom-right",
  format: "pre",
  scrollY: true,
  closable: true,
  showCloseButton: true,
  maxHeight: "40vh"
});
```

Help, errors, and reports can all use the same `OverlayPanel`. Learn the purpose of options such as `anchor`, `format`, `scrollY`, `collapsible`, `buttons`, and `choices` rather than memorizing a class for every use case.

## Anchoring and Avoiding the Debug Dock

When designing a DOM overlay, first choose where it should appear. Users focus on the center of the 3D scene, so a panel anchored there can obscure important visual information.

`OverlayPanel` supports these `anchor` values:

| `anchor` | Typical use |
|---|---|
| `top-left` | Control guide and supplementary help |
| `top-center` | Temporary notice |
| `top-right` | Status and supplementary information |
| `middle-left` | Left-side menu |
| `middle-center` | Modal and dialog |
| `middle-right` | Right-side inspector |
| `bottom-left` | Briefing and dialogue |
| `bottom-center` | Prompt and input wait |
| `bottom-right` | Log, error, and report |

Set `offsetX` and `offsetY` to adjust the margin from the anchor precisely.

```js
app.showOverlayPanel({
  id: "briefing",
  title: "Mission",
  lines: ["Alpha collects the beacon"],
  anchor: "bottom-left",
  offsetX: 16,
  offsetY: 16,
  width: 360
});
```

If a `DebugDock` is open on the right, a right-aligned panel may overlap it. Set `avoidDebugDock: true` to position the panel clear of the dock automatically.

## Build Help Panels from Options or Presets

Many applications show control instructions in a collapsible panel. In `webg`, help is represented by a combination of `OverlayPanel` options.

The direct form is:

```js
app.showOverlayPanel({
  id: "runtime-help",
  title: "Help",
  lines: [
    "Drag: orbit",
    "Wheel: zoom",
    "R: reset"
  ],
  anchor: "top-left",
  collapsible: true,
  collapsed: false,
  closable: false,
  showCollapseButton: true,
  collapseLabelExpanded: "Hide Help",
  collapseLabelCollapsed: "Show Help"
});
```

Use the helper in `OverlayPanelPresets.js` to assemble the same options more compactly:

```js
import { buildHelpPanelOptions } from "../../webg/OverlayPanelPresets.js";

app.showOverlayPanel(buildHelpPanelOptions({
  id: "help",
  lines: [
    "Drag: orbit",
    "Wheel: zoom",
    "R: reset"
  ],
  anchor: "top-left"
}));
```

`buildHelpPanelOptions()` is a helper that creates an options object; it does not create another UI class. `OverlayPanel` still performs the display.

## Separate Error Display from Diagnostic Reports

Show complete error messages and diagnostic information in an `OverlayPanel` that users can read carefully. Keep the HUD for changing current values.

An error panel can be written as follows:

```js
app.showOverlayPanel({
  id: "start-error",
  title: "Start Error",
  text: error.message,
  anchor: "bottom-right",
  format: "pre",
  scrollY: true,
  closable: true,
  showCloseButton: true,
  maxHeight: "40vh"
});
```

The error helper in `OverlayPanelPresets.js` is another option:

```js
import { buildErrorPanelOptions } from "../../webg/OverlayPanelPresets.js";

app.showOverlayPanel(buildErrorPanelOptions(error, {
  id: "load-error",
  title: "Load Error"
}));
```

When an error should also be shared with developers or analysis tools, record it as a report in `Diagnostics`. Think of `OverlayPanel` as a place to read information and `Diagnostics` as a place to record state.

## Control Briefing Flow in the Application

Dialogue, tutorials, and mission briefings need flow control as well as display: advancing to the next entry, choosing an option, branching, and resuming the game after closing the panel.

`OverlayPanel` returns actions from buttons and choices. The application keeps the text queue and branching rules. This separation lets the display component and scenario flow be designed independently and keeps game-specific rules in the application.

A minimal briefing controller can live in the sample application:

```js
const briefingEntries = [
  {
    title: "Mission",
    lines: [
      "Alpha collects the beacon",
      "Escape when the goal opens"
    ]
  },
  {
    title: "Controls",
    lines: [
      "Arrow keys: move",
      "Enter: next"
    ]
  }
];

let briefingIndex = 0;

function showBriefing() {
  const entry = briefingEntries[briefingIndex];
  app.showOverlayPanel({
    id: "briefing",
    title: entry.title,
    lines: entry.lines,
    anchor: "bottom-left",
    width: 420,
    buttons: [
      { id: "next", label: "Next", kind: "primary" },
      { id: "close", label: "Close", kind: "secondary" }
    ],
    onAction: ({ actionId }) => {
      if (actionId === "close") {
        app.hideOverlayPanel("briefing");
        return;
      }
      briefingIndex += 1;
      if (briefingIndex >= briefingEntries.length) {
        app.hideOverlayPanel("briefing");
      } else {
        showBriefing();
      }
    }
  });
}
```

With this structure, `OverlayPanel` handles display while the application fully controls text order and branching.

## Modal Settings and Pausing the Scene

`OverlayPanel` provides two important options: `modal` and `pauseScene`.

`modal` concentrates DOM interaction on the panel. Use it for confirmation dialogs or a briefing before a game starts when users should focus on that panel.

`pauseScene` communicates to the application that the scene should stop progressing while the panel is visible. The game loop decides how to act on that state.

```js
app.showOverlayPanel({
  id: "confirm",
  title: "Start?",
  lines: ["Start with these settings?"],
  anchor: "middle-center",
  modal: true,
  pauseScene: true,
  buttons: [
    { id: "start", label: "Start", kind: "primary" },
    { id: "cancel", label: "Cancel", kind: "secondary" }
  ],
  onAction: ({ actionId }) => {
    if (actionId === "start") {
      app.hideOverlayPanel("confirm");
      startGame();
    }
  }
});
```

The update loop can check this state and skip game logic when needed:

```js
app.start({
  onUpdate: ({ deltaSec }) => {
    const confirm = app.getOverlayPanel("confirm");
    const state = confirm?.getState?.();
    if (state?.visible && state.pauseScene) {
      return false;
    }

    updateGame(deltaSec);
    return false;
  }
});
```

This lets the application decide whether to pause the scene, while the UI component reports the requested state.

## Record and Share Diagnostics

Many internal states in a 3D application are difficult to understand from the visible display alone. The camera's exact orientation, the number of loaded shapes, shader settings, and input response are difficult to reproduce or share if they appear only in the HUD.

In `webg`, treat `Diagnostics` as the canonical record. Create a report first, then send it as needed to `DebugDock`, the console, copyable text, JSON, or an `OverlayPanel`.

`DebugDock` is a development aid for desktop use. It can collect controls, diagnostic reports, and probe state on the right side of the screen, allowing detailed monitoring without filling the canvas HUD.

Use this placement guide:

- **Current values the user should grasp immediately** → `Message`
- **Explanations the user should read** → `OverlayPanel`
- **State to share with developers or analysis tools** → `Diagnostics`
- **Details to monitor continuously during development** → `DebugDock`

This separation is especially useful for AI-assisted debugging. A reproducible report makes it much easier to isolate a problem than adding more text to the visible screen.

## Use `Touch` as an Input Interface

`Touch` displays DOM buttons and produces key states or actions such as `arrowleft`, `space`, `enter`, and `r` in place of a keyboard. Use `OverlayPanel` for explanatory text.

Choose by purpose rather than routing every button through `Touch`:

- **Enter movement, confirm, or reset input on a touch device** → `Touch`
- **Show explanations or choices over the scene** → `OverlayPanel`
- **Show temporary commands or simple settings over the canvas** → `CommandPalette`
- **Show a concise current value** → `Message`

Keeping these roles distinct makes input and presentation easier to manage.

## UI Implementation Decision Flow

Use the length of the information, its update frequency, and whether it needs interaction to choose among `Message`, `OverlayPanel`, and `Touch`. Choosing by purpose keeps input and display responsibilities clear as the UI grows.

1. **Classify the information**: Is it a short current value or text to read?
2. **For short Latin text, numbers, and symbols showing current values**: Use `Message`.
3. **For multilingual or long text, buttons, or choices**: Use `OverlayPanel`.
4. **For flow control such as ordering or branching**: Implement a controller in the application.
5. **For temporary commands or lightweight settings on the canvas**: Use `CommandPalette`.
6. **For investigation or sharing**: Record a report with `Diagnostics`.
7. **For touch input**: Add `Touch` as an input API.

In loader samples, choose the display surface by the length and purpose of the information. Show a short loading status in `Message`, the full failure reason in `OverlayPanel`, and loading targets or statistics in `Diagnostics`. This division keeps the UI easy to follow.

## Summary

This chapter organized the criteria for choosing text displays in `webg`:

- Short Latin text, numbers, and symbols in a HUD → `Message`
- multilingual or longer text, help, errors, and explanations with buttons → `OverlayPanel`
- Compact setup for standard options → `OverlayPanelPresets`
- Temporary commands, toggles, staged changes, and choices over the canvas → `CommandPalette`
- Dialogue and briefing flow → application-side controller
- Investigation records → `Diagnostics` / `DebugDock`
- Touch input → `Touch`

This classification encourages you to think about which information belongs on which display surface, rather than which class name to use. Chapter 13 examines how this division is implemented through the canvas HUD and DOM overlay structures.
